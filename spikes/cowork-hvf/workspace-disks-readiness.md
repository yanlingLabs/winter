## API and ownership

`krun_set_cowork_workspace_disks(ctx, data_fd, data_identity*, environment_fd, environment_identity*)` is one atomic pair setter. The C identity ABI is 32 bytes: device, inode and capacity as uint64, UID and mode as uint32. Both inputs are borrowed for the synchronous call. The library duplicates first with `F_DUPFD_CLOEXEC` and owns each copy immediately. It checks the pinned descriptor is regular, current-UID owned, exact0600, single-link, O_RDWR/non-append, recorded device/inode and exact capacity. Geometry is 16MiB–256GiB, aligned4096. FD<3, closed/missing FD, directory/socket, wrong identity/mode/size/access, duplicate pair setter and same-inode aliases refuse. After both intake steps, both descriptors are revalidated before publication. A failed second intake closes the newly owned first copy too, preserving caller descriptors. Context-free closes unstarted copies; it never supplies disk-release/native-stop proof.

`ExpectedVolume` is corroborating metadata, not a capability. A caller who can obtain two valid FDs can invoke this developer API; no claim is made that the library authenticates daemon, home, workspace, controller, worker/incarnation/lease or signed runtime image. Those remain the mandatory native launch adapter's responsibility. Mutable same-user files can drift after a check; this is neither encryption nor cryptographic content integrity.

Workspace disks occupy an independent resources field, never path-backed `BlockDeviceConfig` values. The profile requires both volumes, exactly one generic runtime port and the existing guarded reclaim profile; path configs (including dormant legacy root/data fields), prebuilt/extra block devices and HVC combinations refuse. Existing one-path-backed-RAW fixture validation stays unchanged when no workspace pair is present. The fixed2vCPU/768MiB limit is a conservative developer gate, not the user's eventual automatic demand/pressure-aware sizing policy.

## Native storage and device construction

The pair produces further owned admitted descriptors, carrying their original expected metadata. `BlockBuilder::from_cowork_workspace` constructs both devices in a local temporary list, revalidates the pair, then publishes the complete list. Partial failures drop both pending descriptors and any already constructed block. IDs are fixed `winter-data` and `winter-environment`, with capacities from the admitted RAW backing files. No volume filename is stored, no `/dev/fd` workaround is used, and no volume path is reopened.

The reviewed adaptation is a narrow `PinnedRawStorage` implementation of the pinned imago Storage trait. `imago::File::try_from(std::File)` was deliberately not used: inspected imago0.2.3 `file.rs:611–661` performs an alignment pread/pwrite probe at offset1, even during construction. The descriptor storage constructor only validates metadata. Positional I/O validates the expected identity/geometry/access and checks whole-vector offset+length before any transfer, completes short reads/writes, retries Interrupted and surfaces zero-transfer/EIO/overflow failures. Unexpected premature EOF is an error. Resize/growth and filename/open/create/relative-path fallback are unsupported; raw-wrapper grow/shrink refusal is tested. Flush has no internal buffered data; full sync uses `File::sync_all()` as the pinned full-sync path does, with no relaxed override, and propagates errors. This is an independently reviewable new storage boundary, not an assertion of general behavioral equivalence with imago's path constructor or power-loss/drive durability proof.

Native tests verify intake and both actual RAW constructors preserve size, nanosecond mtime, full bytes and allocated block count before explicit I/O. After both original names are renamed, replacement names contain unrelated bytes, and caller FDs close, actual RAW writes/readbacks still use the admitted inodes. Replacements remain unchanged. No formatting, filesystem signature/readiness or guest mount is invented.

## Reclaim IDs and resource bounds

The workspace access coordinator has exactly3 device slots: data0, environment1 and generic runtime2. The VMM's guarded block loop registers the two ordered block entries as0/1; runtime registration selects2 only for this profile. The old one-disk/runtime profile keeps0/1. The global budget is48 pins and8MiB pinned bytes, with no unpin-on-limit fallback.

The aggregate test accounts for each 256-entry block ring twice (permanent pin and request protection), each <=1MiB block payload plus17 header/status bytes, the four32-entry generic rings, two <=1MiB reported RX chains, <=64KiB data TX and8-byte control TX. That admitted workload is below8MiB. Malicious excess header/report geometry can still exceed this conservative budget and be refused; it is not silently accepted. Tests require unique IDs, unchanged existing pin accounting after byte/count limit refusals, all three pin identities present at freeze, and retained pins after terminal stop until actual owning Pin objects drop. These are native coordinator tests, not two-disk Linux active-RAM-return evidence.
