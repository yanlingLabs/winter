# CLAUDE.md

Guidance for Claude Code (claude.ai/code) when working in this repository.

## What this is

Winter is a macOS-native AI assistant: a TypeScript/Bun daemon (`winter-core`) plus a native Swift menu-bar app. They speak JSON-RPC 2.0 over NDJSON on a Unix socket (`<WINTER_HOME>/run/core.sock`; default home `~/.winter`). The daemon is the single source of truth; every client — CLI, Mac app, phone — is a view over its event stream.

**The daemon runs no agent loop of its own.** Every session is a runtime child driven through the router (`@yanlinglabs/winter-runtime-sdk`) on the **Winter leg** — the Winter agent runtime, the only one. Every model runs on it, Claude-catalog models included. Code sessions spawn it as a `winter` binary from `@yanlinglabs/winter-agent-sdk`; **chat and dispatch run it EMBEDDED** in `winter-core`, one Bun Worker per session (`runtime-sdk/embedded.ts`, the `@yanlinglabs/winter-agent-runtime` package — WS-23). Both topologies speak the same NDJSON frame stream to the same `query()`, so the projector, approval bridge and `sdk_mcp_call` cannot tell them apart. WS-23 retired the **official leg** (Anthropic's own `claude` binary); the daemon no longer loads `@anthropic-ai/claude-agent-sdk`, and a session that leg created is adopted onto the Winter leg at its next resume (see "Which runtime a session runs on").

The daemon owns everything around that child: IPC, event-sourced session storage, settings, approvals/questions, the capability tools it hands the child over MCP, the hooks, and the SDK-message→`SessionEvent` projector. Session modes are `code`, `dispatch`, `chat` (`SessionMode`, `runtime-sdk/create.ts`).

### Profiles — which daemon you are talking to

The home and the profile are set INDEPENDENTLY, and the home is profile-blind: `resolveWinterHome()` reads only `WINTER_HOME` and defaults to `~/.winter` — the user's live daily driver (`winter-dir.ts`). `WINTER_PROFILE=dev` changes only the Keychain service (`com.winter.core.dev`) and the app identity ("Winter Dev", `com.winter.app.dev`); it does NOT move the home. So `WINTER_PROFILE=dev` alone would run dev-profile tooling against `~/.winter` — always set BOTH (`WINTER_HOME=~/.winter-dev WINTER_PROFILE=dev …`). The `~/.winter-dev` convention is supplied by the `winter-dev` wrapper script (it exports `WINTER_HOME` for you), not by core code. The `dist` profile is `~/.winter` + `com.winter.core` + `Winter.app` (`com.winter.app`). `profile.ts`'s `keychainService()` honours `WINTER_KEYCHAIN_SERVICE` only when the caller passes a home that is *not* the profile's default, which is how tests stay off the real Keychain.

**The dev daemon is a compiled `winter-core` signed by Winter's team** (WS-27), never Homebrew `bun`: a Keychain item's partition list is its CREATOR's team (`auth/app-token-acl.ts`'s header), so a `bun`-run daemon creates items Winter Dev is asked about once per pairing token. `bun run dev:daemon` (`scripts/dev-daemon.ts`) runs `compile:core` into `dist/dev/winter-core` (never `dist/winter-core`, which the `verify:*` gates rebuild; built to a temp file and renamed, so never over a running daemon), signs it with the codesigning identity whose certificate's OU is `WINTER_TEAM_ID` (Apple Development preferred; `WINTER_DEV_SIGN_IDENTITY` overrides) under the stable identifier `com.winter.core.dev` and a STATED designated requirement (`identifier "com.winter.core.dev" and anchor apple generic and certificate leaf[subject.OU] = "<team>"` — any Winter-team certificate satisfies it, so the Keychain keeps trusting every rebuild), hardened runtime + `scripts/winter-core.entitlements`, checks the recorded requirement and the team and runs `__keychain-ffi-probe`, then runs `daemon run` with `WINTER_HOME=~/.winter-dev WINTER_PROFILE=dev` — and `WINTER_RUNTIME_EXECUTABLE`/`WINTER_ANT_EXECUTABLE` resolved under bun, since a compiled binary cannot reach the npm platform package or search `$PATH` for `ant`. `--no-build` reuses the binary; any other arguments are run through it instead of `daemon run` (`bun run dev:daemon credentials list`).

```sh
bun run dev:daemon                  # build + sign + run the dev daemon
bun run dev:daemon --transition     # ONCE, dev daemon stopped: move the bun-created dev items to the signed binary
```

Before `--transition`, quit Winter Dev and stop every dev daemon, a launchd-managed one included (`launchctl list | grep -i winter`): between the transition and the signed daemon's first boot the pairing tokens are self-only (that boot re-widens them for Winter Dev), and a `bun` daemon relaunched afterwards is prompted for every item.

**The transition is one-way.** Items `bun` created would prompt the signed binary once each, so `--transition` (run under `bun`, their creator) reads each value and hands it over a pipe to `dist/dev/winter-core __dev-keychain-adopt`, which re-creates the item as itself — shadow, delete (by bun), add, read back, drop the shadow (`auth/dev-keychain-transition.ts`), holding the home's credential migration lock (the child refuses unless its parent holds it) and the boot lock; it refuses while `core.lock` names any live process, socket or not (unless that pid started after the lock was written — a reused pid). Bun's own leftover shadows are recovered first and adopted too; a child that exits or stops answering (30 s per request) stops the run with no marker. Crash-safe and idempotent: if interrupted, run it again. Until it has run, `bun run dev:daemon` refuses to start the signed binary on `~/.winter-dev` (an item bun can still read silently means bun still owns them). Afterwards EVERY dev-profile process must be that binary — a `bun`-run dev CLI or daemon (`bun src/main.ts` with the dev env, the old `winter-dev` wrapper) is prompted for each item it reads, the admin token first. Point `winter-dev` at the signed binary:

```sh
#!/bin/sh
exec bun "<repo>/scripts/dev-daemon.ts" --no-build --cli "$@"
```

`--cli` runs exactly `dist/dev/winter-core <args>` (no args: the TUI) on `~/.winter-dev` with the dev profile and the runtime paths — after the same pre-start check `bun run dev:daemon` makes (a bun startup plus one attributes-only listing). Tests are unaffected: they use temp homes, file stores and the throwaway Keychain service.

Two traps: a plain `winter` is the DIST CLI and, on a dead socket, auto-launches the dist app — never use it for dev or test work. Debug app builds embed neither `winter-core` nor the runtimes, so "Winter Dev" cannot spawn its own daemon; start the dev daemon first or the orb shows disconnected.

### Where the runtime binaries come from

**Embedded chat/dispatch need no binary.** `create.ts`'s `spawnHookFor(mode)` is the one topology site: code resolves the `winter` ladder below; chat and dispatch get the daemon's embedded host (`createEmbeddedSessionHost`, owned by `daemon.ts`, drained in `stop()` before the stores close). A Worker is constructed from `packages/cli/src/embedded-worker.ts` — a SECOND `compile:core` entrypoint, reached by the plain string `"./embedded-worker.ts"` in the compiled binary (a `new URL(…, import.meta.url).href` hangs there) and by `core`'s own `embedded-worker-entry.ts` in dev. That file imports only `.build/embedded-worker.bundle.js`, which `compile`/`compile:core` first build from `src/embedded-worker.source.ts` ALONE: bundled beside `src/main.ts` (whose dynamic `import()`s of core/protocol make Bun wrap shared modules like zod in `__esm`), the npm-installed runtime's Worker died at load (`new ZodLazy` is not a constructor) — `test/compile-core.test.ts` loads the real two-entry bundle to catch it. The runtime, the wrapper and `REQUIRED_WINTER_AGENT_SDK` are version-locked (exact pins, and `embeddedVersionCheck` at boot and at every spawn): a mismatch refuses chat/dispatch typed (`embedded_runtime_unavailable`), never a fallback to the binary. An embedded session's Workflow tool spawns `winter-core __runtime-workflow-worker --bridge` (the runtime's worker), never `__workflow-worker` (the daemon's own). `pid` is `null` for an embedded session; tests observe its Worker through `daemon.embedded.live()`.

`winter` (`runtime-sdk/executable.ts`, `resolveWinterExecutable`), for code sessions: `settings.runtimes.winterExecutable` → `$WINTER_RUNTIME_EXECUTABLE` → `<dirname(execPath)>/runtimes/winter` (Release bundle only) → `<WINTER_HOME>/runtimes/bin/winter` → the optional npm platform package `@yanlinglabs/winter-agent-sdk-darwin-arm64`. An explicit setting/env path is authoritative — if it is missing, that is the failure, never a fall-through to a different binary. The package rung refuses a version differing from `REQUIRED_WINTER_AGENT_SDK` (`runtime-sdk/versions.ts`) and is resolved *through the wrapper's own* `require`, because bun's isolated linker nests it under the wrapper. So a plain `bun install` is enough for a dev daemon.

`ant` (`runtime-sdk/bundle-layout.ts`, `resolveAntExecutable`) — the Console's login and token-refresh door, never a session runtime: `settings.runtimes.antExecutable` → `$WINTER_ANT_EXECUTABLE` → `<dirname(execPath)>/runtimes/ant/ant` → `$PATH` (skipped entirely in a compiled binary).

The Release bundle carries two records beside the binaries (`RUNTIME_BUNDLE_LAYOUT`): `runtimes/VERSIONS.json` (schema 2 — the winter pins and its pre-sign checksum; a schema-1 record is the pre-WS-23 `claude-official` shape and is refused by name) and `ant`'s own `runtimes/ant/VERSIONS.json` (its tag and pre-sign checksum, written by `embed-runtimes.sh` and held to the repo-root `VERSIONS.json` pin by `release-lib.ts`'s `verifyAntEmbed`). No `claude` binary is staged, and `runtimes.claudeExecutable`/`$WINTER_CLAUDE_EXECUTABLE` are read by nothing.

`bun run build:winter` builds `dist/winter` from a sibling `../winter-agent-sdk` checkout; point a daemon at it explicitly:

```sh
WINTER_RUNTIME_EXECUTABLE="$PWD/../../dist/winter" WINTER_HOME=~/.winter-dev WINTER_PROFILE=dev bun src/main.ts daemon run
```

**No session reads the Keychain itself** (WS-25 §7). macOS asks for consent whenever a process reads an item ANOTHER binary created, so a code session's `winter` child used to prompt once per credential item per binary identity (per rebuild, on a dev build). Now the daemon sets `Options.onCredentialResolve`, the SDK puts `hostCredentials: true` on the child's wire config, and the child builds no Keychain store at all: each credential it needs is asked of the daemon over its control channel (`credential_resolve`, `runtime-sdk/host-credentials.ts`) and answered by `winter-core`, the binary that created the items — so nothing prompts, in code sessions or in embedded chat/dispatch alike. A standalone SDK user with no host handler keeps the SDK's own Keychain store. `build:winter --sign <identity>` (or `$WINTER_RUNTIME_SIGN_IDENTITY`) still re-signs with the stable identifier `com.winter.runtime`, which matters only for a `winter` binary run without a daemon.

## Architecture

### Monorepo layout

- `packages/protocol` (`@yanlinglabs/winter-protocol`) — the contract: zod schemas for every JSON-RPC method (`methods.ts`) and `SessionEvent` variant (`events.ts`). `scripts/generate.ts` emits a JSON schema plus one canonical fixture per event variant and copies the event fixtures into the Swift test bundle; it never reads `methods.ts`.
- `packages/core` (`@yanlinglabs/winter-core`) — the daemon: `runtime-sdk/` (router handle in `create.ts`, the session driver table in `session-driver.ts`, `Options` assembly in `mode-options.ts`, hooks in `hooks.ts`, the model-switch review in `handoff.ts`), `projector/`, `capabilities/`, `agent/` (approvals, gate, memory, skills, sandbox, LSP, and the daemon-owned tools in `agent/tools/`), `sessions/`, `runtime-state/`, `providers/` (the daemon's own internal model calls; Codex OAuth), `plugins/`, `routines/`, `workflows/`, `panel/`, `migration/`, `settings*.ts`.
- `packages/core/src/workflows/` — model-authored JS orchestration run in a **sandboxed subprocess**: the daemon self-spawns its own binary as `__workflow-worker` under a macOS seatbelt, with an NDJSON stdio bridge. That worker, and the runtime's `__runtime-workflow-worker --bridge` (embedded sessions' Workflow tool), refuse to run (exit 77) before reading any input unless they are inside a sandbox that denies them the Keychain's mach services (`workflows/sandbox-guard.ts`: `sandbox_check` over bun:ffi, its variadic name bound by hand on arm64) — so the same binary launched bare cannot be made to run a script with `winter-core`'s rights. Dev and compiled paths differ — `bun run verify:workflow` is the compiled-binary proof (the round trip, plus both workers' refusal legs) and must stay green.
- `packages/cli` (`@yanlinglabs/winter-cli`) — the `winter` command: Ink/React TUI, headless `-p`, launchd daemon lifecycle, and the `credentials` / `login` / `doctor` / `migrate` / `model` / `workflow` / … verbs.
- `packages/plugin-sdk` — what third-party plugins build against. Plugins are separate processes granted narrow, user-consented capabilities; `examples/battery-limiter` is the reference plugin.
- `apple/WinterProtocol` — Swift mirror of the protocol types; its round-trip test decodes and re-encodes every generated fixture and asserts the exact count.
- `apple/WinterKit` — the Swift daemon client (`WinterClient`), `WinterSessionKit` (phone-facing), and the `Gateway` that mediates the phone over Iroh.
- `apple/WinterChatKit` — the phone's own chat engine.
- `apple/Winter` — the menu-bar app (xcodegen `project.yml`, no committed pbxproj). Release builds embed `winter-core`, `WinterHelper`, and the `winter` runtime plus `ant` under `Contents/Resources/runtimes/` (`scripts/embed-runtimes.sh`).
- `scripts/release.ts` + `scripts/release-lib.ts` — the release pipeline; `packaging/winter.rb.tmpl` is the Homebrew cask template it renders.
- `docs/superpowers/` is git-ignored (private design docs); never reference it from a committed file.
- The iOS app lives in a **separate repo** (`yanlingLabs/winter-ios`, checked out beside this one as `../norma-ios`). It consumes `WinterProtocol` + `WinterSessionKit` + `WinterChatKit` through the root `Package.swift` pinned to a **git tag of this repo** (`v-<name>-kitN`). Editing Swift sources here does nothing for the phone until commit → push → new kit tag → the iOS project's `revision:` bump + `xcodegen generate`.

### Which runtime a session runs on

Every session, every mode and every model runs on the Winter runtime. `create.ts`'s `selectRuntimeFor` still builds one `SelectionInput` — mode, requested model, the family listing derived from the pinned provider catalog, credential presence — and the router decides the provider/model row; the daemon states `hasClaudePeer: false` (it registers no official peer), so a Claude model selects `winter-agent` like any other, and `session-driver.ts`'s `decideRuntime` refuses typed (`runtime_selection_refused`, `data.reason: "runtime-unavailable"`) any selection naming another runtime. Refusals are typed `WinterLegRefusal`s forwarded as the JSON-RPC error's `data.code` (`winter_executable_unavailable`, `runtime_selection_refused` plus `data.reason`, `legacy_session_migration_refused` plus `data.reason`, `session_cwd_unavailable` — every incarnation checks the session's stored cwd first (`sessionCwdRefusal`, top of `optionsFor`) and refuses naming the path rather than letting the child die at spawn, …). There is never a silent fallback to another provider, another model or another directory.

**Sessions the official leg created** (`runtimeKind: "claude-agent"` in `runtime-state.db`; the protocol keeps the value, ruling R4) are **adopted at their next resume** (ruling R2, `session-driver.ts`'s `adoptLegacyRecord`, synchronous so `ensure()`'s no-await invariant holds): the transcript the `claude` binary wrote is re-keyed to the Winter cwd key (`rekeyForCanonicalCwd`), then `runtimeKind`/`selection`/`authRef` are rewritten to the Winter leg — provider, model and auth family carry over, so a `console/*` session stays a Console session. The Winter runtime reads claude's transcript entries, so the history reaches the model. `session.setModel` runs the same adoption before its review. It refuses typed `legacy_session_migration_refused`, moving nothing, when the transcript is already `repair-required` (`data.reason: "repair-required"`), when the re-key collided or was refused (`"transcript-collision"`, the record left `repair-required`), or for a `claude-oauth` selection (`"claude-oauth"`). `leg.ts`'s `sessionLegOf` still answers `"official"` for such a record until it is adopted. Migration C phase 2 and boot root recovery (`runtime-state/root-recovery.ts`) still reconcile an upgrading home's leftover official working copies and `claude-resume-*` roots through the router, for data safety; nothing creates new ones.

### Providers and credentials

The credential inventory is **derived from the pinned catalog**, never a hand-kept list (`runtime-sdk/keychain.ts`, `credentialInventory()`): every catalog provider whose `authKinds` includes `api-key`, whose `risk.class` is not `blocked`, and which does not require the user's own endpoint gets a Keychain slot at `<providerId>:default`. Four rows are pinned at the front (`openai`, `codex-oauth`, `anthropic`, and `console` → the fixed account `anthropic:console`); since WS-20 their order carries no meaning — a session names its provider in the tag. Every provider has exactly one slot: the Console bearer is filed under the `console` catalog provider (it was a second `anthropic` row until the WS-23 live-gate fix, which left `byProvider.console` unproducible and refused every `console/*` session at create), and `credentialPresenceFrom` counts an Anthropic account only when it holds its own kind (`ANTHROPIC_ACCOUNT_REQUIRED_KIND` — api-key in `anthropic:default`, bearer in `anthropic:console`), the same narrowing `credential.list` applies. A model is always a provider-qualified tag (`codex-oauth/gpt-5.6-terra`); `providerFor(tag)` names the credential and nothing in the daemon selects a provider for a bare id (WS-20).

The daemon **names** credentials on the wire and resolves them only in-process: `Options.provider.authRef` (and every other `authRef` — `advisor`, `web.search`, `web.fetch`) is a `{kind:"keychain", account, service}` locator, never the material. **Children receive credential material only over their control channel** (WS-25 §7, `runtime-sdk/host-credentials.ts`): a code child or an embedded Worker asks with `credential_resolve {ref, minGeneration?}`, and the daemon answers ONLY for the refs that incarnation's final `Options` named, the catalog slots of permitted AND credentialed providers (what a cross-provider subagent resolves), and `mcp-oauth:<id>` for the http/sse servers in the session's own MCP fold — everything else is `not_allowed`, and the pairing tokens and MCP client registrations/secrets never cross at all (`isNeverBrokered`). `winter-core` (the daemon, and the `winter` CLI — the same binary) is the only Winter process that reads or writes a credential item, which is what removes the prompts. That is not a security boundary against other processes running as the same user: any compiled Bun binary, `winter-core` included, can be made to run arbitrary code under its own signed identity through Bun's own launcher switch, which `bun build` offers no way to disable. What it does bound is the agent: a sandboxed `Bash` call cannot reach `securityd`, so a session's shell never reads an item. No refresh token ever crosses: provider `oauth` material goes without it, an MCP token record through `toSessionMcpTokenRecord`, and every refresh (Codex, the Console bearer, MCP sign-ins) is posted by the daemon, single-flight per item, so a rotating refresh token is never replayed by two processes. Each item carries a derived `generation` (a digest of the last value handed out — API keys included), so a child that got a 401 asks again with `minGeneration`. The material travels only in the one `control_response` frame — never argv, env, `Options`, `runtime-state.db`, the session JSONL, the remote stream or a log (tests pin each). Eviction still applies to provider keys (below), because an incarnation's `Options` carry facts derived from a key's PRESENCE (the Exa tool surface, an advisor or digest pin stated only while its slot holds material) and a removal must stop a child holding the old material; an embedded session is still a `WinterSession` incarnation. Three RPCs manage slots — `credential.list`, `credential.set`, `credential.remove` — and on the terminal `winter credentials [list] | set <id> | remove <id>` (masked prompt only, never a flag, a pipe or an env var). `winter login --anthropic-key` / `--api-key` and `winter logout --anthropic` / `--openai` write the same slots. All of these go through the daemon whenever the socket is live, and a write that reaches the daemon **replaces every live child whose record names that provider**, or whose cross-provider advisor pin does (`evictSessionsForCredential` — mid-turn children at their next idle boundary), so the key is in effect on the next turn with no restart. With no daemon running the CLI stores it and says so; live sessions pick it up at their next incarnation.

Two rows are daemon TOOL keys rather than provider credentials (raw values under their own long-standing secret names, `TOOL_ROWS` in `runtime-sdk/credentials.ts`). **`exa` is the exception to "a tool key evicts nothing"**: since the Exa key is named on a spawn (`Options.web.search.authRef`) *and* decides the tool surface, a write through the daemon evicts every **Winter-leg** child resumably, and `winter login --exa-key` goes through the daemon like a provider key. **`web-search`** (the Brave key) is retired: nothing reads it, `credential.set` refuses it typed, the row is listed only when something is actually stored and then only as removable (`manageable: false`), and `winter login --web-search-key` is a one-line deprecation notice.

**The app's two pairing tokens** (`harness-token`, `remote-token`) are the only Keychain items another binary reads, and they are re-created once so it can do so silently (WS-25 §7 B, `auth/app-token-acl.ts` over `auth/keychain-ffi.ts`'s bun:ffi to Security.framework): an item's ACL can only be changed with the keychain password, but its CREATOR may delete and re-add it, so at boot `winter-core` writes a shadow `<name>.migrating`, deletes the original, re-adds it with an ACL naming itself plus the Winter app by designated requirement, reads it back, drops the shadow and records a marker in `<home>/migration/app-token-acl.json` (re-run only when the trusted set changes or a token had to be minted). Real production boot on the profile's own default home only, never under an injected `secrets`, skipped when the keychain is locked, every call with user interaction disabled. A failure after the delete restores the value in-process at once; a shadow found without its original is restored BEFORE `ensureTokens` could mint a fresh token (which would unpair the app and the phone), and a shadow is dropped only when it equals its original. Trusted: dist — the app bundle `winter-core` lives in, nothing else (a local Release build shares `com.winter.app` and must not get the dist tokens); dev — this process plus the `com.winter.app.dev` bundles signed by Winter's team, inspected within one 5 s budget. The app retries a not-found read briefly, for the delete→add window.

**Every other daemon item trusts `winter-core` alone** (WS-27, `auth/credential-acl.ts`): the provider slots, tool keys, MCP sign-in items and the admin token are re-created once, by the same shadow → delete → add → read back → drop sequence (plus a re-read of the original just before the delete, skipping an item written meanwhile), with an ACL naming only this process — dropping the "Always Allow" grants older runtime binaries collected before children stopped reading the Keychain. The accounts are enumerated attributes-only (`listGenericPasswordAccounts` — nothing decrypts), the two app-read tokens and any `.migrating` shadow are excluded, values are compared as raw bytes (a value that is not valid UTF-8 is skipped, never re-added), and an item this process cannot read silently is skipped (counted, never prompted for). Same guards as the pairing tokens. The marker (`<home>/migration/credential-acl.json`) is keyed on the service AND this process's designated requirement, and is not written when nothing could be migrated; when the requirement cannot be read (codesign failed or timed out) only the recovery runs — a marker is never keyed on a path. An original that vanishes between the re-read and the delete stops that item: nothing is put back. **Every Keychain shadow pass and migration — these, the pairing tokens' and the dev transition — runs under the credential migration lock** (`auth/credential-migration-lock.ts`, `<home>/run/credential-migration.lock`: created atomically with its content by `link`, naming the holder's pid AND start time in epoch seconds (sysctl `kern.proc.pid`, `ps` pinned to `LC_ALL=C TZ=UTC` as the fallback — never a locale-formatted date) — a dead pid, a reused pid or our own pid we did not take is stale; an unreadable one younger than 5 s is held), never the boot lock, which treats a live pid with no answering socket as stale — and a booting daemon has no socket yet. A booting daemon that finds it held WAITS (up to 60 s, `auth/keychain-boot.ts`) and then refuses to boot, typed (`credential_migration_busy`, `winter daemon run` exit 75) — it never reaches `ensureTokens` without its recovery; the Mac app's `DaemonSupervisor` shows exit 75 as its own state ("waiting for another Winter process to finish updating credentials") and respawns after a back-off (5 s doubling to 60 s), never counting it as a crash. Under it, a restore-only shadow recovery runs before `credentialPresenceFrom` (so an interrupted migration never reads as a missing key); after the boot lock and Migration B (and only if the keychain is still unlocked) the full recovery, the migration, and — if the migration failed — a restore-only pass again before `ensureTokens`. A credential's shadow beside its original is always stale (the original is the newer write) and the full recovery drops it — but a pairing token's DIFFERING pair is kept (either value could be what paired clients hold), in the transition too; every credential delete door (`KeychainSecretStore.delete`, the daemon's MCP OAuth store) deletes `<name>.migrating` too, so a removed credential can never be resurrected from one.

A session whose decided provider has no stored key refuses typed at the first turn (`runtime_selection_refused`, `data.reason: "no-credential"`) rather than a vendor 401 mid-turn. There is no daemon-side endpoint table and there must never be one: the catalog ships each provider's endpoints, and `settings.providers.<catalogId>.baseUrl` (`providerBaseUrlFor`) is the only override — hot, per provider. The legacy single-provider `settings.provider.baseUrl` is gone (WS-20): the v2→v3 settings migration copies a stored value into `providers.openai.baseUrl` once.

### The daemon's own background jobs

Session titles, the bash safety reviewer, the dreamer and the session cleaner are the daemon's OWN model calls — not a session, not a runtime child. They run through `providers/internal-router.ts`'s `resolve(role, settings)`, which answers `{provider, model, tag, effort}` or a typed refusal; the four consumers (`agent/titles.ts`, `agent/reviewer.ts`, `agent/dreamer.ts`, `sessions/cleaner.ts`) each take that one seam and skip their run on a refusal.

**They are decoupled from `settings.provider.model`** (2026-09-19). Which providers they can run on is `internalEligibleProviderIds()` (`settings.ts`): every catalog provider that is an ordinary model-role candidate (`permittedProviders()`'s floor), has a Keychain slot in `credentialInventory()`, whose adapter family the daemon can drive (`providers/internal-adapters.ts`'s table — bedrock/vertex are out because their `aws`/`gcp-*` material is refused by `credential-store.ts`; xai-oauth has no Winter login door; azure/oci/local are `requiresUserEndpoint`), and that is **not the reserved first-party Claude row** (`CLAUDE_FIRST_PARTY_PROVIDER_IDS`, only `cc` — the subscription arm). `anthropic` is eligible (WS-23): every model, Claude included, runs on the Winter agent SDK, so an Anthropic API key is an ordinary token-priced credential for these jobs, and a Claude-only home gets its titles and its bash reviewer on it. So is `console` (the WS-23 live-gate fix): `buildInternalProvider` hands the Anthropic adapter `connection.providerId: "console"` and the `anthropic:console` locator, the store returns the bearer, and the SDK sends it as `Authorization: Bearer` + the OAuth beta for that provider id only. That is an exclusion by provider ID, never by adapter family: `deepseek-anthropic`, `zai-anthropic` and friends merely speak the dialect and stay eligible.

A role with no explicit pin resolves through `internalRoleEffectiveTag`, and **Winter never chooses a model on a provider the user did not choose**: (1) `settings.provider.model`'s provider when it is eligible AND credentialed — its `terra`/`luna` family slot if it declares one, else `provider.model` itself (so a DeepSeek user with a DeepSeek key gets titles on DeepSeek with zero setup); (2) else a credentialed `codex-oauth`/`openai`, which both declare the slots; (3) else **no default at all** — the role reports `no-default-model` and is inert until the user pins one. A first draft had a rung picking "the provider's first non-blocked llm row"; measurement killed it (only 3 of 94 eligible providers declare a `terra` slot, and that rung chose things like `agentrouter/claude-opus-4-8` and a vision model). `cc` never answers at any rung — it sits outside the eligible set entirely.

Effort: the SDK's `mapEffort` validates against real descriptors, and `internalWireEffortFor` maps a role's effort onto the row it is about to run on and **drops** what the row cannot take — an unmappable non-`"none"` effort (e.g. the dreamer's `"medium"` on a row whose vocabulary omits it) is dropped rather than falling through to `implicitEffortFor`'s ordinary rule. `"none"` has its own rule (2026-09-22, after a dist cleaner/title timeout storm): a row with no effort vocabulary still sends nothing; a row whose vocabulary lists `"none"` itself still has it dropped (what those endpoints do with a literal `"none"` is unmeasured); but a row that reasons without a `"none"` tier is sent its **lowest declared effort** — never dropped to silence, because an effortless request lets the provider's own default (`"medium"` on `codex-oauth/gpt-5.6-luna`) escalate past what a role pinned to `"none"` for speed asked for. A failed cleaner judgment is not retried for 30 minutes (`CLEANER_RETRY_BACKOFF_MS`).

Quota is **one `QuotaManager` per provider** (`InternalRouter.quotaFor`), keyed like the `Provider` cache: a Codex usage-limit 429 carries an hour-scale retry-after and a shared ledger's `limitedUntil` would stall a healthy DeepSeek role. `daemon.status`/`sync.config` read the **`codex-oauth` ledger**, created at boot (`daemon.ts` reads `internalRouter.quota` once, with the map empty) — so a codex user's status is unchanged, and a non-codex home shows an inert zero/ok ledger, which is what it showed before this branch too. Token counters are one provider's alone, never a cross-vendor sum.

`winter login` (ChatGPT/Codex) and bare `winter logout` write `codex-oauth:default` **in-process** and cannot use `credential.set`, so the snapshot has two other carriers: the CLI pokes a live daemon through `credential.list` (whose handler reconciles the view), and the router self-heals — `view.refreshSoon()` (non-blocking, one probe per 30 s) on `no-internal-credential`, on `no-default-model`'s sibling refusals, on any `auth`-classified failure of the titler, the reviewer, the dreamer or the cleaner, and once per dreamer tick.

`providers/internal-view.ts` holds the ONE mutable fact — which eligible providers hold material — seeded from the boot probe and refreshed inside `credential.set`/`credential.remove` before they return. The wire, the default-tag readers and the dispatcher all derive from that snapshot synchronously, which is how they cannot disagree; a per-provider `Provider` instance is cached against `view.generation()` and the resolved base URL. One log line per change, never per call. `INTERNAL_PROVIDER_IDS` no longer gates anything — it survives only as the preference-order head.

Three `problem` reasons on `settings.modelRoles` are **derived, never persisted** (`providers/internal-role-problems.ts`): `provider-unsupported` (an explicit pin on a provider Winter's jobs cannot use), `no-internal-credential` (nothing eligible is credentialed) and `no-default-model` (something IS credentialed, but Winter will not name a model on it — the fix is a pin, not a key). A per-provider `no-credential` is the pre-existing reason, reused. They take precedence over a recorded `role-health.json` note and clear themselves the moment the condition clears. `setModelRole` refuses an internal role's tag only on the permanent facts and accepts an eligible provider whose key has not arrived yet (which then reports the pre-existing `no-credential`).

Effort is normalised at the boundary: the SDK's `mapEffort` validates against real descriptors and refuses both `"none"` on an openai/codex row and the dreamer's `"medium"` on a deepseek row, so `internalWireEffortFor` maps the effort onto the row — dropping an unmappable non-`"none"` effort, and sending the row's own lowest declared tier for a role's `"none"` (above). **Turn compaction is vestigial** — `agent/compactor.ts` has no production construction site (the runtime child compacts itself; `session.compact` answers `not_supported_on_winter_leg`), so it is not one of these jobs.

### Anthropic authentication

Claude models run on the Winter runtime like every other provider's. The arm is the tag's prefix: `anthropic/*` = API key, `console/*` = the Console profile, `cc/*` reserved.

- **api-key** — the ordinary Keychain slot (`anthropic:default`), named to the child as a locator like every other provider credential.
- **console** — the single login door is `ant auth login --profile winter` with `ANTHROPIC_CONFIG_DIR=<home>/runtimes/anthropic-config` (`winter login --anthropic-console`), driven by the SDK's own broker (`auth/console-profile-broker.ts`); the profile lands at `<home>/runtimes/anthropic-config/credentials/winter.json` (`consoleProfileCredentialFile`, `runtime-sdk/anthropic-paths.ts`), and `ant` is also the token-refresh and logout door. The broker keeps the bearer it mints in the Keychain slot `anthropic:console` — the `console` provider's one inventory row, which `credentialRefFor("console")` names to the child and Winter's own jobs alike. **Readiness is that slot, not the profile file**: presence, the router's create-time admission, `sync.config`'s models and `models.catalog`'s `credentialPresent` all read it (`credentialPresentProbe`), because it is what a turn sends; the profile is only the refresher's source (the broker's watcher deletes the slot when the profile disappears). `models.catalog` still reports `credentialDoor: "console-profile"` for it — the fix is a sign-in, never a pasted key — and `credential.set`/`credential.remove console` refuse typed (`credential_kind_unsupported`, door `provider.login`). A signed-out Console session refuses its next turn typed (`no-credential`, naming `winter login --anthropic-console`). A sign-in or sign-out through `provider.login`/`provider.logout` replaces the live `console` children and re-probes the internal-jobs view, like `credential.set`; the CLI doors poke a live daemon through `credential.list`. `provider.status` reports which Anthropic credentials exist (`effectiveAnthropicAuthFor` — the api key and the on-disk profile, presence only).

**claude.ai subscription auth is not shipped.** The official leg that could have used it is gone, and with it `runtimes.official.subscriptionAuth` and `OFFICIAL_SUBSCRIPTION_AUTH_APPROVED`. A `claude-oauth` credential family never routes to the Winter runtime (D28). A legacy session recorded with one is refused at resume rather than adopted.

**Retired settings still load.** `runtimes.claudeExecutable`, `runtimes.official.*` (a `.loose()` block, so any key there parses) and `runtimes.handoff.crossRuntime` are accepted and ignored. `settings.ts`'s `retiredRuntimeSettingKeys` names them in one boot log line, and `settings-apply.ts` logs once when a settings change introduces a new one. They never refuse boot and are never obeyed.

### Switching model mid-session

A switch never changes runtime — there is one. `session.setModel` runs `runtime-sdk/handoff.ts`'s `planAndApplySwitch`: a fresh `selectRuntimeFor` for the requested model, then the router's pre-flight review (`reviewSwitch`, reached through `runtimeSdkInternals(sdk).barrier`) for a change that crosses **families** (gpt → deepseek, claude → gpt):

- a lossy switch refuses typed (`handoff_confirmation_required`, carrying the warnings and what stays portable); `confirmLossy: true` is a one-shot confirmation for that call only and is never stored. An unreviewable switch (the review throws, or the session's directory row is missing even after `materializeDirectoryRow`'s one retry) is a prompt, never a silent apply or a refusal;
- an applied switch patches the runtime record (`selection`/`providerId`/`modelRef`/`authRef`), and `ipc/server.ts` refuses to write `meta.model` unless the record names the decided selection (the 1c invariant). A switch that changes PROVIDER evicts the live child at its next idle boundary, so the next turn runs against the new provider's endpoint and credential;
- a session the official leg created is adopted first (above); an adoption refusal is the switch's refusal.

The cross-runtime move — the router's handoff barrier (drain, stage, validate, `confirmInit`, deferral past a running turn, zero-turn re-selection) — is gone, and `runtimes.handoff.crossRuntime` is inert.

### The protocol change checklist

A new or changed **`SessionEvent` variant** touches, in order:

1. `packages/protocol/src/events.ts` — the zod schema.
2. `packages/protocol/scripts/generate.ts` — a canonical fixture for the variant.
3. `pnpm protocol:generate`.
4. `packages/core/src/projector/event-coverage.ts` — `PROJECTED_EVENT_COVERAGE` (`satisfies Record<SessionEvent["type"], boolean>`) is the one exhaustiveness map; core's `tsc` fails until it is updated.
5. `apple/WinterProtocol` — mirror the Swift type; the round-trip test asserts the exact fixture count, so it fails until synced.
6. `apple/WinterKit` — it has exhaustive `switch`es over variants (the `seq`/`sessionId` accessors); a new variant breaks compilation **there**, not in WinterProtocol.
7. Build WinterKit **and** the app, not just `swift test` in WinterProtocol — that is the only way to catch step 6.

A new **RPC method** engages none of steps 2-3 or 5 (`generate.ts` reads only `events.ts`): the zod schema in `methods.ts`, a handler in `ipc/server.ts`, the Swift call site if a Swift client needs it — plus the four remote mirrors below when it is remote-reachable.

**Adding a FIELD (not a variant) engages no compile-time trap at all**, so sweep the field's PRODUCERS BY MEANING, not by build breakage. `turn_completed.contextTokens` shipped correct on the daemon while `WinterChatKit`'s `ChatEngine` stayed a live second producer of the old shape, reaching the daemon's log verbatim through `sync.push` and past a consumer whose fallback accepted it. Ask: who else *writes* this event, in either language, and does the consumer silently accept their shape?

A new **transient** variant must be added to `TRANSIENT_EVENT_TYPES` *and* reach `REMOTE_STREAM_EVENT_TYPES` (which spreads that set, so membership is the edit). Omitting the first drops it for every remote client, silently and permanently; the parity tests pin "exactly the current set" and will **not** catch that direction.

### Event-sourced sessions

Every session is an append-only JSONL of `SessionEvent`s, each carrying `seq`/`sessionId`. Clients reconstruct state by replaying; the daemon rebroadcasts live events to attached harnesses. Provider `encrypted_content` / `reasoning_item.itemJson` is opaque: the session JSONL is its only sink — never log it, never write it into a model-readable transcript.

Durable per-session facts (the backend transcript id, provider, runtime kind, selection) live in `runtime-state.db` (`packages/core/src/runtime-state/`), which is why a resumed session re-reads its credential, model and connection at every incarnation.

### Remote surface & history (phone-facing)

- The remote-role method allowlist is **four hand-mirrored lists that move in lockstep**: `REMOTE_ALLOWED_METHODS` (`packages/core/src/ipc/server.ts`, currently 24 entries) + its literal parity test (`packages/core/test/ipc/remote-allowlist-parity.test.ts`) + Swift `Gateway.remoteAllowedMethods` (`apple/WinterKit/Sources/WinterKit/Gateway/Gateway.swift`) + its count test (`GatewayGateTests`). Adding a remote method is a deliberate edit to all four; the two tests are the drift tripwire. `REMOTE_ELIGIBLE_SESSION_MODES` (`code`/`dispatch`/`chat`) is a second, mode-level gate on every bare-`sessionId` method.
- `session.history` serves paged past events filtered by `HISTORY_EVENT_TYPES` (`packages/core/src/sessions/history.ts`) — an **allowlist, never a denylist**: `reasoning_item` must never pass it (a security sweep test pins this). Adding a type requires confirming the recursive per-event string cap bounds its large fields at every depth — the phone transport hard-fails on oversized frames, so an unbounded field is a silent connection-killer.
- The **live/replay** stream to a remote client is a *second* allowlist with the identical obligation: `REMOTE_STREAM_EVENT_TYPES` + `capEvent` (`packages/core/src/sessions/remote-stream.ts`), applied at the one `HubClient` construction in `ipc/server.ts` and gated on `authedRole === "remote"`. It is `HISTORY_EVENT_TYPES` ∪ `TRANSIENT_EVENT_TYPES` ∪ three stream-control types: history governs *persisted* replay and excludes transients by construction, so using history's set alone silently kills streaming. The three controls are retained by necessity — `harness_attached`/`harness_detached` are the Gateway's replay **terminator** (filtering them burns a 5 s watchdog per open) and `session_created` is pinned by `IrohE2ETests` as a fresh session's first frame. The Swift stack's apparent safety on `reasoning_item` is an accident of a missing protocol variant, not policy; this daemon-side guard is what makes it policy, which is why it does not live in the Gateway.
- **Transient events are one shared constant**: `TRANSIENT_EVENT_TYPES` (`packages/protocol/src/events.ts`, 11 types) ↔ Swift `SessionEvent.transientTypes`/`.isTransient`, with literal parity tests on both sides and a fixture-driven Swift equivalence test. `WinterClient`, `WinterSessionClient` and the remote-stream filter all **derive** from it — never hand-copy the strings. The daemon stamps a transient with the store's current `lastSeq`, so any client that dedupes them by seq drops all of them, forever, silently.

### Settings

`<WINTER_HOME>/settings.json` is watched (`settings-watcher.ts`: debounced, single-flight, keep-last-good on a torn file) and swapped atomically by `settings-apply.ts`; feature code reads live getters, never a boot snapshot. The runtime-facing keys (permissions allow/deny/additionalDirectories, `outputStyle`, memory, plugins, `mcpServers`) live in the shared runtime home instead — see below. **No setting and no credential change may ever require a daemon restart.** Concretely: the daemon's own reads go live on the next call; a live runtime child keeps the `Options` it was spawned with and picks up new settings at its next incarnation (`optionsFor` re-reads `deps.settings()` every time) — the one exception is a credential write through the daemon, which evicts the affected children resumably so the next turn is already on the new material. New settings follow the same shape: an `.optional()` block with its default spelled in exactly one reader function (`handoffCrossRuntimeEnabled`, `legacyProjectFilesReadEnabled`, `providerBaseUrlFor`, `pinsFor`, `winterOptionsFromSettings`, …), because an absent block never materializes zod's per-key defaults.

### Migration from the legacy home

On first boot the daemon migrates a legacy `~/.norma[-dev]` home into a pristine `~/.winter[-dev]` (absent, empty, or only empty bootstrap dirs) before creating anything else — `migration/migrate-b.ts`'s `planMigrationB`/`runMigrationB`, from `daemon.ts`'s boot hook. Auto-migration fires **only** when the home resolves to the profile's own default (`winter-dir.ts`'s `isDefaultWinterHome`), however it arrived; any other home (a temp dir, a custom `WINTER_HOME`, a CI home) logs one line and needs the explicit `winter migrate --from <legacyHome>`. Files copy byte-for-byte except the disposable set (`run/**`, `logs/**`, `cache/**`, `daemon.log`, `*.db-wal`/`*.db-shm` skipped; any `index.db` left for the runtime to rebuild) and `settings.json`, which is re-keyed (`migration/rekey-settings.ts` rewrites legacy env-var names and `~/.norma[-dev]` path segments; keys are never renamed). The known-name Keychain items (`auth/legacy-secret-names.ts`'s `MIGRATION_B_SECRET_NAMES`) copy from the legacy service to the current one, never overwriting an existing destination item. `<home>/migration/manifest.json` is written atomically after every step; a home caught mid-migration refuses boot typed (`home_half_migrated`) until `winter migrate --resume` or `--rollback` runs — the daemon never auto-resumes. `winter migrate-project [dir]` converts one project's `NORMA.md`/`.norma/` to `WINTER.md`/`.winter/` (`git mv` when tracked, content untouched). Until a project converts, Winter reads its legacy instructions file, rules, output styles and settings read-only when the Winter-named path is absent (`legacy.readLegacyProjectFiles`, default on), with a one-line deprecation notice folded into the session's system context. `winter doctor` reports migration status and a count — never names or values — of remaining legacy Keychain items, probed for PRESENCE only (`legacyKeychainPresence`, no data request), so counting them never raises a consent dialog.

### Shared runtime home (WS-21)

`<home>/sdk` is the runtime's shared home, in claude's formats (it was BOTH runtimes' home until WS-23; the Winter SDK keeps claude's formats) — `~/.winter/sdk` on the default profile home. It is the app home's one durable, claude-format config dir; `<home>/cache/runs/<id>` (below) is a disposable per-run VIEW onto it, never a second copy of record. `sdk/settings.json` (`permissions.allow`/`deny`/`additionalDirectories`, `outputStyle`, `autoMemoryEnabled`/`autoMemoryDirectory`, `enabledPlugins`) and `sdk/.winter.json` (MCP servers: `mcpServers` is the user scope, `projects[<root>].mcpServers` the local scope — the default of `winter mcp add`/`mcp.add`; a trusted project's `.winter/mcp.json` is the project scope, precedence local > project > user, and the repo-root `.mcp.json` is no longer read). Both project-named scopes key on the cwd's OWN git top (`gitRootFor`, `runtime-sdk/run-home-input.ts`) — a linked worktree's own top, never the main checkout `repoRootFor` follows a worktree to — so a session opened in a worktree reads and writes that worktree's own local/project MCP and settings tier, not the repo it was branched from; TRUST alone stays keyed on `repoRootFor` (a linked worktree of a trusted repo is trusted). Those keys moved out of `settings.json`: the daemon reads them only through the `sdk…` readers in `settings.ts` (`liveSettingsView` strips them from every live holder), writes go through `sdk-files.ts` (atomic, 0600, never over a file that does not parse), and the **settings split** (`migration/settings-split.ts`) copies each key once — per-key marker AND sdk-key-absent — at every boot on every home, never writing `settings.json` (its copies stay for a downgrade). The runtimes' STORE (`projects`, `skills`, `agents`, `file-history`, …) is `storeHomeFor(home)`: `<home>/sdk` when the linked router applies run homes, `<home>` on router 0.0.11.

**Run homes.** When the linked router exports `buildRunHome` (feature detection, `runtime-sdk/run-home-support.ts`), every incarnation awaits a per-run folder `<home>/cache/runs/<id>` (`runHomeInputFor`), built last so a refusal never leaves one behind, and the daemon stops stating what the folder carries: no `agents`/`plugins`/`skills`/`outputStyle`/`brand`, no saved allow rules, no project instructions/rules/output style, none of the five router-owned `WINTER_*` variables, and `settingSources: ["user"]` (the router refuses each typed; `isRunHomeError` forwards its code as `data.code`). The child's own `$WINTER_HOME` is THAT run folder — its discovery view, torn down with it — while `$WINTER_STORE_HOME` is the durable `<home>/sdk` the run folder is built from; a hook or fence written against `$WINTER_HOME` reads only the disposable copy, never the store. A folder is disposed only when the router says `safe`; a quarantined one is kept and recorded (`run_root_quarantine`, schema v7); a failed open disposes at once. Boot recovery reconciles recorded roots, leftover run folders and stale `claude-resume-*` roots through the router's `reconcileRootForRecovery` BEFORE deleting anything (`runtime-state/root-recovery.ts`, run late at the runtime-sdk site like §13 step 10). On router 0.0.11 none of this runs and every child launches as before.

**Migration C** (`migration/migrate-c.ts`) moves an old-layout home (real `projects/` or `skills/` content) into `sdk/` in two phases: phase 1 at the boot hook, after the lock and the settings load (preflight — a live lease, an unexpected `sdk/`, an unreconcilable official working copy or unconvertible plugins refuse BOOT — then move-dirs with relative compatibility links, copy-files, the split, convert-plugins, runtime-state), and phase 2 at the late site through the router's door (an upgrading home's leftover official working copies, the archive, the done marker — kept after WS-23 so nothing an old home holds is lost). Only the profile's default home migrates by itself; any other old-layout home refuses `sdk_home_migration_required` until the explicit `winter migrate --sdk-home [--home <dir>] [--resume | --rollback | --status]`, and a half-migrated one refuses `sdk_home_half_migrated` on every build until `--resume`/`--rollback`. `--status` alone is always allowed and reports the manifest's state without acting; `--rollback` never reverts what the user did after the upgrade. Stored model tags are never rewritten: `canonicalModelTag` (`runtime-sdk/model-tag.ts`) resolves a catalog rename ON READ — the live settings view, the runtime-state row decoder and `ModelTagSchema`'s transform — and only when the old tag no longer resolves and the new one does.

**Saved answers** from approval cards: "everywhere" → `sdk/settings.json`; "in this project" → the trusted project's `<git root>/.winter/settings.local.json` in claude's grammar (`agent/saved-answers.ts`; offered only for a trusted project; then `**/.winter/settings.local.json` joins the user's global git excludes, resolved as claude does). `<home>/permissions/projects.json` and `.winter/permissions.local.json` are read-only now; `winter migrate-project` moves their entries (and a repo-root `.mcp.json`) into the project. `winter doctor` reports the migration, the split, untranslated rules, leftover approved-rules entries and quarantined roots.

**Plugins are claude's own format**: `skills/`, `.mcp.json`, `agents/`, `hooks/hooks.json` inside the plugin directory, installed from a **directory marketplace** (a local path whose own manifest names installable plugins) and keyed everywhere as `"<name>@<marketplace>"` (`installed_plugins.json`, consent records, `setPluginEnabled`). `winter-plugin.json` is a Winter-only EXTRAS tier layered on top (`agent/plugin-manifest.ts`) — optional, and a plugin with none, or an invalid one, loads anyway via the legacy `plugin.json`-only path with no manifest and no log. An extras manifest that still declares `contributes.{…}` for what now lives in claude's own layout logs a one-line notice and ignores those keys; only the extras a manifest actually declares (not skills, MCP, agents or hooks, which ride claude's own loader) gate on the consent flow.

### Tool surface

Tool design deliberately tracks Claude Code's shape; `winter-vs-cc-tools.md` at the repo root is the live comparison.

The child brings the file, shell, search **and web** tools. The **daemon** contributes its own as in-process MCP servers named `winter__<key>` (`capabilities/`), which the child sees as `mcp__winter__<key>__<tool>` — the keys are `sessions`, `computer`, `browser`, `office`, `research`, `lsp`, `external` (plugin-contributed, dynamic per plugin). Per-mode exposure is `disallowedToolsFor(mode, exposure, …)` (`mode-options.ts`); `exposure` is `{ exaKeyPresent? }` (the leg argument went with the official leg).

**The web surface is the child's `WebFetch`/`WebSearch`** (the 2026-09-18 ruling; the daemon's own `web_fetch`/`web_search`/`ReadPage` and its multi-page research sub-agent are retired, and the `winter__web` server is gone). The daemon supplies what a built-in cannot reach by itself through `Options.web` (`webOptionsFor`): the Exa key as a Keychain **locator** (the child asks the daemon for the key over `credential_resolve`, never reading the Keychain), `pins.research` as `WebFetch`'s page-digest model (dropped rather than stated when it cannot resolve), and the dangerous-domain floor as `blockedDomains`.

The one daemon-owned web tool left is chat's and dispatch's **`Search`** (Exa ANSWER mode — `POST https://api.exa.ai/answer`, the key in the `x-api-key` header, a written answer plus its sources, the floor applied to cited urls). `/answer` cannot be called anonymously, so **exactly one of `Search` / `WebSearch` is exposed to chat and dispatch**, decided by whether an Exa key is stored: `exaKeyPresent(store)` (`runtime-sdk/credentials.ts`) is read once per incarnation and drives BOTH the capability-server build (`capabilities/research.ts`, via `CapabilitySession.exaKeyPresent`) AND `disallowedToolsFor` AND the chat/dispatch base prompts (`chatSystemPrompt`/`dispatchSystemPrompt`). Absent reads as "a key is stored" at every one of those doors. Both halves of the tool gate are required: a `disallowedTools` string naming a tool the server never advertised denies nothing, silently, and the reverse offers nothing, also silently.

**All of that is the DAEMON's chat, not the phone's.** Chat started on the iPhone runs `apple/WinterChatKit`'s own engine (Chat Slice D), which is a live SECOND producer of `Search` — still on Exa's `/search` shape with `numResults`, and still shipping its own `ReadPage`/research runner — and it has no `WebSearch`/`WebFetch` at all, so the "no Exa key falls back to `WebSearch`" rule does not hold there. Any statement about which web tools chat has must say which engine it means until a kit tag brings the phone along.

Hooks ride `Options.hooks` from one builder: `runtime-sdk/hooks.ts`'s `sessionHooksFor` returns `{ winter }` — plugin pre/post/failure hooks, the bash safety reviewer (gated to the `auto` policy), diagnostics-after-edit, the `fileDiff` producer behind the diff tabs, the **sandbox-escape floor** (below), and the dangerous-domain floor for `WebFetch`/`WebSearch` (registered last; a deny for a floor-listed `WebFetch` url, the floor injected into `WebSearch`'s `blocked_domains`).

Reads are deliberately unfenced except for the daemon's own state: `Read`/`Glob`/`Grep` deny `<home>/run` and `<home>/runtimes` plus the SDK's `claude-resume-*` staging dirs, `sdk/.winter.json` and a run folder's or staging root's generated `.winter.json`/`.claude.json`/`.credentials.json` plus their `backups/**` (claude's own `.claude.json.backup.*` copies), and the bash sandbox mirrors what a real path can express (`sandboxConfigFor`'s `denyRead` — neither SDK's sandbox takes a glob or regex, so the run-folder files are the deny rules' and the path-fence hook's). **Writes are denied to every self-grant path** by the write-tool deny rules (`controlPlaneDenyRules`) and the bash sandbox's `denyWrite` (`sandboxConfigFor(home, cwd)`): the three control-plane filenames (`permissions.local.json`, `settings.json`, `settings.local.json`) at any depth in any project and the user's global copies, agent definitions (`<home>/agents` and any `.winter/agents` — the sandbox, which takes only real paths, names the session's own `<cwd>/.winter/agents`), `<home>/run`, `<home>/runtimes`, `<home>/plugins`, `<home>/permissions`, all of `<home>/cache` and `<home>/trust.json`, and (WS-21) `sdk/settings.json`, `sdk/.winter.json`, `sdk/agents`, `sdk/plugins`, any `.winter/mcp.json` and `.winter/settings*.json`, and — for the cwd and its project root — the project's `.winter/` MCP list, settings tiers, agents and protected item directories. `sandboxConfigFor`'s `denyWrite` is the one list the escape floor derives from (`runtime-sdk/home-fence.ts`), so a new self-grant path goes there. `sdk/projects/**` outside each project's `memory/` is the runtimes' store: no deny rule or sandbox entry (that would take the MEMDIR with it), but the escape floor and the path-fence hook deny a write there.

**Protected paths** (`runtime-sdk/protected-paths.ts`): a trusted project's `.winter/{skills,commands,rules,output-styles}/**` on the walk from the cwd up to the root (never `$HOME`), `sdk/{skills,commands,rules,output-styles}/**` and `sdk/WINTER.md` load into every future session, so a write to one is a card in code under EVERY policy and a typed deny in chat and dispatch — from one unmatched `PreToolUse` path-fence hook (which also runs the control-plane fence, the store denial and the read denial), from the router's flag-layer ask rules (the same set, `protectedPathRules`), and from the bridge, which never auto-allows one (bypass/accept-edits/auto → card, dont-ask → deny). `<root>/WINTER.md` stays ordinary.

A **sandbox escape** (`Bash` with `dangerouslyDisableSandbox`) follows claude's rule, not an always-card: deny rules, the permission mode, allow rules, then the approval bridge. Escapes meet three fences built from ONE list (`runtime-sdk/home-fence.ts`: `sandboxConfigFor(home).filesystem.denyWrite` plus `<home>/agents`, `<home>/cache`, `<home>/trust.json`, any `.winter/agents` and the control-plane filenames): the bash sandbox's own `denyWrite`; the **escape floor**, a `PreToolUse` hook that denies under **every** policy, `bypass` included — any mention of `run`/`runtimes` or a self-grant store (`.winter.json` included), and `cache`/`plugins`/`sdk/plugins`, a project's `.winter/mcp.json`/`settings*.json`, `sdk/projects` outside `memory/` and `claude-resume-*` roots only in a write-shaped position (after a redirect or a write verb), so plugin skill scripts still run; and the bridge's write-tool fence (`controlPlaneTargetForCall`). The floor is a static match on the normalised command text (quotes stripped, `//`/`/./`/`..` collapsed, `cd` tracked), so a path the command builds at run time is out of its reach, as it is for any static check. Under `auto`, an escape that **reaches the approval bridge** runs only on the bash reviewer's positive clearance for that exact call and command (`bridge-common.ts`; reviewed with the unsandboxed premise — no reviewer, no model, a transient failure or a missing call id is a card in code and a typed deny in dispatch). A matching saved allow rule allows an escape natively (claude parity) unless a hook denies or asks — since agent SDK 0.0.20, which replaced the Winter runtime's old every-escape-is-mandatory-interaction rule with claude's, behind claude's own write-target checks.

**Saved allow rules reach the child** as `Options.permissions.allow` (code mode only; `persistedAllowRulesFor` → `sdkAllowRulesFor`, the one translation into claude's grammar, never wider than what was saved; deny still wins), read live per incarnation: `sdk/settings.json`'s `permissions.allow` (claude grammar, passed verbatim; Winter's own gate reads its inverse, `winterGateRulesFromSdk`); the old **approved-rules record** `<home>/permissions/projects.json` (`agent/approved-project-rules.ts` — now read-only, keyed by canonical project root, never read through a link, applied regardless of trust); and a project's in-repo `.winter/settings.json`/`.winter/settings.local.json`/`.winter/permissions.local.json` only when the project is trusted. On a run-home build the child reads all of these from its run folder's own settings tiers instead, and the daemon states none. The project root is `repoRootFor(cwd)`, which ignores a `.git` file whose git dir does not own the cwd. One claude-parity consequence is deliberate: a dispatch session's code-mode children receive them, as claude's headless mode does. (Under `plan` the Winter SDK still holds writes back.)

**Skills reach a child through its run folder, never from the daemon.** The run folder carries them: the user's `sdk/skills` (and `self`), a trusted project's `.winter/skills` walked nearest-first from the cwd up to the project root (`projectScopeRootFor`), and the enabled plugins, which the runtime loads natively through `enabledPlugins` (code mode only; a plugin's skills appear as `plugin:skill`); `settingSources` is `["user"]`. The daemon hands the child no skills or plugin views of its own (`session-driver.ts`; the old `<home>/cache/skill-plugins` handover is retired), and on a router without run homes (0.0.11) `settingSources: []` switches discovery off. Install+enable is itself the consent for a plugin's claude-native content, skills included — no consent class gates them. `skills.list` reports per skill whether a session can load it (`loadsInSessions`/`sessionNote`), its plugin half built from the installed+enabled set (`plugins/plugin-skills.ts`).

**Connector permissions (WS-26).** Every action of a user-configured MCP server — a **connector action**, `mcp__<server>__<tool>` from the user/local/project scope or an enabled plugin's own `.mcp.json` (the runtime keys a plugin's servers by their raw names, so they are indistinguishable on the wire), never `mcp__winter__*` (the capability tools, `external` included — how Winter's `plugin__*` extras reach a child) and never a built-in (`isConnectorToolName`, `agent/mcp/connector-permissions.ts`) — carries one user setting, Always allow / Always ask / Always deny, valid in **every** mode. The store is Winter's own, `settings.json` → `mcp.toolPermissions: {server: {tool | "*": allow|ask|deny}}` (a tool's own value beats its server's `*`; nothing stored is "default"), read live per decision; `mcp.setToolPermission` also hands the daemon the written table at once (`onConnectorPermissionsSaved`) so a flip does not wait on the watcher's debounce. Claude-grammar rules in `sdk/settings.json` could not be the store: the router snapshots them into each run folder at incarnation and the runtime evaluates a deny rule before anything a hook says, so a stored deny flipped to allow would keep denying in a live session. Those rules still bind natively (a deny in every mode, an allow/ask in code only — the router strips both from chat/dispatch) and `mcp.tools` reports them beside the setting. The matrix (`connectorVerdict`): **deny** → deny under every policy, `bypass` included; **allow** → allow, but under `plan` only a read-only action; **ask** → a card in code (even under `bypass` or over a saved allow rule), chat and dispatch, a deny under `dont-ask`, and under `plan` a card only for a read-only action; **unset** → an action its server marks `readOnlyHint: true` runs unasked in every mode (plan and dont-ask too), anything else cards in chat/dispatch and keeps the gate's per-policy verdict in code. A server name may itself contain `__` (`cf__prod`), so `mcp__cf__prod__x` is weighed at EVERY split (`connectorCandidates`/`connectorFactsFor`, the one resolver the hook, the bridge and `mcp.tools` share): the strictest stored value wins (deny > ask > default > allow); a split whose server is configured for the session (local/project/user scope, or shipped by any installed plugin — `pluginMcpServerNames`) but has not listed the tool votes the default and forbids read-only (the runtime gives a clashing name to whichever server registers first); an unconfirmed server's blanket `*` allow never allows; and read-only counts only from a listing that names the tool. `mcp.tools` names the server a value was borrowed from (`from`). Read-only comes from `McpManager`'s own probe (each tool's annotations, kept stale-tolerant), from the listing of the scope the name resolves to for the session (`agent/mcp/connector-source.ts`: local > project > user — a local-scope server is never probed, a project's own server answers only from that project's listing); a miss fails toward ask and never blocks a turn, and the only background probe a call may start is an unprobed http/sse USER server's — never a stdio or project server, which would spawn a process. Stored values are keyed by server NAME across scopes (a project's `cf` takes the user `cf`'s settings, like `mcp.disabled`), and a subagent definition's inline server the runtime renames on collision (`cf_2`) takes `cf_2`'s values, ordinarily the default — the daemon cannot see that mapping; a subagent's inline server is likewise invisible to the configured-split rule (it counts in an ambiguous `__` split only once stored). **Enforcement is two-sided**: the PreToolUse **connector-permission floor** (`hooks.ts`, every mode, fail-closed) answers the verdict to the child directly — the only layer that sees a call the child decides natively (a `bypass` child, a saved allow rule, `dont-ask`, which denies an unresolved MCP call without calling `canUseTool`), and the only one that ALLOWS — while the approval bridge applies only the verdict's deny and ask: a call that reached `canUseTool` despite the floor's allow was sent there by something else (an `sdk/settings.json` ask rule, a plugin's ask, `requiresUserInteraction`), and a connector allow must not answer that prompt. **This reverses "chat never asks" for connector actions and only those**: `gate.ts`'s chat branch answers `ask` for one, and the bridge cards it in a chat or dispatch session (the ordinary `approval_requested`/`approval.respond`, rendered in both Mac windows and, for the daemon's chat mirrored to the phone, there too — a phone-originated WinterChatKit chat never reaches this bridge; plain Allow/Deny, no rule option); a dispatch **child** keeps the never-prompt deny. Chat still never cards anything else. Doors: `mcp.tools` (reads the same live facts enforcement does), `mcp.setToolPermission` (local role only), the Library MCP tab's server page, and `winter mcp permissions <server> [<tool>] [allow|ask|deny|default]` — a server-wide value clears the per-action ones on both the page and the CLI. The settings schema keeps the block loose down to the row: an unrecognised value reads as ask, a non-object row as all-actions ask.

A session's configured MCP servers (the daemon's own `winter__<key>` ones plus any user/project-scoped external server) connect after the child spawns, not before, so the FIRST turn can carry a user-visible wait of up to 2 s while they come up — claude parity by design, not a Winter regression, and not present on later turns once the servers are already connected.

**MCP sign-ins (OAuth, WS-25).** An http/sse server may carry an `oauth` block (`clientId`, a `clientSecretRef` MARKER, `callbackPort`, `authServerMetadataUrl`, `scopes`) on every config surface — settings, `sdk/.winter.json`, a trusted project's `.winter/mcp.json`, `mcp.add`/`mcp.get` — and each is validated with the runtime's `validateMcpOAuthConfig(oauth, url)` before anything is written. The SDK (`@yanlinglabs/winter-agent-runtime/mcp-auth`) owns the protocol: discovery, registration (pre-registered > CIMD > DCR; Winter's CIMD document is `https://yanlinglabs.com/winter/oauth-client.json`, `WINTER_MCP_CLIENT_METADATA_URL`), PKCE, the loopback listener, `state`, the issuer checks and the SSRF fetch policy. That policy (the runtime's `mcp-auth/fetch-policy.ts`) is HTTPS-only (loopback only when the MCP server itself is on loopback), follows no cross-origin redirect, caps time and size, and refuses a LITERAL private, link-local, unique-local, CGNAT, multicast or unspecified address. It never resolves DNS, so a name that resolves to a private address IS fetched — its response is only ever parsed as discovery metadata or a token answer, never returned to a caller or the model. Every auth request — a sign-in, the daemon's refreshes, a revocation — goes through it. A sign-in is keyed by the server's CANONICAL URL, so one sign-in serves every scope and project naming that server, in three Keychain items: `mcp-oauth:<id>` (the token record — the one a session may be answered for, through `toSessionMcpTokenRecord`, refresh token masked), `mcp-oauth-client:<id>` and `mcp-oauth-client-secret:<id>` (daemon-only, never brokered; the secret's account is DERIVED from the URL and can never be named by a config). All of them go through ONE store instance per Keychain service (`runtime-sdk/mcp-oauth-store.ts`'s `daemonMcpOAuthStore`), because `refreshMcpOAuthToken`'s single-flight is keyed on the store object — the sign-in doors, the `mcp.list` probe, `credential_resolve` and a session's `mcp_oauth_refresh` share it (a daemon handed its own `secrets` — every test daemon, the Swift `RealDaemon` fixture — gets a per-daemon memory store instead, never a Keychain one). The doors (`agent/mcp/oauth-doors.ts`; LOCAL role only, never in `REMOTE_ALLOWED_METHODS` — the phone signs in on the Mac) are `mcp.login` (→ `authUrl` for the client to open; the flow lives in the daemon for 5 minutes), `mcp.loginStatus`, `mcp.logout` (best-effort RFC 7009 revoke; the client registration is kept unless `forgetClient`), `mcp.clientSecretIssuer` and `mcp.setClientSecret`; on the terminal `winter mcp login|logout [--forget-client]|set-secret <name>` and an auth column in `winter mcp list` — `login` prints the resolved scope, URL and issuer and asks before opening the browser, and for a shell with no terminal (an agent's `!`) `login --yes` skips only that question (an issuer change still needs `--confirm-issuer-change`) while `set-secret --from-clipboard` first prints the issuer, then with `--issuer <it>` reads the secret via a spawned `pbpaste` (never an argument, env or pipe) and clears the clipboard after a successful store. **A client secret is bound to an issuer**: it is written only with the issuer the USER-scope server's own discovery names (never a project's `authServerMetadataUrl`), shown to the user and confirmed (`expectedIssuer`; `mcp_expected_issuer_required`/`mcp_issuer_changed` otherwise), and the SDK sends it to no other authorization server. A sign-in whose discovered issuer is not the stored registration's refuses `mcp_issuer_change_requires_confirmation` (both FULL issuers in `data`, compared with `sameIssuer`) until the caller repeats it with `confirmIssuerChange`. Startup is Claude-Code-like without its bug: a still-valid token is used as is (never refreshed at connect), an expired one is refreshed by the daemon only when a refresh token exists, and otherwise the server is `needs-auth` — its tools are not exposed, the model gets no authenticate tool, and the SDK itself announces it with a persisted `mcp_needs_auth` attachment (the daemon adds no system-context line). `mcp.list` rows report `status: "needs-auth"`, `auth` (`none`/`signed-in`/`needs-auth`), `oauthIssuerOrigin` and `oauthPreregistered`. After a sign-in or sign-out, **a Keychain write never evicts or restarts a child**: every live session naming that URL (`WinterSession.mcpServerNamesFor`) reconnects the server by its own name (`reconnectMcpServer`, the runtime's `mcp_reconnect`; mid-turn children at their idle boundary, `agent/mcp/reconnect.ts`), and the tools appear in the session already open.

The bash safety reviewer is the one internal job that **never switches itself off over a pin mistake** (user ruling): when `reviewer.model`'s explicit pin is unrunnable (`provider-unsupported`, or `no-credential` for the pinned provider) it falls back to the default rule's answer and **runs** on that, while the role's `problem` still reports the pin's own issue with a `— reviewing on <tag> meanwhile` clause. `resolve` enforces that on the role, so the other three keep "a refused pin is inert with a note" (spending on a provider the user did not choose for titles/dreams/cleanup is worse than not running). Only when the default rule has **no** answer either (`no-internal-credential`/`no-default-model`) does the hook **allow** an ordinary sandboxed call (never an escape — see above) — byte-identical to what such a home got before the reviewer could exist there at all (a home with no runnable credential at all is exactly this case, and the Mac creates code sessions on `auto`); one log line per change of state. A **transient** failure on a home that does have a runnable provider still escalates with `ask`. A call the gate cannot allow outright raises an approval card in Code mode through `canUseTool` (`runtime-sdk/approval-bridge.ts`) and is a typed deny in dispatch/chat — except a connector action, which cards there too (above); session policies are `plan | dont-ask | ask | accept-edits | auto | bypass`, plus chat's immutable `chat`. Memory is file-based (a MEMDIR of markdown written with ordinary write/edit — no dedicated memory tools). Subagents have no wall-clock timeout; a progress-stall watchdog replaces it.

## Versioning & release

`VERSION` is canonical and is never edited by hand. The format is `#.###.#` — major, a three-digit feature counter, a single-digit patch (e.g. `0.112.0`); the first digit moves only for a rebrand-scale event.

```sh
bun run version:bump                 # patch +1 (throws past 9 — use a feature bump)
bun run version:bump:feature         # feature +1, patch -> 0 (also version:bump:major)
bun run version:sync                 # restamp version.ts / package.jsons / plists from VERSION

bun run scripts/release.ts --dry-run --no-bump   # full rehearsal: builds, notarizes, staples, never publishes
bun run scripts/release.ts                       # real release (bumps the version first)
```

`releases/notes/<version>.md` is **required** for the version being released — it is both the GitHub
release body and the Sparkle appcast `<description>` (rendered to HTML by `releaseNotesHtml`, which
throws on any markdown construct outside `#`/`##`/`###`, paragraphs, `- ` bullets with two-space
continuations, ``` fences, `` `code` `` and `**bold**`). The preflight fails before the bump when it
is absent, so the flow is: write and commit the notes for the next version, bump and sync, then
release with `--no-bump`.

## Hard rules

- **Never kill, restart, launch or write to a running Winter.app or the user's live daemon.** The daily driver is `Winter.app` (`com.winter.app`) in `/Applications` on `~/.winter` with Keychain `com.winter.core`. A local Release build (`out/release/<version>/…/Winter.app`) carries the same bundle id and Launch Services can resolve `com.winter.app` to it at relaunch: build Release copies, never launch one, and never delete an `out/release/<version>` tree while a Winter process runs from it. The legacy `Norma.app` / `~/.norma` / `com.norma.core` items stay untouched as the rollback source.
- **Dev work uses only the dev app** — "Winter Dev" (`com.winter.app.dev`, `~/.winter-dev`, a Debug build with an explicit `-derivedDataPath`). A Claude-launched dist instance is indistinguishable from the user's own in the menu bar and defeats the entire dev/dist split.
- **Tests never touch `~/.winter*`, `~/.claude*`, or the real Keychain.** Always point at a temp `WINTER_HOME`; every test daemon resolves credentials against a throwaway Keychain service (`packages/core/test/preload.ts` sets `WINTER_KEYCHAIN_SERVICE`), never `com.winter.core` / `com.winter.core.dev`, which hold the user's real items.
- Secrets live in the macOS Keychain (`Bun.secrets`, service `com.winter.core`) — never on disk, never in fixtures, never in a log line or an error message.
- `packages/core/src/providers/codex-config.ts` self-identifies as `originator: "winter"` — a deliberate ToS decision; do not revert it to a first-party value.
- Version strings are generated; edit only `VERSION`, through the bump/sync scripts.
- The Sparkle public key in `apple/Winter/project.yml` (`SUPublicEDKey`) is the production key; the private half exists only in the login Keychain — never committed anywhere.
