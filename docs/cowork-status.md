# Cowork implementation map

As of 2026-10-25 (first written 2026-10-15), Winter cannot create or run a supported Cowork session. Code, Chat, and Dispatch are the implemented daemon modes. `SessionModeSchema` ([events.ts](../packages/protocol/src/events.ts)) now has four values, `code`, `dispatch`, `cowork` and `chat`: Cowork exists as a recognised wire and stored mode that the daemon REFUSES everywhere (`session.create` answers `unsupported_topology`, a stored cowork row never runs), and the runtime SDK's `RunMode` still excludes it. Cowork has host-side workspace infrastructure, Mac screens for workspaces, shared guidance and schedules ([later status](#later-status-2026-10-15)), visible UI placeholders for the composer and Dispatch `/spawn`, reserved names, and reusable infrastructure. A reserved predicate or a passing synthetic test does not make it a working product mode.


The 2026-10-12 accepted native-host policy preserves ordinary Code/tool execution without a persistent outer floor or first-activation restart debt. Core file checks and the existing single Bash sandbox protect registered paths; approved escapes keep their normal approval behavior with static write-shaped Cowork integrity checks. Activation refreshes Code incarnations/run homes while preserving queued messages and logical identity, and uses acknowledged live updates for Chat/Dispatch with the independently accepted SDK v1 nine-family context contract, preserving ongoing turns. Protected cold startup waits for its matching Worker acknowledgment. The installed SDK pin remains unchanged and lacks the contract; that version still requires existing embedded Workers to close and refuses protected Chat/Dispatch. Explicit owned-worker/bridge floors and host credential protection remain requirements; separate per-workspace encryption is deferred for the first version. Private images are plaintext, protected offline by FileVault only when enabled, and readable by same-user processes or approved escaped commands, which run as the user; these changes do not pass the production Cowork gate.

This map covers the Winter host and its sibling agent SDK, runtime SDK, and iOS repositories. It describes source behavior; the unavailable Cowork mode has no end-to-end execution to validate. Outstanding work is tracked in [Follow-ups](../follow_up.md#cowork).

The 2026-10-11 [workspace metadata API slice](cowork-workspace-api.md) adds canonical host RPC reads/mutations and isolated daemon fixture coverage. Production Cowork creation/execution and client availability remain blocked; the historical infrastructure map below is retained.

The [implementation ledger](cowork-implementation.md) tracks subsequent native VM, RAM return, protected-store, key-broker, host-output and CLI work, including their remaining gates. The tables below describe the original source audit, not the latest implementation branch inventory. Two rows whose text became false are corrected in place and marked *(updated ...)*.

## What still blocks a functional mode

1. **Session identity and creation.** The [create schema](../packages/protocol/src/methods.ts) and [session event schema](../packages/protocol/src/events.ts) now RECOGNISE `cowork` (`SESSION_MODES`, the session-door slice), but nothing can create or run one: `session.create` refuses it for every role with `unsupported_topology` before any row, run folder or child exists, the [store](../packages/core/src/sessions/store.ts) will not mint it, and the [daemon runtime type](../packages/core/src/runtime-sdk/create.ts) holds only Code, Dispatch, and Chat (pinned to the protocol list by [`session-mode.ts`](../packages/core/src/sessions/session-mode.ts)). A stored cowork row is refused by the driver table, the model-switch door and the computer-use and lease readers rather than read as Code. Dispatch separately refuses its reserved Cowork argument. The workspace binding, remote eligibility and an actual creation transaction are still open.
2. **Runtime and capabilities.** The [tool registry](../packages/core/src/agent/tools/registry.ts), [capability table](../packages/core/src/runtime-sdk/mode-options.ts), and runtime SDK have no Cowork mode. Its prompts, tools, permissions, and execution topology still need an explicit product contract.
3. **Connected surfaces.** The Mac composer controls and `/spawn` callback are placeholders. iOS also remains a placeholder, and the remote gate excludes a Cowork-shaped row. UI availability flags alone cannot close these gaps.
4. **Real execution coverage.** Tests for reserved predicates, injected database rows, and callback closures establish those helpers' behavior only. A functional mode needs tests through supported create, send, tools, resume, and its chosen client surfaces.

## Reading existing references correctly

- **Supported product modes and permission modes are different axes.** The SDK's older reference adapters expose permission-mode values where future product-mode metadata was anticipated. The current host messaging contract has a separate host-supplied product-mode string; neither implements Cowork.
- **There is no supported Cowork fallback.** The old `engine.ts` is gone. Current [session-driver](../packages/core/src/runtime-sdk/session-driver.ts) and [handoff](../packages/core/src/runtime-sdk/handoff.ts) helpers used to map every raw mode but chat/dispatch to Code; their `modeOf` now maps only an absent mode to Code and REFUSES a stored `cowork` — or any other string that is not a runnable mode — with `unsupported_topology`, and supported creation rejects Cowork. Old comments predicting a Chat fallback are obsolete; a Code fallback is not a way to enable Cowork.
- **Tool deferral is not roadmap deferral.** `deferred` in tool registration means schema loading through ToolSearch. It does not indicate that the tool or Cowork is waiting to be implemented.
- **References to an external product's Cowork are comparisons.** Mentions of that product in comparison notes or old vendor metadata do not describe a shipped Winter feature. Dated research and release notes remain historical records.
