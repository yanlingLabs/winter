# The Winter island

*Read this before touching `apple/Winter/Sources/Island/`, `packages/core/src/island/`, the hello's `capabilities`/`tty`, `island.pending`, or where an approval, question or desktop-switch prompt shows on the Mac.*

A Dynamic-Island-style surface at the Mac's camera housing, in Winter.app. Phase 1 (this): the slim strip, the cards born from the housing, the open island with its tab mechanism and ONE tab, **Needs you**.

## Two forms

- **Cards on top** — quick, ephemeral, born from the housing with the desktop-switch pill's liquid (`DesktopIslandFluid`, `WinterCUPresentation`, made public for this): approvals, questions and URL link requests as **rounded rectangles** (`IslandRectShell` → `CUIslandLiquidFrame` with `DesktopIslandGeometry.bodyCornerRadius`), view requests (the desktop switch, and future ones) as **pills** (the package's own `DesktopIslandView`, same look and words).
- **The island** — the permanent surface. A **slim strip** extending the housing, STATIC. It never covers a menu-bar click it does not need (`IslandLayout.strip(_:waiting:)`): while NOTHING waits it is exactly the housing (black on black, nothing drawn; a click there — where no menu item can be — still opens the island), and on a screen without a housing there is no strip at all (an empty island has nothing to show; this blocks no menu click, which a minimal top-edge target could). While something waits it grows its wings (the housing's width plus 46 pt each side, its height) with the amber "waiting for you" icon on the left and the count of every pending card on the right — or, without a housing, a 112 pt tab hanging from the top centre at the menu bar's height. Only then do the wings or the tab take clicks. A **click** on it opens the island (a black rounded shape growing out of the housing, 520 pt wide, ≤ 560 tall); a click outside (global + local mouse-down monitors) or **Esc** closes it (the panel's own key handler when it is key; a global key-down monitor otherwise, which macOS delivers only to an app trusted for Accessibility). A click on the island's top band closes it too.
- **Tabs**: `IslandTabRegistry.tabs` in swipe order — Phase 1 registers only `needsYou`; phase 2 adds Sessions, Usage and limits, Devices, Shelf, Watches by naming them there and giving `IslandExpandedView.tabBody` a body. A **two-finger horizontal swipe** while the pointer is over the open island changes tab (`TrackpadHorizontalSwipeRecognizer`, the Dispatch pill's; fingers left = next, no wrap); small dots show where you are (drawn only with more than one tab).
- **Needs you** lists every pending card, newest first, each answerable there: approvals, questions and links with the transcript's own `TranscriptInteractionCard` (rule options, multi-question decks and notes included), view requests with ✕ / ✓.

## Routing (`IslandRouter`, pure; `IslandRoutingTests`)

1. **Dispatch, or a Dispatch-spawned child** (mode `dispatch`, origin `dispatch-child`, a coordinator among the known Dispatch sessions, or a card mirrored onto one): through the Dispatch pill while it is visible (its floating cards, as before); on top while it is not. The pill's visibility change re-routes.
2. **Any other session**: HIDDEN on top while that session's host is in front; on top otherwise.
   - Winter.app: the app window or a detached window showing the session is key or main AND Winter is frontmost (`AppWindowController.isKeyOrMain`, `DetachedWindowController.isKeyOrMain`).
   - A terminal (the CLI/TUI): only its EXACT terminal window/tab, through its tty (below). No exact match → shown. A phone host (role `remote`) never hides anything.
3. **View requests** (`prompt.desktopVisit`'s card): ALWAYS on top.

Every pending card is in Needs you and the strip's count whatever its placement. Re-routing is event-driven: an app activation, a Winter window becoming key/main, the app (de)activating, the pill showing/hiding, and — only while a card is hidden behind a terminal — an `AXObserver` on that terminal app's focused-window/title changes (`TerminalFocusWatcher`; nothing installed otherwise).

## The terminal match (`TerminalWindowMatcher`, `TerminalWindowMatcherTests`)

- The CLI sends its controlling terminal in its hello (`HelloParams.tty`, `packages/cli/src/tty-name.ts`: the device number of the first terminal among stdin/stdout/stderr matched against `/dev/ttys<minor>`, else a `/dev` scan; no process spawned). The daemon keeps it on the connection's `HubClient` and lists it in `island.pending`'s `hosts`.
- The app reads the process table (`sysctl KERN_PROC_ALL`: pid, parent, `e_tdev` → `devname`, `p_comm`) and, only with Accessibility trust, the frontmost app's focused window title and selected tab title (`AXTabGroup`'s selected tab; 0.1 s messaging timeout, read-only, nothing set) — off the main thread, only when a card's routing needs it.
- The window is read only when a target tty belongs to the front app's process tree — otherwise the answer is "not in front" with no accessibility call at all (which would also switch on a Chromium app's AX tree). Re-judgings are one serial pump in `IslandStore` (fetches and reroutes coalesced; a judgement read while a newer ask came in is read again, never applied — `generation`).
- POSITIVE evidence only: the tty must be on a process descending from the frontmost app (else not in front); the app must have a focused window on this Space (AX, or the window server's on-screen list without trust — minimised, another Space or none → `unknown`); then (1) a title naming a tty names exactly one; (2) in a DEDICATED terminal app (`dedicatedTerminals`: Terminal, iTerm2, Ghostty, kitty, WezTerm, Alacritty, Warp, Hyper, Rio, Tabby) one terminal = that one; (3) there, the title's PROCESS segment (`processSegment`: the one before the size in Terminal.app's "folder — winter — 80×24", or a whole unsegmented title; never the folder) naming the program running in exactly one of its terminals. Anything else is `unknown` → the card shows.
- **Limits**: Terminal.app/iTerm2 titles carry no tty by default, so with several tabs at a shell prompt the answer is `unknown`; iTerm2's sessions are children of its server daemon, not of the app (`unknown`/`notFront` → shown); tmux/ssh: the CLI's pty belongs to a server (shown); an editor's integrated terminal needs the tty in a title; no Accessibility trust → only the process-tree and single-terminal rules.

## Queue (`IslandQueue`, pure; `IslandQueueTests`, `IslandStoreTests`)

- Cards do not stack: a new card REPLACES the current one, which compacts.
- The card being TYPED INTO (its panel took the keyboard for a click in its text field) is held exactly like a hovered one — never replaced, never compacted, never hidden by a re-route — so no keystroke can land in the app behind. The keyboard goes back (`IslandPanel.rest()`, restoring the app the user was in) only when that card is answered (here or anywhere), on an explicit dismiss (a click on the waiting pill) or on Esc; a click in another window simply lets go.
- While the current card is HOVERED or typed into (or is a view request counting down), the newcomer waits as a small compact pill just below it (`IslandWaitingPill`); it expands when the current one clears or self-compacts, or when the user CLICKS it — which tucks the current one away (compacted). A waiting view request is never displaced by an approval.
- **Self-compaction**: approvals, questions and links stay expanded `IslandQueue.selfCompactAfter` (6 s); unhovered they compact into BOTH the badge hanging from the housing ("2 waiting", `IslandBadge`, shown while no card is expanded; hovering it re-expands the newest) AND the Needs-you list. A pointer leaving a card past its time gives it `hoverLeaveGrace` (1.5 s). They stay pending until answered anywhere.
- View requests never self-compact: their deadline (the card's `expiresAt`, default-allow) is the answer.
- A card hidden behind its host leaves the top; when it comes back it goes straight to the badge if it was on top before (no second pop). A card answered from the island goes back up into the housing; one answered elsewhere just goes.

## The desktop switch moved into the island

- The app's hello advertises `CLIENT_CAPABILITY_ISLAND` (`"island"`, `packages/protocol/src/methods.ts`) on its MAIN feed connection (`AppModel.clientCapabilities` → `WinterClient.setClientCapabilities`, re-sent on EVERY reconnect).
- While any island client is connected, `islandAwareDesktopPanel` (`packages/core/src/computer-use/wiring.ts`) does not ask the helper for `prompt.desktopVisit`; the island shows the session's own card (`approval_requested` with `toolName: "ComputerV2"`, `onTimeout: "allow"` and the `switch` option — told apart by that shape, never by its words; `DesktopVisitCardWords` reads the app, bundle id and reason back out of the daemon's sentence only to fill the line). ✓ = `approval.respond {approved: true, optionId: "switch"}`, ✕ = `approved: false`. The first answer wins in the broker across the transcript card, the Dispatch pill, the island and the helper.
- The helper's panel stays the FALLBACK, with the card's own deadline and its answer chained: at a prompt with no island client; when the last island client LEAVES before an answer (a quit or crash mid-prompt — `IslandRegistry.onAllClientsGone`); and when no island client says it shows the card within `ISLAND_SHOWN_ACK_MS` (2 s) — the app sends `island.shown {ids}` for the view requests it puts on top after each `island.pending`, so a Winter.app that is connected but HUNG still gets the prompt on screen (then possibly both show; the first answer wins). `close()` closes whichever is up. `packages/core/test/island/registry.test.ts` pins every leg.

## Daemon (`packages/core/src/island/registry.ts`)

- `IslandRegistry` observes every appended event (`hub.addObserver`): `approval_requested`/`question_asked`/`elicitation_requested` add a card (payload = the event), their resolutions remove it; a Dispatch MIRROR (`childSessionId`) folds into the child's own card (answered at the child); `harness_attached`/`_detached` on a session with a card re-notify. Pending-ness is the BROKERS' (`ApprovalBroker.pendingMeta`, `QuestionBroker.isPending`, `ElicitationBroker.urlFor`): a card the broker no longer holds is pruned at the next list. ≤ 256 held.
- Cowork's shared-guidance approval (`CoworkInstructions.updateAgent`, `cowork/instructions.ts`) goes through the same `approvalBroker`, so it is a card too: `toolName: "workspace.instructions.update"`, its `summary` carrying the whole proposed guidance (up to `COWORK_INSTRUCTION_MAX_BYTES`), each wait 60 s. An untitled Cowork session's card says "Workspace" (`IslandCard.sessionLabel`, pinned in `IslandStoreTests`).
- `island.shown {ids}` (harness only): the client shows these cards — the desktop-switch prompt's ack (above).
- `island.pending` (harness role only — not in `REMOTE_ALLOWED_METHODS`, not for plugins) → `{items: [{sessionId, answerSessionId, kind, event, session: {mode, origin, parentSessionId, title}, hosts: [{clientName, role, tty}]}]}`. An island client is told `island.changed` (a bare JSON-RPC notification, params `{}`) once per burst (one microtask); the app then asks again. No `SessionEvent` changed: no fixture, no Swift mirror, no remote allowlist.
- Swift side: `WinterKit/WinterClient+Island.swift` (`islandPending()`, `capabilityIsland`, `islandChangedNotification`), `IslandClientTests`.

## The app (`apple/Winter/Sources/Island/`)

- `IslandStore` (state, routing applied to the queue, answers through the app's client to the card's ANSWER session — the island never attaches to a session), `IslandController` (panels, pointer, open/close, the one wake-up), `IslandViews`, `IslandLayout`, `IslandPanel` (non-activating, `.statusBar` level, every Space, `sharingType .none`, never key EXCEPT when a click lands in a text field — a question's "Other" — which makes it key for that very click; `rest()` gives it back), `IslandGallery` (offscreen renders). Wired in `AppDelegate.startIsland` (never under unit tests, never without a token).
- Look: the black shell, hairline rim, shadow and morph blur of the Dispatch pill (`CUIslandLiquidFrame`), its type (`Typography.body(.light)`, 14 pt), the white ✕ / blue ✓ circles with `pillHoverGlow`, the 3 % hover grow. Pointer through mouse-move monitors (global + local) installed only while a card, the badge or the open island is on screen; outside what is drawn the top panel ignores the mouse.
- **Screen**: the screen with a camera housing, else the main screen (`IslandLayout.islandScreen`) — a fixed place, re-read when displays change (the helper's own desktop-switch pill uses the pointer's screen instead).
- **Idle**: the strip is a static view; no timer or display link runs. Display-rate frames only while a shape moves (`TimelineView(.animation)` until `DesktopIslandFluid.settle`); the queue's self-compaction is ONE `DispatchWorkItem` while a card is expanded; no ticker for a view request (its expiry arrives as `island.changed`).
- Esc's global key-down monitor exists only while the island is open (removed on close). The view-request pill's VoiceOver label carries no seconds (nothing keeps them current here): "… Winter switches by itself if you don't answer."
- Offscreen renders: `IslandGalleryTests` with `TEST_RUNNER_WINTER_ISLAND_RENDER_DIR=<dir>`; `ImageRenderer` draws AppKit-backed controls (a text field) blank.

## Not in Phase 1

The other tabs (Sessions, Usage and limits, Devices, Shelf, Watches); plan cards (`plan_presented`) on the island; any per-card "open in Winter" jump. The live look is checked with the user on a real screen.
