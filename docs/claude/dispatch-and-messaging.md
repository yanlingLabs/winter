# Dispatch and messaging

*Read this before touching mid-turn pushes, turn pairing, Dispatch's children, SendMessage/ListAgents/TaskStop, or ListSessions.*

## The fold: a push made while a turn runs joins it

A steer (`session.steer`), a messaging delivery or a SendMessage to a running session is pushed into the child at once; the child folds every pending push into the running turn before its NEXT request (after the next tool round) and says so with `system/host_input_folded` (`count` = its N earliest pending pushes). A folded push gets no `result`; a push still pending when the turn ends (an interrupt, budget or hook stop included) is its own next turn with its own `result`. `UserPromptSubmit` runs per folded prompt; a block, `/compact` or a resolver-expanded `/name` ends the fold there.

- Members live in ONE file, `packages/core/src/runtime-sdk/fold.ts` (`FOLD_SINCE` = 0.0.44, `runtimeFolds`, `hostInputFoldedCount`, `clearQueuedInput`).
- Projector (`projector/index.ts`'s `acceptFold`): shifts the folded pushes off its held queue, stops owing them a terminal and announces each one's held `turn_started` NOW; the driver drops them from `inFlight` (`winter-session.ts`'s `onFold`). So every pushed `user_message` has a `turn_started` and a resume never re-pushes a folded text. No projector dedupe for a fold. A daemon-held `send` is never pushed early — only what was pushed can fold.
- **Consumer rule: a main `turn_started` while a main turn is OPEN is a continuation, not a new turn.** "Open" is read off the LOG (a main `turn_started` since the last main `turn_completed`), never off the driver's idle settle. Consumers: the Mac reducer (`apple/Winter/Sources/Model/SessionModel.swift`), the TUI, `winter -p` and its watchdog (`packages/cli/src/watchdog.ts`), the headless elicitation gate, `elicitationTurnTracker`, `DispatchChildren.mainTurnOpen`, and `TurnOriginPairer`/`runningTurnOrigin` (`sessions/turn-origins.ts`), which pair a continuation by ADJACENCY — the nearest preceding unpaired message — so the running turn's origin becomes the folded message's.
- A CONFIGURED code runtime is whatever binary is there, so each spawn hook reports its version (`WinterSpawnHook.runtimeVersion`: the pin for locked rungs, else `executable.ts`'s `winterBinaryVersion`); `WinterSession.foldsQueuedInput` is true only for a runtime KNOWN ≥ 0.0.44 (unknown = not folding: SendMessage queues rather than steers). An older runtime never sends the fold frame, and its `unknown_subtype` answer to `clear_queued_input` is caught (nothing cleared).
- A resume racing an eviction waits for the evicted driver to end (`WinterSessionDeps.predecessorDone`, bounded by the end budget) before `open()` reads the log ONCE (`logFacts`), so the dead-turn close never lands beside the old child's own terminal. Per-call tool results: [runtime-and-sessions](./runtime-and-sessions.md).

## Dispatch's children (`SpawnSession`)

The `sessions` server's `session_spawn` runs `packages/core/src/agent/dispatch-children.ts`'s `DispatchChildren.spawn`.

- Pre-flight refusals are tool errors, nothing created: not a dispatch caller, `cowork`, dir not an existing absolute directory or `/` (canonicalised first), empty prompt, a model outside the LIVE `pickerModels` list (the schema enum is a boot snapshot), shutting down.
- Minted through `session.create`'s own transaction (`ipc/server.ts`'s `createSessionInternal`, published as `onSessionCreator`): CODE, `origin: "dispatch-child"`, `parentSessionId` = coordinator, the coordinator's CURRENT policy (`childPolicyFor`, FIXED for the child's life), model stamped at creation, NOT backgrounded. The prompt goes in through the driver's `send` (`clientName: "dispatch"`); the tool returns without waiting; an undeliverable first message rolls the child back. Spawns of one round run at once, every step per call; an interrupted coordinator turn cancels in-flight spawns via `ctx.signal` (before creation: nothing; before `send`: rolled back; after: the child keeps working).
- **T5 detach rule** (`sessions/activity-enforcement.ts`): a terminal-kind harness's last detach aborts only a turn a HUMAN started (`runningTurnOrigin` over the log); an origin in `AUTOMATED_TURN_ORIGINS` (`messaging`, `dispatch`, `dispatch-wake`) is never aborted.
- A hub observer follows only turns Dispatch started (the spawn's, and a follow-up it delivered — `expectFollowUp`, keyed on coordinator + exact text), writing `child_update`s onto the coordinator's log (`running | awaiting_approval | awaiting_input | completed | error`, last main-thread message as `resultSummary`). An interrupted turn reports `completed` naming who stopped it — every stop door calls `DispatchChildren.noteStop` first.
- **Card mirroring**: `approval_requested`/`question_asked` of EVERY child turn, whoever started it, are mirrored onto the coordinator's main thread with `childSessionId`, resolutions after them, answered at the child's id; an unfollowed turn's cards ride a relay-only entry (no status, no wake). The unattended notification is skipped when the coordinator or the asking child has a harness attached.
- A child's "ask" CARDS (`cardsRelayedToDispatch`, `runtime-sdk/approval-bridge.ts`); approvals and questions expire after `DISPATCH_CHILD_APPROVAL_TIMEOUT_MS` (10 min) — EXCEPT a card raised in a turn the USER typed into the child (`dispatchChildCardTimeoutMs`; a known non-automated origin is human, unknown stays bounded) and ComputerV2's desktop-switch card ([computer-use](./computer-use.md)). It stays the ONE card on the child's log; both doors answer one broker entry (first wins, second gets `alreadyResolved`). Dispatch's own calls never prompt, except its own `session_spawn`, a connector action's card ([mcp](./mcp.md)) and ComputerV2's per-app/foreground/desktop cards.
- **The wake**: a finished followed turn queues a `<child_update>`, flushed as ONE `send` while the coordinator is idle (resumed if resumable) or at its own settle — coalesced, retried 3 times (`WAKE_RETRY_DELAYS_MS` 2/10/30 s). It is a `user_message` with `clientName: "dispatch-wake"` (`DISPATCH_WAKE_CLIENT_NAME`, `packages/protocol/src/events.ts`): the Mac, the TUI and the dreamer treat it as the daemon's, not the user's. A reported child is forgotten at the coordinator's next turn end; a wake unflushed at stop/crash is lost (the `child_update`s stay on the log).
- Boot: one read of the coordinator's log closes what a restart left open — unresolved mirrored cards (`by: "restart"`) and children still in flight (a closing `error`); only those are re-tracked at their next turn. `beginShutdown()` stops reports and wakes but keeps mirroring resolutions; `stop()` runs just before the store closes.

## SendMessage / ListAgents / TaskStop (`Options.hostMessaging`)

`SendMessage` is the ONE tool that messages AND resumes a session; `TaskStop` stops a session's turn by its `s_…` id. A child resolves `to`/`task_id` in-process first; only a miss reaches the daemon over the control channel (`host_message_send`/`host_message_list`/`host_session_stop`), answered by `packages/core/src/agent/session-messaging.ts`'s `SessionMessaging` — one handler per session, set in `session-driver.ts`'s `optionsFor` (the caller is the session whose handler fired, never a request field).

- Targets: Code sessions (`participatesInActivity` also reserves `cowork`). Refused typed: chat/dispatch targets, the caller itself, an archived session, an empty message. Senders: code and dispatch; chat has no trio ([tool-surface](./tool-surface.md)).
- **A message runs at the TARGET's policy with no card for the message itself — a session at `ask` can drive one at `bypass`. Deliberate (recorded in `gate.ts`).**
- Addressing `s_…` or `session:s_…`. Delivery through the target's own driver (`get ?? ensure`, so a FINISHED session is resumed) under `clientName: "messaging"`: a RUNNING target is STEERED → `delivered` (the steer's own `injected` decides); one whose driver already holds `pendingSends` gets `send` → `queued` BEHIND them (FIFO); idle/finished → `delivered`/`resumed_and_delivered`. Steering needs `WinterSession.foldsQueuedInput`, else `queued`. Otherwise `refused` / `not_found` / `unavailable`.
- One delivery per message: memoised on (caller, caller's runtime INCARNATION — a token per `optionsFor` build, since `msg-N` restarts per process/Worker —, message id, target, text digest) for `DELIVERY_DEDUPE_TTL_MS` (10 min); the abort `signal` and shutdown are re-checked after the resume and before `send`.
- Rendering: Dispatch to its OWN child sends plain text and is FOLLOWED (`expectFollowUp`); every other pair gets an attributed `<agent-message from="session:…">` turn (`runtime-sdk/messaging.ts`'s `renderAttributedTurn`), parsed for `clientName: "messaging"` only by `WinterSessionKit.AgentMessageEnvelope` (`apple/WinterKit`) into "From session …", never raw XML; the dreamer labels it another session's. `notify_when_idle` → a refused `notify` fact.
- **TaskStop**: `stopped` (`interrupt({ discardQueued: true })`), `not_running`, or refused/not_found; never resumes; CLEARS both queues behind the stopped turn — the child's pending pushes (`Query.clearQueuedInput`, BEFORE the interrupt, which would keep them; each gets its `turn_started` at once and `Projector.clearQueued` stops owing it) and the daemon-held sends. While the clear is in flight NOTHING pushes (`clearing`; deliveries deferred in order). A cleared push's `aborted` `turn_completed` lands only after the stopped turn's OWN terminal (at once if the child dies); a daemon-held send is closed with its own `turn_started` + `aborted` terminal, so a resume never re-runs either. `STOP_SETTLE_MAX_MS` (2 s, `winter-session.ts`) only RELEASES waiters: held sends leave the queue with their `turn_started`, their terminals wait for the turn's own — never an aborted terminal mid-turn. The Mac stop button (`session.interrupt`) keeps held messages for the next message.
- **ListAgents**: subagents plus RUNNING peers — `working` (`makeSessionSignalsDeriver`, `onSignalsDeriver`) OR `session.list` label `active` (`onActivityDeriver`) — capped at 50 (`LIST_AGENTS_SESSION_MAX`), the rest `omitted`; never padded with idle sessions.

## ListSessions and the edited-files index

`packages/core/src/agent/tools/list-sessions.ts`. Default: every ACTIVE and BACKGROUND Code session plus Dispatch-spawned ones (idle = `completed`, newest 4 only), capped at 50, overflow and hidden counts stated.

- `query` (≤ 500 chars): `sessions/session-query.ts`, deterministic lexical rules — no model call — across ALL Code sessions, archived included: DATE phrases (local time) must overlap the session's span; PATHS match EDITED files, cwd and title/first message; WORDS match title > first message > edited paths > cwd. The 10 best come back with why.
- **The index** is `session_files(session_id, path, last_ts)` in the store's `index.db` (`sessions/store.ts`): every appended `tool_result.fileDiff` is recorded live (never makes `append` throw); so is every file a **Bash** call wrote (`sessions/bash-edits.ts`): the command read statically with the escape floor's shell reader (`runtime-sdk/shell-words.ts`) under NARROWER, case-kept target rules (the verb list is the file's header; `rm`/`rmdir`/`unlink`/`shred` COUNT, reads never). Paths resolve against the cwd plus every `cd`/`pushd` EARLIER IN THE SAME COMMAND; recorded only when the `tool_result` has `isError: false`. Out of reach by design: anything built at run time, writes not named in the command, a `cd` from an EARLIER Bash call. `appendSynced` indexes too; `recoverAll` re-indexes every log in ONE transaction at open — the backfill (`edited_files_backfill` in `index_markers`) and the crash catch-up. A deleted session's rows go with it; a lost `index.db` rebuilds.

## MCP servers connect after spawn

MCP servers (the daemon's `winter__<key>` ones and user/project servers) connect after the child spawns, so the FIRST turn may wait up to ~2 s while they come up; later turns do not.
