# Architecture

*Read this before touching anything outside one package, and before starting any dev daemon or app.*

## Monorepo layout

- `packages/protocol` (`@yanlinglabs/winter-protocol`) — the contract: zod schemas for every JSON-RPC method (`src/methods.ts`) and `SessionEvent` variant (`src/events.ts`). `scripts/generate.ts` emits the JSON schema plus one canonical fixture per event variant and copies the fixtures into the Swift test bundle; it never reads `methods.ts`. See [protocol-and-remote](./protocol-and-remote.md).
- `packages/core` (`@yanlinglabs/winter-core`) — the daemon. `src/runtime-sdk/` (router handle `create.ts`, session driver table `session-driver.ts`, `Options` assembly `mode-options.ts`, `hooks.ts`, model-switch review `handoff.ts`), `projector/`, `capabilities/`, `agent/` (approvals, gate, memory, skills, sandbox, LSP; daemon-owned tools in `agent/tools/`), `sessions/`, `runtime-state/`, `providers/` (the daemon's own model calls; Codex OAuth), `plugins/`, `routines/`, `workflows/`, `panel/`, `migration/`, `settings*.ts`.
  - `src/workflows/` — model-authored JS run in a **sandboxed subprocess**: the daemon self-spawns its own binary as `__workflow-worker` under a macOS seatbelt (NDJSON stdio bridge). That worker and the runtime's `__runtime-workflow-worker --bridge` refuse (exit 77, before reading input) unless their sandbox denies the Keychain's mach services (`workflows/sandbox-guard.ts`, `sandbox_check` over bun:ffi, variadic name bound by hand on arm64) — so the bare binary cannot be made to run a script with `winter-core`'s rights. `bun run verify:workflow` is the compiled proof (round trip + both refusal legs); keep it green.
  - `src/computer-use/` — **ComputerV2**: the per-session sandboxed automation worker (`worker/`, `winter-core __automation-worker`, same seatbelt and exit-77 guard; proof `bun run verify:automation-worker`), the client of the signed "Winter Computer Use" helper (`helper-client.ts`, `protocol.ts`, `helper-verify.ts`), and the per-app policy, locks, diff base, screenshot budget, result builder and telemetry (`service.ts` ties them; `wiring.ts` builds it at boot). See [computer-use](./computer-use.md).
- `packages/cli` (`@yanlinglabs/winter-cli`) — the `winter` command: Ink TUI, headless `-p`, launchd daemon lifecycle, verbs `credentials` / `login` / `doctor` / `migrate` / `model` / `workflow` / …
- `packages/plugin-sdk` (`@yanlinglabs/winter-plugin-sdk`) — what plugins build against; plugins are separate processes with narrow, user-consented capabilities. `examples/battery-limiter` is the reference plugin.
- `apple/WinterProtocol` — Swift mirror of the protocol; its round-trip test decodes every generated fixture and asserts the exact count.
- `apple/WinterKit` — `WinterClient` (daemon client), `WinterSessionKit` (phone-facing), and the `Gateway` mediating the phone over Iroh.
- `apple/ComputerUse/` — **Winter Computer Use**, split-ready: own semver `VERSION`, wire contract in `PROTOCOL.md` (protocol number, every method/error/notification, the `view.*` stream, bump rules — keep in step with the code); nothing inside imports WinterKit/WinterProtocol (Winter.app depends on it, never the reverse). Clients check the protocol number at `hello` and refuse a mismatch typed ("too old/too new … update Winter").
  - `WinterComputerUse` — the signed LSUIElement helper with its OWN Accessibility/Screen Recording grants (`com.winter.computeruse[.dev]`; home from its bundle id, `WINTER_CU_HOME` only moves a dev build outside an app). `<WINTER_HOME>/run/computer-use.sock` (0600, NDJSON JSON-RPC, `hello` first); peer check BEFORE any read (`LOCAL_PEERTOKEN` → `SecCodeCopyGuestWithAttributes` → `SecCodeCheckValidity` against the daemon's requirement: dist `identifier "winter-core"`, dev `com.winter.core.dev`, + team OU); engine `WinterCUCore`, mirror/cursor/Esc `WinterCUPresentation`; 10-minute idle quit with no target, mirror or script. Launched only through LaunchServices, never spawned (TCC checks the parent). Release embeds it at `Winter.app/Contents/Helpers/Winter Computer Use.app` (`scripts/embed-computer-helper.sh`: hardened runtime, no entitlements, STATED requirement = identifier + team OU, so rebuilds keep grants); Debug embeds nothing — `bun run dev:helper` builds, signs and `lsregister`s it into `dist/dev/`; an Xcode Debug build gets `com.winter.computeruse.xcode-debug` and refuses to run. Test hooks compile only under `WINTER_CU_TEST_BUILD` (only `verify:computer-helper` passes it). The daemon side: [computer-use](./computer-use.md).
  - `WinterBrowserHost` — `winter-browser-host`, Winter for Chrome's native-messaging host, shipped at `Contents/MacOS/winter-browser-host` inside the helper (xcodegen tool target, `Tool/main.swift`). Imports only the system; its own `PROTOCOL.md`. Own identity `com.winter.browserhost[.dev]`, hardened runtime, no entitlements, stated requirement: every signing site signs it BEFORE the helper, never `--deep`.
- `extensions/winter-for-chrome` — the MV3 extension, own semver; `bun run build` → `dist/{dev,store,edge}/`; the dev id is fixed by `keys/dev.pub`; `store` → Chrome Web Store, `edge` → Edge Add-ons (the same build named "Winter for Edge", `src/manifest.ts`'s `PRODUCT_NAMES`, pinned by a build test). Nothing is ever uploaded from here. See [computer-use-browsers](./computer-use-browsers.md).
- `apple/WinterChatKit` — the phone's own chat engine.
- `apple/Winter` — the menu-bar app (xcodegen `project.yml`, no committed pbxproj). Release embeds `winter-core`, `WinterHelper`, and the `winter` runtime plus `ant` under `Contents/Resources/runtimes/` (`scripts/embed-runtimes.sh`). Its ONE Chromium (CEF + the five "Winter Helper" bundles) lives in the nested `Contents/Helpers/Winter Headless.app/Contents/Frameworks` (Debug: `Winter Headless Dev.app`) in every configuration; Winter.app's own CEF runs from there (`Sources/CEF/WinterChromium.swift`) and its own `Contents/Frameworks` holds none (release.ts checks). See [headless](./headless.md).
- `scripts/release.ts` + `scripts/release-lib.ts` — the release pipeline; `packaging/winter.rb.tmpl` is the Homebrew cask template. See [release](./release.md).
- The iOS app is a **separate repo** (`yanlingLabs/winter-ios`, checked out beside this one as `../norma-ios`). It consumes `WinterProtocol` + `WinterSessionKit` + `WinterChatKit` through its root `Package.swift` pinned to a git tag of this repo (`v-<name>-kitN`). A Swift edit here reaches the phone only after commit → push → new kit tag → the iOS project's `revision:` bump + `xcodegen generate`.

## Profiles and the dev daemon

- **Home and profile are independent; the home is profile-blind.** `resolveWinterHome()` (`packages/core/src/winter-dir.ts`) reads only `WINTER_HOME`, default `~/.winter` (the user's live daily driver). `WINTER_PROFILE=dev` changes only the Keychain service (`com.winter.core.dev`) and the app identity ("Winter Dev", `com.winter.app.dev`) — never the home. Always set BOTH: `WINTER_HOME=~/.winter-dev WINTER_PROFILE=dev`. The `~/.winter-dev` convention comes from the user's `winter-dev` wrapper, not core code. `isDefaultWinterHome(home, profile)` is the one predicate for "the profile's own default home". Dist = `~/.winter` + `com.winter.core` + `Winter.app` (`com.winter.app`).
- `profile.ts`'s `keychainService()` honours `WINTER_KEYCHAIN_SERVICE` only for a home that is NOT the profile's default — how tests stay off the real Keychain.
- **The dev daemon is the compiled `winter-core` signed by Winter's team, never Homebrew `bun`**: a Keychain item's partition list is its CREATOR's team (`auth/app-token-acl.ts`), so a `bun`-run daemon creates items Winter Dev is prompted for. `bun run dev:daemon` (`scripts/dev-daemon.ts`): `compile:core` → `dist/dev/winter-core` (never `dist/winter-core`, which `verify:*` rebuilds; built to a temp file and renamed, never over a running daemon); signed with the identity whose certificate OU is `WINTER_TEAM_ID` (Apple Development preferred; `WINTER_DEV_SIGN_IDENTITY` overrides) as `com.winter.core.dev` with a STATED requirement (`identifier "com.winter.core.dev" and anchor apple generic and certificate leaf[subject.OU] = "<team>"` — any Winter-team cert satisfies it, so rebuilds stay trusted), hardened runtime + `scripts/winter-core.entitlements`; checks the requirement and team, runs `__keychain-ffi-probe`, then `daemon run` on `~/.winter-dev`/`dev` with `WINTER_RUNTIME_EXECUTABLE`/`WINTER_ANT_EXECUTABLE` resolved under bun (a compiled binary cannot reach the npm package or `$PATH`). `--no-build` reuses the binary; other arguments run through it instead of `daemon run`; `--cli` runs exactly `dist/dev/winter-core <args>` (no args: the TUI) on the dev home/profile. Point `winter-dev` at `bun "<repo>/scripts/dev-daemon.ts" --no-build --cli "$@"`.
- **The Keychain transition is one-way and runs ONCE**: `bun run dev:daemon --transition` with Winter Dev quit and every dev daemon stopped (launchd ones too: `launchctl list | grep -i winter`). Under `bun` (the old creator) it reads each item and hands it over a pipe to `dist/dev/winter-core __dev-keychain-adopt`, which re-creates it as itself (shadow → delete → add → read back → drop shadow; `auth/dev-keychain-transition.ts`), under the credential migration lock (the child refuses unless its parent holds it) and the boot lock; it refuses while `core.lock` names a live pid, socket or not (a pid started after the lock was written is reused = stale). Bun's leftover shadows are adopted first; a child that exits or stops answering (30 s per request) stops the run with no marker. Crash-safe and idempotent: if interrupted, run it again. Between the transition and the signed daemon's first boot the pairing tokens are self-only (that boot re-widens them). Until it has run, `bun run dev:daemon` refuses to start the signed binary on `~/.winter-dev`; after it, EVERY dev-profile process must be that binary (a `bun`-run dev CLI or daemon is prompted for every item, the admin token first).
- **Two traps**: a plain `winter` is the DIST CLI and auto-launches the dist app on a dead socket — never use it for dev or test work. Debug app builds embed neither `winter-core` nor the runtimes, so "Winter Dev" cannot spawn its own daemon: start the dev daemon first or the orb shows disconnected.
