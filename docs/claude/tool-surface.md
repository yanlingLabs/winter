# Tool surface

*Read this before changing what a session's model can call: capability servers, plain names, deferral, allowed lists, web tools, hooks, write/read fences, sandbox escapes, saved allow rules, skills.*

## Capability servers (`packages/core/src/capabilities/`)

- Tool design tracks Claude Code's (`winter-vs-cc-tools.md`, repo root). The child brings file/shell/search/web tools; the daemon adds in-process MCP servers `winter__<key>` (`CAPABILITY_SERVER_KEYS`, `names.ts`): `sessions`, `computer` / `computer_v2` (exactly one built — [computer-use.md](./computer-use.md)), `browser`, `office`, `lsp`, `external`.
- `external` (plugin tools): a tool keeps its bare name unless another plugin registers the same one; then each is qualified `<tool>__<name>_<marketplace>`, or a digest form ≤ 64 chars (`externalToolNames`) — a saved rule on the bare name stops matching.
- `research`/`web` are retired but RESERVED (`RETIRED_CAPABILITY_SERVER_KEYS`): their old spellings still strip to host names on REPLAY (`packages/core/src/runtime-sdk/tool-names.ts`).
- Three fences hold every `winter__<key>` name, retired/unbuilt included: `mcp.add` refuses one (`agent/mcp/mcp-write.ts`); every incarnation states them as `Options.reservedMcpServerNames`, which the SDK enforces for every origin (`assertNoCapabilityCollision` covers non-run-home spawns only); on a LIVE call `mcp__winter__<key>__*` is the daemon's own only when THIS incarnation built `<key>` (`hostToolNameFor`'s `liveKeys`) — else an ordinary MCP name under connector permissions ([mcp.md](./mcp.md)). Only replay strips every key; `winter__foo` is a plain connector.

## Plain names, deferral, allowed lists (`runtime-sdk/mode-options.ts`)

- `WINTER_CAPABILITY_TOOLS` (`names.ts`, keyed by MCP spelling; `CapabilityToolFacts`) gives five tools ORDINARY names via `McpSdkServerConfig.toolNames` (`server.ts`): `SpawnSession`, `ListSessions` (dispatch), `Computer`/`ComputerV2` (code+dispatch), `Browser` (all). The plain name is the call's ONE identity downstream; the daemon still gets `sdk_mcp_call` under the server's tool name. The old `mcp__winter__<key>__<tool>` spelling stays an EQUIVALENT identity — a rule, `disallowedTools` entry or hook matcher on it binds, strictest-of, and the call is then evaluated UNDER that spelling — so every Winter reader accepts both; the pair table maps each plain name onto the host name its old spelling strips to (`ComputerV2`→`computer_v2`). `ManageSession` keeps a pair and gate entry only for old transcripts.
- Every MCP tool starts DEFERRED, loaded via `ToolSearch` (`toolSearchEnabled: true`, every mode), except the `sessions` pair (`eager` → `_meta["anthropic/alwaysLoad"]`); `deferToolsFor` defers `CronList` (code, dispatch). The runtime lists deferred tools in a persisted `deferred_tools_delta` attachment (once per pool change); a provider that cannot search gets full injection.
- Allowed lists (claude's `Options.tools`, `toolsFor(mode, exposure)`; never filters MCP tools; code: absent):
  - chat `CHAT_BUILTIN_TOOLS`: `AskUserQuestion`, `ToolSearch`, `WebFetch`, `advisor` + the search tool (below); NOT `SendMessage`/`ListAgents`/`ReadNotifications` ([dispatch-and-messaging.md](./dispatch-and-messaging.md)).
  - dispatch `DISPATCH_BUILTIN_TOOLS`: `AskUserQuestion`, `Bash`, `CronCreate`, `CronDelete`, `CronList`, `PushNotification`, `Read`, `ScheduleWakeup`, `SendMessage`, `TaskStop`, `ToolSearch`, `WebFetch` + the search tool; plus eager `SpawnSession`/`ListSessions`, deferred `Computer`|`ComputerV2`/`Browser`. Office is code only.
- Fail closed: `disallowedToolsFor` names the capability tools a mode lacks and, for chat/dispatch, every `KNOWN_RUNTIME_BUILTINS` entry the allowed list omits; at `system/init` `toolSurfaceViolations` checks `init.tools` against `Options.tools` + capability plain names + `mcp__*` (a missing list is a violation too) → `agent_error` `code: "tool_surface_unenforced"`, child aborted (`winter-session.ts`).
- `Options.legacyToolNames` (`LEGACY_TOOL_NAMES`, every mode): `mcp__winter__research__Search` → `Search` (old histories, `ToolSearch` `select:`, agent definitions, rules).
- `capabilities.list` reports EFFECTIVE `deferred` modes: only where the mode's default model can tool-search (`toolSearchSupportedBy`; dispatch's pin, else `settings.provider.model`). `packages/core/test/e2e/tool-surface-e2e.test.ts` pins each mode's eager list and deferred pool.

## Web tools

- The web surface is the child's `WebFetch`/`WebSearch`. `webOptionsFor` → `Options.web`: the Exa key as a Keychain LOCATOR (`search.authRef`, resolved over `credential_resolve`), `pins.research` as `fetch.digestModel` (dropped when unresolvable), the dangerous-domain floor as `blockedDomains`; `fetch.privateAddressPolicy` is `ask` only in code outside a dispatch child, else `deny`.
- `Search` (Exa ANSWER mode, `POST https://api.exa.ai/answer`, `x-api-key`) is the SDK's opt-in built-in: offered only when `Options.tools` names it AND `search.authRef` names a key. `/answer` has no anonymous tier, so chat and dispatch get EXACTLY ONE of `Search`/`WebSearch`: `exaKeyPresent(store)` (`runtime-sdk/credentials.ts`; secret `EXA_API_KEY_SECRET`, `agent/exa-key.ts`), read once per incarnation, drives `toolsFor`, `webOptionsFor` and `chatSystemPrompt`/`dispatchSystemPrompt`. UNDEFINED reads as stored at every door; a store that THROWS reads as absent (→ `WebSearch`).
- Two hooks: the LIVE floor (shipped ∪ `dangerousDomainsAdded`, per call) injected as `blocked_domains`, which `Search` reads only to ADD to its spawn-time floor (never advertised, never sent to Exa); and one `{kind:"network", tool:"Search", query, outcome}` line per call in `<home>/audit.jsonl` (`searchAuditHook`; never the key or answer).
- That is the DAEMON's chat. The phone's `apple/WinterChatKit` engine is a second producer — `Search` (Exa `/answer`, key only) + its own `WebFetch` port + `AskQuestion`, no `WebSearch`. Say which engine you mean.

## Hooks (`runtime-sdk/hooks.ts`, `sessionHooksFor` → `Options.hooks`)

PreToolUse order: plugin pre-tool; bash safety reviewer (`Bash`, `auto` only — [internal-jobs.md](./internal-jobs.md)); escape floor + `bashProtectedWriteHook` (a Bash write under a protected item dir is asked, sandboxed or not); path fence (unmatched); connector-permission floor ([mcp.md](./mcp.md)); `computerV2AllowHook`; `toolSearchDontAskHook` (READ_ONLY verdict for `ToolSearch` under `dont-ask`, else no deferred tool could load); `fileDiff` snapshots; the dangerous-domain floor for `WebFetch` (deny) and `WebSearch`/`Search` (floor into `blocked_domains`) — registered LAST: transforms compose last-writer-wins. PostToolUse: plugin, `Search` audit, `fileDiff` producer, diagnostics-after-edit; PostToolUseFailure: plugin + audit. Every floor is `failClosed`-wrapped (throw/timeout/malformed = deny); the plugin, fileDiff and diagnostics observers are not.

## `tool_result.siteIcons`

Optional `[{url, iconUrl}]` (schema and caps `SITE_ICONS_MAX`/`SITE_ICON_URL_MAX_LENGTH` in `packages/protocol/src/events.ts` — [protocol-and-remote.md](./protocol-and-remote.md)); never model-visible. ONE producer, read statelessly at the projector's `tool_result` emission (`runtime-sdk/site-icons.ts`): the runtime's host-facing block field `winter_site_icons: [{url, icon_url}]`. `sync.push` STRIPS that one key from a pushed `tool_result` (`ipc/sync.ts`): a phone list is never stored, a re-pushed daemon-born fork still lands. The Mac pill's `FaviconCache` draws from it (in-memory only).

## Reads, writes, fences

- Reads are unfenced except daemon state. `Read`/`Glob`/`Grep` deny rules (`controlPlaneDenyRules`): `<home>/run`, `<home>/runtimes`, `sdk/.winter.json`, and in any run folder or `claude-resume-*` root ONLY the generated `.winter.json`/`.claude.json`/`.credentials.json` + `backups/**`. The sandbox's `denyRead` holds the three real paths; the run-folder files ride the deny rules and the path fence's `protectedReadDenial`.
- Writes to every SELF-GRANT path are denied by the write-tool deny rules (`controlPlaneDenyRules`) and the bash sandbox's `denyWrite` (`sandboxConfigFor(home, cwd)`). **`selfGrantDenyWrite(home)` is the ONE source** — the control-plane filenames `permissions.local.json`/`settings.json`/`settings.local.json` (`CONTROL_PLANE_FILENAMES`, `runtime-sdk/control-plane.ts`) under any `.winter/` and the user's global copies; `<home>/{run,runtimes,plugins,permissions,cache,agents,computer-use}`, `<home>/trust.json`; and, for the cwd and its project roots, the project's `.winter/` control files, agents and the four protected item dirs (`skills`, `commands`, `rules`, `output-styles`). The sandbox `denyWrite` = it + `protectedHomeDenyWrite` + `projectSandboxDenyWrite(cwd)`; `runtime-sdk/home-fence.ts` derives the escape floor and write-tool fence from it (protected paths excluded: a card, not a hard deny). A new self-grant path goes there.
- `sdk/projects/**` outside each project's `memory/` is the runtimes' store: no deny rule or sandbox entry (it would take the MEMDIR); the escape floor and path fence (`storeWriteDenial`) deny a write there.
- Protected paths (`runtime-sdk/protected-paths.ts`): the four item dirs under `sdk/` and under any `.winter/`, plus `sdk/WINTER.md`, load into future sessions, so a write is a CARD in code under EVERY policy and a typed deny in chat/dispatch — from the path-fence hook (any project's item dir at any depth, trusted or not; it also runs the control-plane fence, store and read denials), the router's ask rules (the trusted project's walk cwd→root, never `$HOME`; `protectedPathRules`), and the bridge, which never auto-allows one (bypass/accept-edits/auto → card, dont-ask → deny). `<root>/WINTER.md` is ordinary.
- A sandbox escape (`Bash` + `dangerouslyDisableSandbox`) follows claude's rule — deny rules, permission mode, allow rules, then the bridge; a saved allow rule allows it natively unless a hook denies or asks. Three fences from ONE list (`home-fence.ts`): the sandbox `denyWrite`; the escape floor (`escapeFloorHook`, EVERY policy, bypass included: every self-grant path above on ANY mention, and only in a write-shaped position — so plugin skill scripts still run — `cache`/`plugins`/`sdk/plugins`/`computer-use` (`HOME_WRITE_ONLY_FENCED`, matched as a whole path segment), a project's `.winter/mcp.json`/`settings*.json`/item dirs, `sdk/projects` outside `memory/`, `claude-resume-*` roots); the bridge's write-tool fence (`controlPlaneTargetForCall`, `control-plane.ts`). The floor is a static match on the normalised command (case, quotes, `//`, `/./`, `..`, `cd`, child path variables); a path built at run time is beyond it. Under `auto` an escape reaching the bridge runs only on the reviewer's positive clearance for that exact call and command (`bridge-common.ts`; reviewed unsandboxed; no reviewer/model, transient failure or missing call id → card in code, typed deny in dispatch).

## Saved allow rules

`Options.permissions.allow`, code only, read live per incarnation: `persistedAllowRulesFor` → `sdkAllowRulesFor`, the one translation into claude's grammar, never wider than saved (deny wins). Sources: `sdk/settings.json` `permissions.allow` (verbatim; Winter's gate reads its inverse, `winterGateRulesFromSdk`); the read-only record `<home>/permissions/projects.json` (`agent/approved-project-rules.ts`: keyed by `repoRootFor(cwd)`, never read through a link, applied regardless of trust); a TRUSTED project's `.winter/settings.json`/`settings.local.json`/`permissions.local.json` at `projectScopeRootFor(cwd)` (a worktree's own top). `repoRootFor` (`agent/memory-dir.ts`) ignores a `.git` file whose git dir does not own the cwd. On a run-home build the child reads these from its run folder and the daemon states none ([runtime-home.md](./runtime-home.md)). Dispatch's code children receive them; under `plan` the SDK still holds writes back.

## Skills

- Skills reach a child through its run folder, never from the daemon: `sdk/skills` (+ `self`), a trusted project's `.winter/skills` walked nearest-first cwd→`projectScopeRootFor`, and enabled plugins loaded natively (`enabledPlugins`, code only, shown as `plugin:skill`). `settingSources` is `["user"]`; without run homes `[]` (discovery off). Install+enable is the consent for a plugin's claude-native content. `skills.list` reports `loadsInSessions`/`sessionNote` (plugin half: `plugins/plugin-skills.ts`).
- The one shipped skill a child can load is a managed COPY. `packages/core/skills/computer-use/SKILL.md` (ComputerV2 recipes; the tool description never points at it) is the source and the `builtin` row; its text is EMBEDDED by a bun text import (`migration/builtin-skills.ts`, `src/ambient-md.ts` types `*.md`; a compiled `winter-core` has no `skills/` — `packages/cli/test/compile-core.test.ts` seeds from the binary). Every boot, after the settings split, `seedBuiltinSkills` writes `<home>/sdk/skills/computer-use/SKILL.md` (atomic, 0600) and records its hash in `<home>/migration/builtin-skills.json`: never seeded + absent → write; seeded + untouched + shipped text changed → overwrite; seeded + edited → left alone; seeded + deleted by the user → NEVER re-created; present but never seeded (the user's own) → never touched; byte-identical → record repaired only. A symlinked dir/file is never written through; an unparseable record stops seeding; failures only log. The copy is a `user`-tier skill (`loadsInSessions: true`). To ship another: a dir under `packages/core/skills/` + an entry in `BUILTIN_SEEDED_SKILLS`.
