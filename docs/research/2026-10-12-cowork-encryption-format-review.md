# Cowork private-disk encryption format: independent review

Date: 2026-10-12. **Recommendation: advance a fixed LUKS2 `aes/xts-random` + `hmac(sha256)` profile to the bounded fixture; reject `aes/gcm-random` as the default for long-lived build workspaces. Neither profile is production-accepted by this review.** Keep the existing broker/worker topology and pinned Linux/cryptsetup direction. Do not replace this work with standalone `integritysetup`, unauthenticated XTS, or a new home-grown encrypted block format.

This is source review and an implementation recommendation, not permission to run a VM or evidence of encrypted I/O. No volume, key, mapper, filesystem, VM, live Winter process, home or Keychain was created or accessed. Only this report was written. Review started at `13bd3a19`; the concurrent checkout reached `abbdefb6` while it was underway. The relevant contract is [`cowork-storage-security.md`](../cowork-storage-security.md), especially lines 10–46 and 86–107. Candidate details are in [`candidate-2026-10-12.md`](../../spikes/cowork-hvf/kernel/userspace/candidate-2026-10-12.md).

## Decision and its limits

XTS/HMAC is the better **next candidate**, because it uses independent, familiar encryption/authentication primitives and avoids GCM's catastrophic nonce-reuse behavior. Linux's `authenc` construction authenticates associated data and ciphertext; the reviewed decrypt path checks the HMAC before decrypting. This is useful assurance for the specific implementation, not a claim that XTS itself supplies authentication. [Linux 6.18.35 `crypto/authenc.c`, particularly `crypto_authenc_decrypt_tail`](https://raw.githubusercontent.com/gregkh/linux/v6.18.35/crypto/authenc.c)

Cryptsetup 2.8.8 still calls authenticated LUKS2 **experimental**. Its stable release number does not remove that qualification. A successful small fixture cannot settle long-term crash recovery, migration, support or cryptographic lifetime. Shipping this profile means Winter owns its narrow supported configuration, recovery tooling, regression matrix and upstream security updates. Make that an explicit production gate rather than treating the label as either proof of unsuitability or something to omit. [Cryptsetup 2.8.8 authenticated-encryption manual](https://gitlab.com/cryptsetup/cryptsetup/-/raw/v2.8.8/man/cryptsetup.8.adoc)

The claim that can eventually be supported is: private sector contents are encrypted; unauthorized new ciphertext/IV/tag combinations are rejected on read; authenticated control records constrain volume identity and interpretation. **Valid older sectors, journal states and whole-volume snapshots are not made fresh by this format.** At-rest encryption does not prevent same-user deletion, corruption, host API access or observation of the admitted running guest.

## Exact construction and key handling

| Parameter | Recommended fixture candidate | Rejected default candidate |
| --- | --- | --- |
| libcryptsetup cipher / mode / integrity | `aes` / `xts-random` / `hmac(sha256)` | `aes` / `gcm-random` / `aead` |
| Effective dm-crypt transform | `capi:authenc(hmac(sha256),xts(aes))-random` | `capi:gcm(aes)-random` |
| Raw volume material | 96 bytes: AES data key 32, AES tweak key 32, HMAC key 32 | 32-byte AES key |
| Persisted metadata per 4096-byte encryption sector | 32-byte HMAC + 16-byte IV = 48 bytes | 16-byte tag + 12-byte IV = 28 bytes |
| Authentication input | ciphertext plus logical sector number and IV | ciphertext plus logical sector number and IV |

The transform translation is explicit in [cryptsetup `libdevmapper.c`](https://gitlab.com/cryptsetup/cryptsetup/-/raw/v2.8.8/lib/libdevmapper.c); key/tag/IV sizes are explicit in [`lib/integrity/integrity.c`](https://gitlab.com/cryptsetup/cryptsetup/-/raw/v2.8.8/lib/integrity/integrity.c). Linux consumes encryption bytes first, authentication bytes last, then internally constructs the crypto API's differently ordered authenc key. Its AAD contains the little-endian sector number and IV. AAD does **not** independently contain a workspace UUID; independent per-volume keys and admitted metadata provide that separation. [Linux 6.18.35 `dm-crypt.c`, `crypt_copy_authenckey`, `crypt_convert_block_aead`](https://raw.githubusercontent.com/gregkh/linux/v6.18.35/drivers/md/dm-crypt.c)

For XTS-AES-256, **512 CLI key bits describe the two AES keys together**. `get_adjusted_key_size` adds the 32-byte integrity key, producing 96 total bytes. Direct `crypt_format` / `crypt_activate_by_volume_key` callers supply **96**, not 64, bytes. Do not call a 64-byte XTS key “AES-512.” [CLI key-size adjustment](https://gitlab.com/cryptsetup/cryptsetup/-/raw/v2.8.8/src/utils_luks.c)

Use native CSPRNG-generated, independent component keys; explicitly reject equal AES halves. Wrap all 96 bytes under the existing 32-byte broker KEK, binding a versioned format ID, exact key length/layout and geometry. This changes the native protocol. Current `SyntheticVault` is explicitly volatile and enforces 32 bytes at `apple/Cowork/WinterCoworkKeyBroker/Sources/KeyBrokerCore/Identity.swift:42–75`; `FixtureWorker/main.swift:18–20` also hardcodes 32. It is not durable production custody. Never reinterpret a pre-existing 32-byte volume key as a passphrase/seed or silently replace it.

`crypt_format` does not create a keyslot; the raw-key activation API supports the proposed keyslot-free profile. No password, password KDF or extra unlock secret is needed. [Public libcryptsetup API](https://gitlab.com/cryptsetup/cryptsetup/-/raw/v2.8.8/lib/libcryptsetup.h) The header still contains a verification digest over the volume key. With `CRYPT_PBKDF_NO_BENCHMARK`, the digest code selects its minimum iteration count; the pinned minimum is 1000. Use explicit PBKDF2-SHA256 settings and verify the resolved header. This is verification of random key material, **not** advice to protect a human password with 1000 iterations. [Digest implementation](https://gitlab.com/cryptsetup/cryptsetup/-/raw/v2.8.8/lib/luks2/luks2_digest_pbkdf2.c), [PBKDF limits](https://gitlab.com/cryptsetup/cryptsetup/-/raw/v2.8.8/lib/crypto_backend/pbkdf_check.c)

## Lifetime is still a production requirement

Final NIST SP 800-38D §8.3 limits RBG-based GCM to **2^32 encryptions under one key across all instances**. At one invocation per 4096-byte sector, that is **16 TiB of encryption work**, including initialization and rewrites, not 16 TiB of capacity. §8.2.2 also requires independent RNG instances. Counter reset on boot, cloning a running RNG state, or rotating only the wrapping KEK does not establish a new disk-key lifetime. Linux's random-IV function uses `get_random_bytes`; it supplies no persistent per-volume invocation counter. These are avoidable operational hazards for a long-lived build disk. [Final SP 800-38D §§8.2.2–8.3](https://nvlpubs.nist.gov/nistpubs/Legacy/SP/nistspecialpublication800-38d.pdf)

XTS/HMAC is not an unlimited-write solution. The **final 2010** SP 800-38E approves XTS for confidentiality, not authentication. The **September 2026 initial public draft**, not a final requirement, gives a maximum of 2^44 AES blocks per key scope (**256 TiB**) and recommends at most 2^36 (**1 TiB**) for optimum security; a data unit is limited to 2^20 blocks. It defines scope in terms of data an adversary might access. Do not equate scope to live disk capacity when the threat includes retained images and snapshots, or claim this randomized-tweak composition is a NIST-validated construction. [Final SP 800-38E](https://csrc.nist.gov/pubs/sp/800/38/e/final), [2026 initial public draft, §§3–4](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-38Er1.ipd.pdf)

**Proposed conservative first production policy:** budget at most 1 TiB of encrypted payload exposure per volume-key generation until a cryptographic review approves a different budget. Count initialization, rewriting and imported generations; retain usage across cold starts and supported crash/restore. Start automatic maintenance before the budget is exhausted. This is a product default informed by the draft, not a claim that the draft is binding or that exceeding 1 TiB suddenly breaks XTS.

Use a reviewed replacement-volume migration with fresh 96-byte material, authenticated copying, flush/verification and an atomic admitted-generation switch; preserve the old encrypted generation until recovery commits. KEK rotation and relocation preserve the DEK and its consumed budget. Do not enable online reencryption merely to solve this. A conservative worker-issued-byte allowance may overcount journal/metadata writes and be useful for XTS storage exposure, but it must reserve before I/O, count failed/partial writes, survive crashes and cover every path. It is **not** automatically a GCM invocation counter. The first tiny fixture needs only a fixed small write cap; durable budgeting/migration remain production work.

## Header, journal and replay boundaries

LUKS2's header checksum and redundant header sequence numbers are not keyed authority. The format specification explicitly excludes intentional metadata modification from their protection. A volume-key digest proves a key matches that digest; it does not authenticate arbitrary replacement metadata. [LUKS2 on-disk specification §§1.2, 2.1](https://gitlab.com/cryptsetup/cryptsetup/-/raw/v2.8.8/docs/on-disk-format-luks2.pdf)

Proposed fixed-profile admission must bind both header copies and their bounded byte ranges, LUKS UUID, cipher/key layout, sector/tag size, data/IV offsets, backing length, dm-integrity version/flags/geometry and volume generation to the broker-authenticated record. Admit only the expected single crypt segment, digest, empty keyslots/tokens and no reencryption/repair flags. Reject a modified copy even if generic LUKS recovery could repair it. Missing keys or damaged identity remain locked/recovery-required.

**A preflight hash followed by rereading a mutable host header is a TOCTOU gap.** The implementation must ensure the bytes parsed are the bytes admitted: for example, copy a bounded header once, authenticate that copy, and let trusted bootstrap consume the immutable copy through a supported detached-header arrangement. This is an implementation proposal requiring an exact API/block-layout review. Pinning an inode alone does not stop modification. dm-integrity's separately consumed superblock needs equivalent consideration: validate its fixed fields, enforce the expected mapping before filesystem exposure, and prove that a post-check change cannot silently select another layout. Do not describe a preflight hash alone as solving this.

The kernel journal provides data/tag update atomicity in journal mode. Bitmap mode recalculates interrupted regions and offers weaker corruption behavior; it is excluded. Flush requests force journal commit. [Kernel dm-integrity documentation](https://docs.kernel.org/admin-guide/device-mapper/dm-integrity.html) But LUKS2's parameter validator rejects journal encryption/MAC, and segment construction records both as `none`. Thus the sector payload in the journal is already ciphertext, while its structural metadata is not a keyed authenticated journal. [Cryptsetup parameter validation](https://gitlab.com/cryptsetup/cryptsetup/-/raw/v2.8.8/lib/setup.c), [LUKS2 segment construction](https://gitlab.com/cryptsetup/cryptsetup/-/raw/v2.8.8/lib/luks2/luks2_segment.c)

There is a concrete reason not to expect every journal mutation to return an authentication error: in pinned Linux `dm-integrity.c:3595–3597`, an unknown commit ID takes the `clear_journal` path; inconsistent commits can also terminate the replay range. This is part of crash recovery. Sector HMAC still prevents forging new accepted data, but suppressing a committed journal entry can expose an older valid home-location sector. Journal MAC would not itself solve replay of old authentic entries. [Linux 6.18.35 `replay_journal`](https://raw.githubusercontent.com/gregkh/linux/v6.18.35/drivers/md/dm-integrity.c)

Accordingly, test and document same-LBA replay, whole-image rollback and journal suppression separately from new-content forgery. No blanket “all tampering is detected,” “authenticated journal,” or “fresh after rollback” claim is warranted. If production requires rejecting every damaged journal before any automatic recovery, the current candidate does not meet that stronger requirement; upstream format/kernel work or another architecture is necessary. The accepted contract must explicitly distinguish legitimate torn-write recovery and the residual rollback boundary.

## Durability, provisioning and alternatives

An application `fsync` is meaningful only if filesystem, dm-crypt, dm-integrity, virtio and the macOS backing implementation preserve flush/FUA ordering and errors. A successful `pwrite`, a timer-based journal commit and a clean guest shutdown are weaker observations. Linux requires remapping drivers to propagate FUA and implement global preflush correctly. [Linux writeback-cache contract](https://docs.kernel.org/block/writeback_cache_control.html) Review the actual libkrun/macOS completion path, including its host durable-flush primitive, and fault-inject it. Worker `SIGKILL` while the host retains cache does not simulate host power failure; make that evidence limit explicit.

Discards are unsupported in authenticated LUKS2. Fully initialize the authenticated payload before filesystem use and keep raw holes, `no-wipe`, bitmap, recovery-ignore and implicit resize paths disabled. Consequently, allocating a large sparse host file is not a cheap promise of a large usable encrypted disk: initialization writes ciphertext across the provisioned payload. Deleted guest files do not reclaim host extents through TRIM. Admit capacity against real host free space, measure physical allocation, retain a host-free floor, and treat growth/compaction as a separate authenticated migration. [Cryptsetup authenticated-encryption limitations](https://gitlab.com/cryptsetup/cryptsetup/-/raw/v2.8.8/man/cryptsetup.8.adoc)

| Alternative | Finding and disposition |
| --- | --- |
| Standalone dm-integrity + dm-crypt | Not a maturity escape. Cryptsetup 2.8.8 says standalone integritysetup was intended for non-cryptographic protection and directs cryptographic users to LUKS2/AEAD. Hand assembly also makes Winter own key, order, header and journal compatibility. Do not select it. [2.8.8 release notes](https://gitlab.com/cryptsetup/cryptsetup/-/raw/v2.8.8/docs/v2.8.8-ReleaseNotes) |
| Plain XTS with filesystem checksums | Checksums are not secret-key authentication. It fails the accepted authenticated-integrity requirement. |
| fscrypt | Upstream explicitly does not support authenticated encryption. It is not a substitute for the required disk boundary. [Kernel fscrypt documentation](https://docs.kernel.org/filesystems/fscrypt.html) |
| dm-verity | Useful for immutable trusted artifacts, but read-only and not a writable workspace solution. [Kernel dm-verity documentation](https://docs.kernel.org/admin-guide/device-mapper/verity.html) |
| OpenZFS native encryption | A meaningful fallback if production LUKS gates fail, because it integrates encrypted/authenticated blocks and managed key evolution. It changes filesystem, kernel/build, boot, resource and recovery scope; some pool/dataset metadata remains plaintext. Its raw user key is a wrapping key for internal master keys, which would change the current direct-DEK contract. Do not migrate this spike to ZFS without a separate measured design review. [OpenZFS key/encryption manual](https://openzfs.github.io/openzfs-docs/man/master/8/zfs-load-key.8.html), [documented salt-use policy](https://openzfs.github.io/openzfs-docs/Performance%20and%20Tuning/Module%20Parameters.html#zfs-key-max-salt-uses) |

## Bounded fixture and promotion gates

The next reviewable increment should implement the versioned native 96-byte profile and trusted bootstrap **without running it**, then obtain the existing independent gate review. Keep 128 MiB raw backing, 4096-byte encryption sectors, the candidate's bounded 4 MiB requested journal, journal mode, fixed payload/header/geometry limits, no discards and a strict maximum synthetic write count. Record resolved geometry rather than assuming requested journal sizes map exactly to disk. Never silently format or reprovision an existing identity after an incomplete attempt; retain that state for explicit recovery.

| Fixture obligation | Required evidence |
| --- | --- |
| Admission and key custody | Exact profile/length rejection; wrong, absent and cross-volume keys; immutable artifact and exact-process binding; no raw key in Core/argv/environment/logs/files; closure of the scoped key channel before tools. Cold restore uses the same material. Relocation and KEK rotation preserve it. |
| Geometry and provisioning | Full authenticated initialization; 48-byte tag-space and 96-byte layout proved by resolved non-secret configuration and independent test vectors; empty keyslots/tokens; both LUKS headers and dm-integrity fields bounded/authenticated; each torn provisioning stage remains unavailable. |
| Ciphertext and sector integrity | Synthetic markers readable inside the guest and absent from raw data/journal scans; ciphertext, IV and tag mutations each fail reads; full tuple cross-LBA and cross-volume substitution fails; partial backing writes/truncation cannot cause plaintext fallback. Drop caches or cold boot before reads so page-cache hits do not mask corruption. |
| Replay and structural metadata | Mutate header with a recomputed plain checksum; corrupt either header; change superblock layout/flags after preflight; alter journal LBA/commit fields; replay same-LBA old tuples, journal-only images and whole images. Record allowed replay explicitly and reject forged content. No assertion that every malformed commit ID must fail unlock. |
| Crash and durability | Deterministic fault points before/after journal commit and home-copy completion; acknowledged fsync records survive restart; unacknowledged writes may be old or new but must be structurally valid. Inject short I/O, EIO, ENOSPC and flush failure; never acknowledge an unsuccessful durable barrier. Test filesystem journal recovery as well as raw sectors. |
| Active memory return | Repeat the live reclaim cycles with encrypted asynchronous I/O in flight, heartbeats, retained-data checks and post-reclaim authenticated rereads. Measure guest/kernel/worker peaks and host backing allocation; do not inherit the earlier plaintext/restricted result. |

Use only disposable homes, fixture shares, isolated coordination and synthetic native keys. For data-corruption cases, make one controlled mutation per saved fixture image and preserve the original and fault schedule. No generic repair tool, plaintext export, encrypted-volume auto-recreation or guest tool access to raw disk/mapper/key controls is permitted.

Passing this bounded suite selects a **feasible integration candidate**. Production additionally needs durable broker custody/authority and rollback dispositions, recoverable key/volume generation transitions, write-budget maintenance, larger build-workload performance/ENOSPC testing, backups/restores, guest confinement, code signing and full worker/device/reclaim regression. These are concrete promotion criteria; they are not proved by this report or by a successful capability executable.
