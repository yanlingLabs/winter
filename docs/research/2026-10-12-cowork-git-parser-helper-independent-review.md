## Finding

`packages/core/src/cowork/git/read-transport.ts` checks authority after each nonempty body chunk, but awaits the final `reader.read()` EOF and then calls the response parser without another current check. A revocation committed during that final await can therefore admit response bytes into the helper even though the final delivery check later refuses. Add a synchronous `recheck()` immediately before response parser validation and keep the existing check after parsing. Request parsing already has a preceding check.

An isolated archive test injects a reader whose final EOF changes its host grant to revoked, and a parser that only increments a counter. The overall read rejects `authority_denied`, but the parser counter is **1**, where the required pre-parse refusal expects **0**. Result: **1 targeted test failed, 2 assertions, 8 other tests filtered**. No helper, subprocess parser, account or network was used. Evidence beside this report: `2026-10-12-cowork-git-parser-preparse-independent-probe.ts`, `-tests.log` and `-tests.json`. Original implementation and the author's continuing work were not edited.

## Source findings and limits

- The entry imports the exact shared `read-wire` validators and `checkPackBudget`, rather than implementing a second parser. The fixed 20-byte request header bounds kind, packet length, object count and expanded bytes; the child verifies exact EOF length. Its fixed ready/verdict/digest output binds the returned status to the original owned bytes. URLs, credentials, host grant IDs and runtime authority are absent from this pipe protocol.
- Host admission checks canonical artifact paths, ordinary file identities and payload digest, then static code requirements, hardened runtime and prohibited entitlement exceptions. Identity is rechecked after awaited signature inspections and before use. The Node PID's dynamic code requirement is checked after readiness and before sending packet input. Requirements and bundle paths are host-owned configuration; the interface's `native-confined` string is not independently an authority token. Protected immutable artifact staging remains a packaging prerequisite, including the acknowledged same-user replacement residual.
- The bootstrap verifies sandbox denials, installs and verifies hard CPU/FD/core/file-size limits, closes inherited descriptors above stdio, replaces the environment and execs the exact Node path with jitless/no-addon/no-global-search flags. The profile has no network or fork permission and no general writable/file-data roots. It grants broad metadata and required system-library reads, as documented. This is the dedicated helper policy, not an extra sandbox around ordinary Code tools.
- Parent input is copied and length-bounded. Output is capped at 45 bytes and stderr at 4096 bytes. Ready identity/RSS checks precede input. Wall timeout, cancellation and RSS excess terminate the owned process group. Capacity is released by the owned exit event, not merely by sending kill; a missing exit after the drain timeout rejects and retains capacity. Reactive sampled RSS allows overshoot and does not constitute a hard memory reservation; README wording makes that distinction.
- The auxiliary static `codesign` admission wrapper has a five-second kill timer and capped readers, but no separate kill-confirmation/drain deadline; it is weaker lifecycle evidence than the parser process owner. The fixture build-command wrapper similarly has no per-child timeout/output cap or explicit reap-on-test-timeout. Fixed trusted local tools and bounded fixture inputs keep the existing tests narrow, but an outer test timeout is not proof that these auxiliary children were stopped. Production packaging/admission should preserve this distinction rather than claiming every subprocess has the parser's lifecycle bounds.
- The `validate` setup increments capacity before profile generation/spawn. A synchronous exception in that setup can leave capacity occupied despite no child being created. This is a fail-closed availability/cleanup edge, not a permission escape; covering it with an owned-spawn setup-failure regression would make the lifecycle contract clearer.

These auxiliary-process and no-child setup lifecycle gaps are nonblocking for the narrowly gated, fixed-artifact fixtures reviewed here. They remain production-hardening requirements; this acceptance must not be described as proof that all admission/build subprocesses have bounded teardown, or as permission to remove the production refusal.

## Existing fixture-test assessment

The existing helper cases are relevant and appropriately scoped for root's isolated verification: exact parser success, malformed packet/pack rejection, unsandboxed/weaker-profile refusal, signature/payload/entitlement refusal, inherited environment denial, and bounded cancellation/resource behavior. They compile/sign only disposable copies, with ad-hoc signatures and no production identity.

The RSS-stop case does **not** create host memory pressure: it sets a 1024-byte threshold and starts normal Node, then verifies observed excess causes termination. The CPU case is a deliberately declared busy-loop payload with a hard two-second CPU limit and a ten-second wall limit, separately from the actual parser. Neither proves realistic worst-case production RSS overshoot. The denial payload reads/writes only disposable sentinel paths and attempts a loopback port/fork operation expected to be refused. These are useful narrow regression tests; rerunning the entire unrelated suite or escalating memory load is unnecessary for this source review. Root owns their execution; this reviewer launched none of them.
