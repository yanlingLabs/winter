# macOS workspace management slice

Base: `4453509b1b5fbdd08139e551d0b6dd4026ea7292`, branch `cowork/macos-workspaces`.
Scope: real Swift metadata/control client and Mac management surface, independently of VM execution. No Core/protocol TypeScript changes, runtime/SDK pins, VM launches, live app/home/Keychain access, pushes or releases.

## Implemented

The Cowork destination now opens `CoworkWorkspaceView` through the shell's existing non-attaching management connection. Its WinterKit `CoworkWorkspaceModel` uses the existing typed requests and real `WinterClient.request` transport. It lists workspace pages, filters reusable Projects by canonical ownership, loads paginated sources and the policy summary, and displays recorded lifecycle/power/trust/access and pending operation state. Complete and response-limit summary snapshots both fetch the actual source generation, bound to the snapshot config revision; policy reads are bound to the snapshot policy revision. Invalid/repeated cursors and duplicate source/workspace IDs refuse without publishing a partial generation. Explicit Refresh reads current state; no unsupported subscription/watch is invented.

Rename, remove and revoke use current expected revision and stable request IDs. The final-source removal button is disabled; final-source security revocation remains available and has separate confirmation text. Revocation/removal are desired state changes, never immediate guest acknowledgments or data deletion. Successful mutation receipts remain recorded when a subsequent refresh fails. Creation retains its idempotency key after commitment, including a failed follow-up read; the creation sheet closes on recorded commitment so the user cannot mistake a failed refresh for an uncommitted creation. The adapter serializes mutations while a receipt is in flight.

Workspace and reusable Project creation and source addition are implemented against their actual existing APIs and exercised by injected-host tests. The Mac-only `CoworkSelectionIssuer` seam accepts a user-picked URL for a separate authenticated host issuance operation, or invokes host-authorized repository selection; it returns opaque selections. The UI never sends a folder path/bookmark through workspace mutation RPCs, fabricates a grant, or asks users to enter opaque selection IDs. The native folder chooser selects one directory and cannot create directories.

**Production creation/addition remain disabled.** The actual daemon `disabledCoworkHost.selection` returns undefined and `requireProvisioning` throws `unsupported_topology`; no production selection issuer or capability-negotiation API exists. The CLI likewise explicitly refuses creation. The shell intentionally supplies no issuer until these host boundaries are implemented and admitted. This is a working metadata/control slice and tested creation/addition integration seam, not a completed production provisioning flow.

No conversation or VM launch action exists. A source reporting ready or VM reporting running never enables a Cowork session. The existing session-mode admission rules and reserved Cowork predicates are unchanged. The sidebar's existing unavailable/Soon treatment still refers to Cowork execution.

## Host integration boundary

Root owns any Core/protocol changes. Before enabling creation/addition, provide principal-bound local selection issuance, current grant validation and real provisioning admission; a picker URL alone is not authority. A proposed boundary is local-only folder selection preparation accepting a security-scoped bookmark/access/safe label, and local-only repository selection preparation from host-authorized repository identity, returning opaque selection IDs. Add a safe server capability projection before enabling these doors. Neither operation belongs in paired allowlists. The issuer must also handle cancellation/expiry/selection cleanup and grant revocation; this UI seam is not that implementation.

A future issuer should be passed only once production provisioning is admitted, and any capability downgrade must remove it. Actual VM launch/readiness, source transport acknowledgments, production watchers, conversation creation/Project membership, and source reauthorization remain backend/integration work. No folder path is automatically adopted as a workspace grant.
