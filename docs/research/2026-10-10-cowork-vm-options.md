# Cowork VM architecture options

Research cutoff: 2026-10-10. This comparison incorporates two Astra reviews of primary Apple and upstream sources. It covers the practical architecture families for Winter; it is not an exhaustive audit of every wrapper or a performance evaluation. No VM was launched, guest image prepared, or Winter/native bridge benchmarked. No backend or guest-sharing layout has been selected.

Accepted product inputs: standalone workspace per conversation; reusable Project workspaces; concurrent Project conversations sharing files and Project memory; separate logical transcripts; direct edits to selected host folders or selected GitHub repositories cloned by guest execution; Winter and its subagents in the guest; durable logical continuation after cold stop; no Winter-owned host process per conversation, preferably with controllers in the existing daemon.

The comparison separates backend, controller placement, guest allocation and guest OS. A VM per Project, a pool, and a shared helper are not competing hypervisor implementations.

## 1. Backend families

| Family | What Winter would use | Advantages for this task | Costs and limitations |
| --- | --- | --- | --- |
| Apple Containerization library | A Swift library using VZ on macOS, with image/init/process machinery | Less provisioning and guest-process plumbing to build; candidate for native integration into the daemon | Requires Apple silicon/macOS 26; native integration and persistent workspace behavior still need proof; pin an audited package version |
| Direct Virtualization.framework | Winter configures VM devices, disks, shares, networking and a guest supervisor | Explicit control; fewer higher-level lifecycle assumptions; underlying Linux guest support includes Intel and Apple silicon | Winter owns more image/provisioning/supervision machinery; available devices determine the actual OS floor |
| Custom Hypervisor.framework VMM or libkrun | Lower-level virtualization APIs or an embeddable VMM library | More control over the VMM; libkrun offers a C API | More device/security/lifecycle responsibility; Hypervisor permits one VM per calling process, so this does not put many independent VMs directly in one daemon PID |
| QEMU with HVF or emulation | QEMU's VM/device/storage stack and machine-control interface | Broad guest/device support; HVF acceleration on supported Mac architectures; emulation when required | Separate VMM lifecycle; emulation has different performance costs; not a demonstrated in-process Bun integration |
| Existing VM/container managers | Apple `container`, vfkit, Lima/Colima, Tart, Docker, OrbStack, Multipass, Podman, UTM or another full VM product | Existing provisioning and administration; useful prototypes or optional external backends | Another product's processes, defaults, upgrades and lifecycle; these wrappers do not establish embedded control in Winter's daemon |
| Outer Linux VM plus nested microVMs | One outer VZ guest; Firecracker/cloud-hypervisor-style environments inside Linux | Inner VMM processes live inside the guest, rather than one Winter host VMM process per conversation; can separate inner kernels | Extra virtualization/storage/network layers; Apple documents nested support on M3 and later; requires runtime capability checks and suitable guest KVM/kernel support; unvalidated here |
| Remote VM/sandbox | Remote Linux/KVM infrastructure executing Winter | Natural fit for cloned repositories; no local guest-memory cost | Changes the local-product scope; network/service/privacy/cost obligations; selected Mac folders need a separate explicit access/synchronization design |

Sources: [Containerization](https://github.com/apple/containerization), [Apple Linux guest support](https://developer.apple.com/documentation/virtualization/creating-and-running-a-linux-virtual-machine), [Hypervisor](https://developer.apple.com/documentation/Hypervisor), [libkrun](https://github.com/libkrun/libkrun), [QEMU architecture and accelerators](https://www.qemu.org/docs/master/system/introduction.html), [Podman providers](https://docs.podman.io/en/v6.1.3/markdown/podman-machine.1.html), [nested virtualization support](https://developer.apple.com/documentation/virtualization/vzgenericplatformconfiguration/isnestedvirtualizationsupported), [Firecracker prerequisites](https://github.com/firecracker-microvm/firecracker/blob/main/docs/getting-started.md).

The current Containerization documentation also describes a Linux cloud-hypervisor/KVM backend. That is relevant to a future remote or Linux-host product; it is not another native Mac backend. [Backend documentation](https://github.com/apple/containerization#backends)

Nested microVMs were mentioned in the initial survey but dismissed too quickly. The host-process preference makes them a conditional option worth showing explicitly. Their suitability is an architectural inference, not a demonstrated performance or reliability result. Apple's nested-support API was introduced in macOS 15; the documented chip requirement is M3 or newer, and applications must query support rather than infer it solely from the model name. [Apple capability API](https://developer.apple.com/documentation/virtualization/vzgenericplatformconfiguration/isnestedvirtualizationsupported)

## 2. Controller placement

| Placement | Winter-owned host controller processes | Implication |
| --- | --- | --- |
| Native bridge loaded into the existing daemon | No additional controller process per VM/conversation | Matches the preferred integration; an in-process native failure can take down the daemon |
| One shared native helper managing every VM | One additional Winter service overall | Preserves the no-process-per-conversation goal and separates native failures; changes the preference for control inside the daemon |
| Helper executable per VM | One additional helper per VM | Straightforward with CLI-oriented VMMs, but conflicts with the stated process preference |

These counts concern Winter-owned controllers, not all macOS processes. One application can own multiple `VZVirtualMachine` controller objects; Apple's multiple-VM networking example demonstrates that arrangement. Apple's backing execution services are a separate layer. In-process control does not promise that all VM execution occupies the daemon PID. The lower-level Hypervisor one-VM-per-process restriction must not be applied to VZ controller objects. [Apple multiple-VM example](https://developer.apple.com/videos/play/wwdc2026/224/), [Hypervisor process mapping](https://developer.apple.com/documentation/Hypervisor)

A Swift/native bridge must marshal operations onto each VM's designated queue. Node-API versus a minimal C-ABI/FFI shim is an integration decision still to validate; existing synchronous Keychain FFI is not proof of safe asynchronous VM integration. Native ownership, cancellation, event delivery, signing, entitlement and daemon-crash behavior all need testing. [VZ queue contract](https://developer.apple.com/documentation/virtualization/vzvirtualmachine/queue?language=objc), [Bun native integration](https://bun.sh/docs/runtime/ffi), [virtualization entitlement](https://developer.apple.com/documentation/virtualization/adding-the-virtualization-entitlement-to-your-project)

## 3. Guest allocation with concurrent Projects

| Layout | Standalone conversation | Project with concurrent conversations | Main tradeoff |
| --- | --- | --- | --- |
| VM per durable workspace | Its own VM | One Project VM runs several Winter conversation contexts against shared files/memory | Direct fit for the accepted sharing behavior; Project conversations share the guest kernel and VM failure boundary |
| VM per conversation | Its own VM | Separate kernels, with a shared-filesystem service or validated host-backed Project directory | Stronger execution separation; greater guest count and more storage/coherence complexity |
| One shared VM with guest containers | A container/environment in the common guest | Containers share an explicitly granted Project filesystem/memory location | Fewer guests, but unrelated workspaces share a kernel; Winter must enforce guest-side isolation and access |
| Outer VM with inner microVMs | An inner guest | Multiple inner guests plus shared Project storage, or one inner guest per Project | Adds kernel boundaries inside one outer guest; nesting and shared storage both require validation |
| Hybrid | Dedicated standalone VMs | One VM per Project, potentially a bounded set of active Project VMs | Allocation policy combining the first layout with resource admission; does not select the backend |

One Project VM is now a first-class candidate because concurrent conversations and shared Project memory are accepted requirements. It must aggregate occupancy across all conversations and their subagents; one idle conversation cannot stop a VM used by another. Separate transcripts mean separate conversation records, not confidentiality between agents with access to shared files and memory.

Do not independently mount the same ordinary writable block filesystem in several guests. A Project spanning multiple guests needs a single authoritative filesystem service or validated shared host directories. VZ directory sharing is a relevant primitive, but cross-guest coherence, locking, case sensitivity and Git behavior still need experiments. [Apple shared directories](https://developer.apple.com/documentation/virtualization/shared-directories)

Concurrency also means no automatic branch switch whenever a Project conversation starts. A shared checkout keeps its current branch and dirty state. The user's 2026-10-11 decision is ordinary shared-filesystem/Git behavior: agents coordinate through SendMessage and choose worktrees themselves. No Cowork-specific conflict manager, Git mutation lock, memory transaction service or workspace-wide conversation queue is assumed.

A bounded pool/admission policy applies to any layout. Pooling controls how many guests may run; it does not by itself provide isolation or make a writable disk safe to share.

## 4. Guest OS and platform support

Linux is the general tooling/repository candidate. It does not provide Xcode or native macOS application execution. A macOS guest is a separate workload choice and can also use VZ; it is not necessarily a different backend. It has different image provisioning, resource and licensing considerations. Do not apply macOS guest licensing assumptions to Linux guests. [Apple macOS guests](https://developer.apple.com/documentation/virtualization/running-macos-in-a-virtual-machine-on-apple-silicon)

Containerization's documented floor is Apple silicon/macOS 26. Direct VZ has broader underlying OS/hardware support, with feature-specific minimum versions. Winter itself currently targets macOS 26 in [Package.swift](../../Package.swift) and [the app project](../../apple/Winter/project.yml); the broader API does not automatically add older-macOS or Intel support to Winter's packaging. [Containerization requirements](https://github.com/apple/containerization#requirements), [VZ Linux architectures](https://developer.apple.com/documentation/virtualization/creating-and-running-a-linux-virtual-machine)

## Important limitations in particular candidates

- The pinned Containerization 0.47.0 `LinuxPod` path is experimental. Its normal VZ manager does not install the hotplug provider used to add containers after boot. Pre-registering containers and running multiple processes in one existing workspace environment are different arrangements. Do not promise an elastic pod pool from those APIs without a prototype. [LinuxPod](https://github.com/apple/containerization/blob/bc994b88df46207fad7775b0eabc51947e315881/Sources/Containerization/LinuxPod.swift#L24-L29), [VZ manager](https://github.com/apple/containerization/blob/bc994b88df46207fad7775b0eabc51947e315881/Sources/Containerization/VZVirtualMachineManager.swift#L49-L66), [hotplug implementation](https://github.com/apple/containerization/blob/bc994b88df46207fad7775b0eabc51947e315881/Sources/Containerization/VZVirtualMachineInstance.swift#L318-L325)
- libkrun's security documentation says its virtio-fs implementation alone does not confine the guest to the named directory. An embedded daemon with broad host access needs a separately established confinement design. [libkrun security model](https://github.com/libkrun/libkrun#security-model)
- External managers differ substantially. vfkit is a VZ CLI; Lima offers VZ/QEMU orchestration; OrbStack documents a shared Linux kernel; Podman exposes libkrun/applehv providers. Their presence on one list does not imply equivalent process or isolation models. [vfkit](https://github.com/crc-org/vfkit), [Lima VM types](https://lima-vm.io/docs/config/vmtype/), [OrbStack architecture](https://docs.orbstack.dev/architecture), [Podman machine](https://docs.podman.io/en/v6.1.3/markdown/podman-machine.1.html)
- Apple's `container machine` defaults described in the original research include broad home sharing and SSH forwarding. Do not adopt those as Winter's selected-folder boundary. A library integration can define its own grants. [Machine guide](https://github.com/apple/container/blob/1.5.0/docs/container-machine.md)

## What the research does and does not establish

Resource clarification, 2026-10-11: the user wants automatic capacity sharing rather than assigning CPU/RAM/GPU per VM. vCPUs share the Mac's physical scheduler, and VZ guest RAM reserves virtual address space with demand-backed physical pages. Returning guest-freed pages is a separate issue: current Apple container documentation says this is not automatic. VZ ballooning plus Containerization extension hooks provide an integration candidate, not demonstrated reclaim. A common Linux VM shares one guest memory pool but does not itself guarantee returning that memory to macOS. The [working spec's resource contract](../cowork-spec.md#resource-policy-and-product-surfaces) replaces the earlier fixed-allocation proposal. [Apple resource scheduling](https://github.com/apple/container/blob/f70ecbb926d925818a34917529e304b1177ce98c/docs/resource-usage.md), [memory size](https://developer.apple.com/documentation/virtualization/vzvirtualmachineconfiguration/memorysize), [current reclaim limitation](https://github.com/apple/container/blob/f70ecbb926d925818a34917529e304b1177ce98c/docs/technical-overview.md#releasing-container-memory-to-macos)

The principal native local candidates remain Containerization and direct VZ, without selecting between them. Shared-helper placement, per-Project guest allocation, and nested microVMs must be compared separately. Podman and UTM add examples of existing managers; they do not constitute new hypervisor families. Remote execution is shown as a scope change.

Apple describes sub-second startup for prepared lightweight Containerization guests. This is not a Winter-ready measurement and excludes image acquisition, provisioning, repository cloning and runtime reconstruction. Pause, RAM saved-state restoration and cold stop are different contracts. The selected durable state behavior does not require RAM snapshots. [Apple Containerization presentation](https://developer.apple.com/videos/play/wwdc2025/346/), [saved-state validation](https://developer.apple.com/documentation/virtualization/vzvirtualmachineconfiguration/validatesaverestoresupport())

Still unverified: signed Bun/native integration; exact host PID counts; cold/warm Winter readiness; CPU/RAM/disk overhead across many guests; concurrent Project filesystem semantics; folder revocation; Linux tool execution; failure recovery; and compatible image/runtime updates. A documentation survey can establish candidate coverage, but cannot choose a performance winner.

The [working specification](../cowork-spec.md) records the accepted behavior. [SDK PR #2](https://github.com/yanlingLabs/winter-agent-sdk/pull/2) is merged (`ec8012b5`, reviewed head `27f1c43e`) but unreleased and unpinned in Winter. It supplies a subagent-continuation prerequisite, not a Cowork VM implementation.
