# CEF spike: build it, sign it, run it — before Plan B gets written

**Date:** 2026-08-09 · **Status:** spike, nothing shipped, nothing integrated into Norma · **Question:** Plan A shipped a right-hand panel with daemon-owned tabs. Plan B wants to embed Chromium (CEF) into that panel. Before that plan gets written, which of its assumed facts actually hold up when you download, build, sign, and run the real thing on this machine?

**Short answer:** everything asked for got measured. The framework is bigger and the entitlement story is different than assumed; CEF's own build produces five helper apps, not four; the message-loop pattern every sample demonstrates is the wrong one for an app that (unlike CEF's own samples) already owns its run loop; and the one signing failure this spike deliberately provoked (ad-hoc-only, per the ground rules) is very likely an artifact of testing without a real Developer ID identity, not a preview of what Plan B will hit in Norma's real release pipeline.

All work happened in a scratch directory outside the repo; nothing under `apple/` or `packages/` was touched; the dev app/daemon were never launched; this file is the only write inside the repo.

---

## Corrections to the "already established" facts

This is the section the spike exists to produce. Five things stated as settled going in did not survive contact with the real distribution.

1. **Four helper variants was wrong — CEF's own CMake template builds five.** `cmake/cef_variables.cmake:398-404` in the 151.3.16 distribution defines `CEF_HELPER_APP_SUFFIXES` as base (`::`), Alerts, GPU, **Plugin**, Renderer. The Plugin helper is real, gets built, gets copied into `Contents/Frameworks/`, and needs its own entry in Plan B's `project.yml` and signing loop. Separately: at runtime, for a single HTTPS page load, only the **base** `cefsimple Helper.app` (used for `--type=gpu-process` and both `--type=utility` roles) and `cefsimple Helper (Renderer).app` were ever launched — `(GPU)`, `(Plugin)`, and `(Alerts)` sat on disk unused. Which bundle *exists* is not the same question as which bundle *runs what*, and that distinction matters for where Plan B puts entitlements.

2. **CEF's own build ships zero entitlements on every target.** `codesign -d --entitlements -` on the as-built `cefsimple.app`, its framework, and all five helpers returned nothing for every single one. `com.apple.security.cs.allow-jit` on Chrome's renderer helper (the "already established" fact) is Google's own addition to their fork's build, not something CEF's CMake template provides. Plan B must add every entitlement itself, from a blank slate.

3. **cefsimple does not use the external message pump.** It calls the blocking `CefRunMessageLoop()` (confirmed by reading `cefsimple_mac.mm`). The external pump is opt-in even in the fuller `cefclient` sample, gated behind `settings.external_message_pump` (`cefclient_mac.mm:598`), and is off by default. More importantly: **even the external-pump sample's own `Run()` method calls `[NSApp run]` itself** (`main_message_loop_external_pump_mac.mm:110`). No CEF sample in this distribution demonstrates CEF living inside a host application that already owns its own pre-existing run loop — which is exactly Norma's situation as a SwiftUI app. See §5.

4. **The hardened-runtime crash this spike reproduced is very likely a testing artifact, not a Plan B blocker.** Two independently ad-hoc-signed Mach-O binaries carry no Team ID at all, and hardened runtime's library validation refused to let one load the other. A real Developer ID build signs every nested binary with the *same* certificate, so every bundle shares one Team ID by construction — the exact condition this check is designed to accept. This is consistent with `2026-08-07-embedded-surfaces.md`'s measurement of `/Applications/ChatGPT.app`, which ships Chromium under one real Team ID **without** `disable-library-validation`. Full details and the caveat on this conclusion are in §4 — do not read this spike as "Plan B needs disable-library-validation."

5. **The minimal distribution ships no sample apps at all**, not a trimmed set. No `cefsimple`, no `cefclient`, no `tests/` directory of any kind — confirmed by `find` and by its own `README.txt`. Getting to `cefsimple_mac.mm`, or to anything buildable, required the 284 MB **standard** distribution. Only the `Release/` framework from either distribution is what would actually ship inside Norma.

## Q2 — Does a minimal embed actually build on this machine

Environment: macOS 26.6.1 (25G76), arm64, Xcode 26.4.1, AppleClang 21.0.0.21000099, CMake 4.2.1, no `ninja` installed.

**Configure:**
```
cd cef_binary_.../  && mkdir build && cd build
cmake -G "Unix Makefiles" -DPROJECT_ARCH=arm64 -DCMAKE_BUILD_TYPE=Release ..
```
2.2 seconds. No CMake policy-minimum friction at all — the predicted `-DCMAKE_POLICY_VERSION_MINIMUM=3.5` workaround was never needed. "Unix Makefiles" is not one of the two generators CEF's top-level comment calls "tested" on macOS (it lists Ninja and Xcode only), but `cmake/cef_variables.cmake` explicitly branches on `GEN_MAKEFILES` right alongside `GEN_NINJA`, and it worked without any special-casing. The only output was a harmless "Doxygen must be installed" warning (docs generation only).

**Build**, 14 cores (`sysctl hw.ncpu` = 14):

| Target | Wall clock | CPU | Notes |
| --- | --- | --- | --- |
| `make -j14 libcef_dll_wrapper` | 11.4s | 1119% (14-way parallel, genuinely compute-bound) | Produces `libcef_dll_wrapper.a`, 5.4 MB. AppleClang only, no external deps. |
| `make -j14 cefsimple` | 2m04.5s | **5%** | Only 5.70s user + 1.54s system CPU across 2+ minutes wall — this step is I/O/codesign-bound, not compute-bound: it copies the 332 MB framework into the bundle once, builds and copies 5 small helper `.app`s, and ad-hoc-signs every one of them as part of the CMake post-build step. |

Total active build time (excluding download/extract, which is Q1's concern): **~2 minutes 18 seconds**. Comfortably inside the 15-minute budget, with no Xcode/CMake version friction of any kind.

**It runs, and it renders.** `open cefsimple.app --args --url=https://example.com`. Verification took two passes because the first one was a false negative worth recording:

- `screencapture -x` from this sandboxed CLI environment produced a **solid black 3024×1964 PNG**, even though the app was alive (7 processes: main + gpu-process + 2 utility processes + 3 renderer processes) and `lsappinfo` showed it registered as a checked-in foreground GUI app. `osascript`/System Events could see the process but returned empty window-property data. This is consistent with the automation environment lacking macOS Screen Recording TCC permission — **not** a CEF or rendering failure. Worth remembering for any future spike run from this kind of environment: don't trust a black `screencapture` result as proof of anything.
- Relaunched with `--remote-debugging-port=9222` and used Chrome DevTools Protocol instead, which is unaffected by OS screen-recording permissions because it asks the browser's own compositor for pixels, not the window server. `curl localhost:9222/json` showed a `"page"` target with `"title": "Example Domain"`, `"url": "https://example.com/"`. A short Bun script opened the target's WebSocket and called `Page.captureScreenshot`, producing a real 1600×1136 PNG (36,820 bytes) showing the actual rendered "Example Domain" heading, paragraph, and "Learn more" link.

**Answer: yes, it builds, yes, it renders.** All cefsimple processes and their working directories (`~/Library/Application Support/CEF/User Data`, which the first launch created in the real home directory since no `--user-data-dir` was passed) were killed and deleted before moving on.

## Q4 — Signing under a hardened runtime

Norma signs Developer ID with `ENABLE_HARDENED_RUNTIME=YES` and currently-empty entitlements. Per the ground rules, only ad-hoc (`-`) identities were used here — this is the one area where that constraint materially shapes what could be learned, and that limit is stated explicitly below rather than glossed over.

**State A — as-built** (no `--options runtime`, ad-hoc linker-signed, empty entitlements): launches and fetches `https://example.com` correctly (§Q2). Baseline.

**State B — re-signed inside-out with hardened runtime, mirroring Norma's current posture** (empty entitlements everywhere except `allow-jit` on the Renderer helper, matching the "already established" Chrome fact):

```
codesign -f -s - --options runtime --entitlements empty.entitlements   "Chromium Embedded Framework.framework"
codesign -f -s - --options runtime --entitlements jit.entitlements     "cefsimple Helper (Renderer).app"
codesign -f -s - --options runtime --entitlements empty.entitlements   "cefsimple Helper (GPU).app"
codesign -f -s - --options runtime --entitlements empty.entitlements   "cefsimple Helper (Plugin).app"
codesign -f -s - --options runtime --entitlements empty.entitlements   "cefsimple Helper (Alerts).app"
codesign -f -s - --options runtime --entitlements empty.entitlements   "cefsimple Helper.app"
codesign -f -s - --options runtime --entitlements empty.entitlements   "cefsimple.app"
```

`codesign --verify --deep --strict` **passed** ("valid on disk", "satisfies its Designated Requirement"). The app then **failed to launch.** Direct execution (not `open`, which swallows stderr) showed the exact cause:

```
cef_load_library: dlopen .../Chromium Embedded Framework: dlopen(...): tried:
'.../Chromium Embedded Framework.framework/Chromium Embedded Framework'
(code signature in <UUID> '.../Chromium Embedded Framework' not valid for use
in process: mapping process and mapped file (non-platform) have different Team IDs)
...
Failed to load the CEF framework.
```

**Root cause:** two Mach-O binaries signed ad-hoc, in separate `codesign` invocations, carry **no Team ID at all** — ad-hoc signing has no notion of a shared identity. Hardened runtime's library validation (armed by `--options runtime`) requires the loading process and the framework it loads to share a Team ID (or the loaded code to be Apple-signed), and two independently-ad-hoc-signed binaries never satisfy that.

**State C — added `com.apple.security.cs.disable-library-validation`** to every bundle's entitlements (Renderer keeps `allow-jit` too): `codesign --verify` passed, and this time the app **launched successfully** — 7 processes, all PIDs stable for 2+ minutes, no crash reports in `~/Library/Logs/DiagnosticReports`. Local rendering works fully under this signing: navigating to `data:text/html,<h1>hello-local</h1>` via CDP produced `document.body.innerText === "hello-local"` and a valid 18,388-byte PNG from `Page.captureScreenshot`, both immediately.

**But a live `https://example.com` fetch through that same running instance did not.** The page target sat at `readyState: "complete"` with an empty title and empty body for over two minutes. Direct execution with `--enable-logging=stderr --v=1` named the failure:

```
[...ERROR:cef/libcef/browser/browser_info_manager.cc:858] Timeout of new browser info response for frame ...
[...ERROR:base/mac/process_requirement.cc:159] Unable to derive validation category for current process.
  Signature validation of current process failed: Error Domain=NSOSStatusErrorDomain Code=-67030 "(null)" (-67030)
```

**Interpretation** (labeled as interpretation, since this was not root-caused further): `disable-library-validation` only defeats dyld's library-validation check. Chromium carries its **own**, separate macOS process-validation layer (`base/mac/process_requirement.cc`) used to authenticate cooperating processes for its internal IPC/sandbox-broker plumbing, and that layer appears to independently require a consistent code-signing identity across processes — which, again, two separately ad-hoc-signed processes don't have. Patching the dyld-level check doesn't patch this second, CEF/Chromium-internal one.

**The caveat that matters most for Plan B:** this entire crash-and-workaround cycle is very plausibly a pure artifact of testing with ad-hoc-only signing, which the ground rules required. A real Developer ID build signs the framework, every helper, and the outer app with the **same certificate**, so every one of them shares a single real Team ID by construction — exactly the condition both the dyld check and (very likely) Chromium's own process-validation check are designed to accept. This reconciles cleanly with `2026-08-07-embedded-surfaces.md`'s direct measurement of `/Applications/ChatGPT.app`: real Developer ID, one Team ID throughout, shipping **without** `disable-library-validation` at all. **Do not carry `disable-library-validation` into Plan B's entitlements based on this spike** — the evidence instead says: sign with one real identity, inside-out, and test that specific recipe early, because ad-hoc testing structurally cannot validate this path all the way through (and, here, did not).

## Q5 — The Swift bridging shape

Read `tests/cefsimple/cefsimple_mac.mm`, `process_helper_mac.cc`, `tests/shared/browser/main_message_loop_external_pump_mac.mm`, and `include/wrapper/cef_library_loader.h` in full.

**Before `CefInitialize`:** the framework must be `dlopen`'d at runtime (never linked directly — a macOS sandboxing requirement CEF documents in `cef_library_loader.h`), via `CefScopedLibraryLoader::LoadInMain()`:

```objc
int main(int argc, char* argv[]) {
  CefScopedLibraryLoader library_loader;
  if (!library_loader.LoadInMain()) {
    return 1;
  }
  CefMainArgs main_args(argc, argv);
  @autoreleasepool {
    [SimpleApplication sharedApplication];
    CHECK([NSApp isKindOfClass:[SimpleApplication class]]);
    ...
    CefSettings settings;
    CefRefPtr<SimpleApp> app(new SimpleApp);
    if (!CefInitialize(main_args, settings, app.get(), nullptr)) {
      return CefGetExitCode();
    }
    ...
    CefRunMessageLoop();   // blocks until CefQuitMessageLoop()
    CefShutdown();
  }
  return 0;
}
```

**The `NSApplication` subclass** must implement `CefAppProtocol` exactly as the "already established" facts describe — confirmed verbatim in `cefsimple_mac.mm`:

```objc
@interface SimpleApplication : NSApplication <CefAppProtocol> {
 @private
  BOOL handlingSendEvent_;
}
@end

@implementation SimpleApplication
- (BOOL)isHandlingSendEvent { return handlingSendEvent_; }
- (void)setHandlingSendEvent:(BOOL)handlingSendEvent { handlingSendEvent_ = handlingSendEvent; }
- (void)sendEvent:(NSEvent*)event {
  CefScopedSendingEvent sendingEventScoper;
  [super sendEvent:event];
}
@end
```

It also overrides `-terminate:` to redirect Cocoa's default (`exit()`-calling, run-loop-skipping) quit behavior into CEF's own orderly `CloseAllBrowsers` → `CefQuitMessageLoop` shutdown sequence — a second, less obvious reason a plain stock `NSApplication` cannot be used.

**The helper process entry point** matches the "already established" fact exactly, and is short enough to quote in full — this is genuinely all of it, 37 lines:

```c
int main(int argc, char* argv[]) {
#if defined(CEF_USE_SANDBOX)
  CefScopedSandboxContext sandbox_context;
  if (!sandbox_context.Initialize(argc, argv)) {
    return 1;
  }
#endif
  CefScopedLibraryLoader library_loader;
  if (!library_loader.LoadInHelper()) {
    return 1;
  }
  CefMainArgs main_args(argc, argv);
  return CefExecuteProcess(main_args, nullptr, nullptr);
}
```

**The `CefApp`/`CefBrowserProcessHandler` implementation is plain C++, not Objective-C++** — `simple_app.h` declares `class SimpleApp : public CefApp, public CefBrowserProcessHandler`, a normal C++ class with `IMPLEMENT_REFCOUNTING`. Only the pieces that must talk to Cocoa (the `NSApplication` subclass, the delegate, and the message-pump timer below) need to live in `.mm` files. That narrows what an Obj-C++ bridge actually has to own: not "all of CEF," just the AppKit-facing seam.

**The external pump — the piece Norma actually needs, which no sample runs by default** (per correction #3). `main_message_loop_external_pump_mac.mm` implements it with an `NSTimer`, and the detail that is easy to drop in a Swift port is which run-loop modes the timer is added to:

```objc
void MainMessageLoopExternalPumpMac::SetTimer(int64_t delay_ms) {
  ...
  timer_ = [NSTimer timerWithTimeInterval:delay_s
                                   target:event_handler_
                                 selector:@selector(timerTimeout:)
                                 userInfo:nil
                                  repeats:NO];
  NSRunLoop* owner_runloop = [NSRunLoop currentRunLoop];
  [owner_runloop addTimer:timer_ forMode:NSRunLoopCommonModes];
  [owner_runloop addTimer:timer_ forMode:NSEventTrackingRunLoopMode];
}

void MainMessageLoopExternalPumpMac::OnScheduleMessagePumpWork(int64_t delay_ms) {
  // May be called on any thread — hop to the owner thread first.
  [event_handler_ performSelector:@selector(scheduleWork:)
                         onThread:owner_thread_
                       withObject:[NSNumber numberWithInt:(int)delay_ms]
                    waitUntilDone:NO];
}
```

A timer added only to the default run-loop mode (what a naive Swift `Timer.scheduledTimer(withTimeInterval:...)` gives you) **stalls while the user resizes a window, tracks a menu, or does anything else that pumps the event-tracking run loop mode instead of the default one** — the classic "NSTimer freezes during a drag" bug, except here it would freeze CEF's entire message pump, and by extension the embedded browser, for the duration. This is exactly the class of concrete detail the controller's prior 17 plan defects were made of, and it only shows up by reading the actual source, not by reasoning about the API from its header.

**The bigger structural point:** `MainMessageLoopExternalPumpMac::Run()` still calls `[NSApp run]` itself —
```objc
int MainMessageLoopExternalPumpMac::Run() {
  [NSApp run];
  ...
}
```
— meaning even CEF's "external pump" sample is written assuming *it* owns the application's run loop; it merely lets CEF's internal work interleave with Cocoa's rather than block it. **No sample in this distribution shows CEF embedded inside a host that already has its own run loop running** (SwiftUI's `App` protocol, in Norma's case). Plan B has to adapt this pattern, not copy it: implement `OnScheduleMessagePumpWork`/`SetTimer` as shown, but never call `[NSApp run]` — SwiftUI already owns that — and rely on Norma's existing, already-explicit `NSPrincipalClass` override in `apple/Norma/project.yml:97` (currently pointed at plain `NSApplication`) to install a `CefAppProtocol`-conforming subclass in its place. **That last sentence is reasoned from what `project.yml` already declares plus CEF's documented requirements, not independently verified against a running SwiftUI+CEF app** — building that was out of scope for this spike (§ "Could not determine").

**A fork in the road worth flagging, found while reading, not asked for:** the standard distribution's `tests/cefsimple_capi/` is a second complete implementation of the *same* sample against CEF's plain **C API** (`include/capi/*.h`) instead of the C++ API — struct-of-function-pointers, manual atomic reference counting, no virtual-method inheritance at all (`simple_app.c` was read in full). Swift's C-interop layer imports plain C structs and function pointers far more directly than it can bridge C++ virtual classes, which normally requires an Objective-C++ shim in between. Whether the C API actually imports cleanly through Swift's `ClangImporter` (macro-heavy headers, the ref-counting boilerplate macros, etc. are a real risk) was **not tested** — but it's a materially different possible bridging strategy for Plan B to weigh against the ObjC++-shim approach the C++ API forces, and it costs little to spend an afternoon on before committing.

**Also observed, unprompted:** CDP's target list for a bare, default `cefsimple` launch included two `"type": "browser_ui"` targets titled "Omnibox Popup" (`chrome://omnibox-popup.top-chrome/...`) alongside the one content page. Current CEF defaults to **Chrome-style** runtime (a fuller browser-chrome UI, address bar included), not the older, bare "Alloy style" content-only window — `simple_app.c` in the C-API sample even branches on a `--use-alloy-style` switch and a `cef_runtime_style_t` enum. A panel that wants to be *just* an embedded content surface (which is what Norma's tab panel wants) will need to deliberately request Alloy-style / a plain child-`NSView` browser rather than take CEF's new default, or it will get an unwanted mini-Chrome window-chrome stack along for the ride.

## What surprised me

- The minimal distribution containing **zero** sample-app source was more absolute than "trimmed" implied — there is no `tests/` directory at all, not even headers or stubs.
- CEF's own CMake template shipping **five** helper suffixes and **zero** entitlements anywhere — both cut against what the "already established" facts assumed CEF hands you for free.
- The `cefsimple` build itself being I/O/codesign-bound (5% CPU over 2 minutes), not compute-bound — the compile step is fast; assembling and ad-hoc-signing the bundle is what takes the wall clock.
- Modern CEF defaulting to Chrome-style UI (omnibox popup targets present in a "simple" sample) rather than a bare content view.
- The hardened-runtime failure not being one problem but two stacked ones: a dyld-level Team-ID check fixable by an entitlement, and a second, CEF/Chromium-internal process-validation check (`base/mac/process_requirement.cc`) that the entitlement doesn't touch, discovered only by turning on stderr logging and reading the actual error.
- How much OS-level verification (`screencapture`) silently lies in this kind of sandboxed environment — CDP turned out to be the more trustworthy prover of "did it actually render," being independent of the OS window server entirely.

## What Plan B must handle that is not obvious

- **Five helper targets in `project.yml`, not four** — including Plugin, which the pre-spike brief omitted.
- **Every entitlement is Plan B's to add.** Nothing about CEF's build gives Norma `allow-jit` or anything else "for free" the way it might for a Google-built Chrome.
- **The message-loop integration has no template to copy.** `main_message_loop_external_pump_mac.mm` is the closest reference, but it must be *adapted* (drop `[NSApp run]`, keep the `NSRunLoopCommonModes` + `NSEventTrackingRunLoopMode` timer scheduling) rather than ported as-is, because Norma's SwiftUI app — unlike every CEF sample — already owns its run loop.
- **Sign with one real Developer ID identity end-to-end and test that exact path early.** The ad-hoc-only failure mode in §Q4 (and its workaround) should not be treated as Plan B's actual signing recipe; it's a symptom of the ad-hoc constraint this spike had to work under. The real risk is that the *real* recipe hasn't been tried yet.
- **Decide Alloy-style vs Chrome-style deliberately.** The default in this CEF version brings browser chrome (omnibox popup UI) that a pure content panel almost certainly doesn't want.
- **The C API is a real alternative bridging path**, not just the C++-via-ObjC++-shim path the "already established" facts assumed — worth a short, separate evaluation before committing to the shim architecture.
- **Locale trimming is a legitimate, CEF-endorsed way to cut the 81 MB Resources figure** if Norma only needs a handful of languages — not evaluated here, but real and documented.

## What I could not determine

- **Whether the real Developer ID signing recipe (one identity, inside-out, no `disable-library-validation`) actually launches and fetches network content cleanly.** Only ad-hoc signing was tested, per the ground rules; §Q4's conclusion that the ad-hoc failure is testing-artifact rather than a real blocker is inference from first principles (Team ID consistency) and from the separate, already-recorded ChatGPT.app measurement — it is not itself a direct measurement from this spike.
- **The exact root cause inside `base/mac/process_requirement.cc`** — the mechanism was named (a macOS code-signature "validation category" check failing with `NSOSStatusErrorDomain` code `-67030`) but not traced further into Chromium's source; I don't have a symbolic name for that OSStatus code I can vouch for (the local SDK headers didn't expose it, and I chose not to state a symbol name from memory).
- **Whether `cefsimple_capi`'s plain-C API actually imports cleanly into a Swift package via `ClangImporter`.** Flagged as a promising alternative in §Q5; not built or tested against Swift in any way.
- **Whether Norma's existing `NSPrincipalClass: NSApplication` override in `project.yml:97` is sufficient, on its own, to install a `CefAppProtocol`-conforming `NSApplication` subclass under SwiftUI's app lifecycle.** This is a reasoned inference from reading `project.yml` and CEF's documented requirement, not a built-and-run test — building that crosses into "integrating into Norma," which was out of scope.
- **Actual compressed/DMG-delta impact** on Norma's release pipeline and Sparkle updates — out of scope for this spike (it targeted the uncompressed framework size specifically), but the number Plan B will actually feel on every release is a compressed/delta figure, not the 332 MB uncompressed one reported here.
- **GPU/software-rendering behavior under a *correctly* Developer-ID-signed build** — State C's local-content success (data: URL) suggests compositing itself is fine under hardened runtime with the right entitlements, but this was only observed under the ad-hoc + disable-library-validation combination, not under real signing.
