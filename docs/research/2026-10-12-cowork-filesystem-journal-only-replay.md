## Contract

An exact known previously-ready volume may receive `replay-journal-then-probe` in normal startup. Its closed target binds the last confirmed ready operation, volume/creation/purpose, file identity, UUID and geometry. Only v2/v3 exact-contract ready history qualifies; minimal v1, unknown/restored/migrated/unformatted or uncertain formatting histories cannot acquire this permission. Format-new retains one-shot virgin rules and cannot claim journal replay.

Core commits a bounded `replayDebt` tuple before writable handoff. The tuple is the exact operation and owner; malformed/missing debt and forged ready references fail closed. New plans require a separate fail-closed `authorizeJournalReplay` port for current native writable authority. Current public/default production provisioning remains unavailable; these trusted callbacks must be wired by the actual native producer, never inferred from a descriptor or guest packet.

A failed or interrupted replay-capable operation retains probing state, canonical owner, debt and last confirmed history. It does not release ownership, restore readiness or regain format eligibility. Recovery is idempotent but is not permission to overlap uncertain writers: a new attempt requires a distinct current owner and mandatory `verifyPreviousReplayStopped` evidence for the exact old operation/owner, plus renewed write authority. Missing/failed stop proof holds debt. The existing raw owner-release verifier remains mandatory. A read-only check also cannot erase old uncertain-write debt without that stop proof. Read-only failures without write debt remain safely retryable.

The immutable bootstrap preflights BOTH borrowed/pinned targets read-only before any write: identity/mode/size, expected UUID, capacity/block geometry, exact persistent features and normal clean-state checks. Only clean state plus `needs_recovery` takes the journal route. Already-clean disks run probes only, reporting `journalReplayed:false`; an error/non-clean state still refuses into explicit full-check recovery. Explicit full-read-only checking of existing volumes never replays. There is no full repair, preen, journal recreation request, or automatic reformat path.

The only recovery command is fixed `e2fsck -E journal_only` on the admitted RW FD, with no `-p`, `-y` or `-f`. Its config/environment are fixed, input is /dev/null, output/time are bounded, and success accepts only 0/1 before fsync and a fresh read-only exact probe. The fresh probe must show no pending transient recovery; protected receipt carries actual `journalReplayed` per volume. A pending/forged/stale receipt cannot confirm ready. [e2fsprogs 1.47 implementation](https://github.com/tytso/e2fsprogs/blob/v1.47.0/e2fsck/unix.c), [e2fsck journal-only semantics](https://man7.org/linux/man-pages/man8/e2fsck.8.html).

Protocol 1/2 receipts remain readable history only. Current confirmations/readiness require v3 and its explicit replay observations. No existing filesystem is reformatted to upgrade protocol; a new protected probe/replay plan provides current observations. This is an explicit native-envelope contract revision; the signed worker/bootstrap and future immutable image must be updated/reviewed together before activation. The previously frozen packaged image is not silently relabeled.
