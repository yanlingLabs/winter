**Why zero guest TX waits is compatible with backpressure.** Source paths in this paragraph are under the cached upstream Linux `6.18.35` archive, extracted to `spikes/cowork-hvf/out/stream-hvc-source`. The archive hash and all five extracted members were independently checked against `results/2026-10-12-stream-hvc-kernel-source-audit.json` and against the actual archive members. This is primary-source evidence for the boot-reported version; exact build equivalence between that upstream archive and the separately pinned measured kernel binary remains unverified.

`drivers/tty/hvc/hvc_console.c:499–551` copies/pushes chunks through `hvc_push`, which calls `hp->ops->put_chars` at line 480. `drivers/char/virtio_console.c:1107–1125` implements that callback and explicitly calls `__send_to_port(..., false)`. Its lines 607–640 take the output-queue irqsave spinlock and, on the successful non-asynchronous path, spin until the host returns the virtqueue buffer or the queue breaks. The callback then returns the amount written. The HVC callback receives no userspace `O_NONBLOCK` flag. `drivers/tty/tty_io.c:952–1028` can split and aggregate lower-level writes into one full successful userspace write. Consequently, lower-level ACK delay need not become EAGAIN or a short userspace result. The zero guest TX counters cannot establish that the private host stream never filled or that the driver never waited.

This differs from the generic non-console port path: `virtio_console.c:776–838` checks `O_NONBLOCK`, can return EAGAIN before queuing, and invokes `__send_to_port` with `nonblock=true`. Merely opening `/dev/vport...` for the existing console cannot select that behavior: `port_fops_open` at lines 1034–1040 refuses console ports. A real generic port requires an intentional device/feature/control-handshake change.

The run's timing is consistent with synchronous TX delay: raw-mode readiness appears at about 0.165 seconds; first guest TX progress appears at 3.011 seconds, just after the host's three-second read pause. The second heartbeat is also only observed around 3.004 seconds. These are capture/telemetry observations, not measured guest write start/end or a native capacity-wait trace; they do not prove the exact blocking interval or healthy guest scheduling throughout the initial pause. The sustained later freed windows do demonstrate concurrent progress. Do not replace the failed assertion with a claim that a guest TX stall was measured.

**Production consequence and recommendation.** The before/after monotonic checks in `stream_fixture_init.c:93–103` detect an overdue write after it returns; they cannot preempt a guest syscall that is spinning inside this HVC driver. `O_NONBLOCK`, a dedicated guest I/O thread, or a userspace timeout alone is therefore not a bounded-write/cancellation guarantee. The fixture's independent host-worker alarm and finite supervisor kill/reap remain its whole-VM backstop. Native host Stop/reset source tests have their earlier scope; normal poweroff in this run adds no live guest reset or stalled-syscall cancellation proof.

For v1's long-lived concurrent control/runtime traffic, **prefer one generic non-console virtio port with the minimum required MULTIPORT/control handshake** if the transport must preserve the rest of the guest while applying backpressure or cancelling one operation. That would select the source's asynchronous port path and avoid this known HVC spin-until-ACK behavior. This is a recommendation for the next integration decision, not a mechanism implemented or validated here. It adds control queues and feature/lifecycle parsing: the current two-queue admission, pin/exclusion and reset evidence cannot simply be extended to it by assertion.

HVC can still suffice for a deliberately bounded bring-up/control lane if the design explicitly accepts whole-worker recovery on a transport stall: a trusted dedicated guest I/O owner, bounded message/queue sizes, a separately supervised sandboxed host peer that keeps draining independently of approvals or model work, and an out-of-band host deadline that terminates/reaps the workspace worker on sink failure or overflow. It must not depend on sending a shutdown message through the blocked channel. A dedicated guest I/O thread alone is insufficient because the kernel spin holds interrupts/locks and can affect other guest work. That design would need its delivery/replay/cold-continuity behavior defined around the possible whole-VM abort; none follows from this fixture.
