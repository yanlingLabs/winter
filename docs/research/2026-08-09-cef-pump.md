# CEF inside a run loop SwiftUI already owns

**Date:** 2026-08-09 · **Status:** scratch app only, nothing shipped, nothing integrated into Norma · **Question:** every CEF sample owns the application's run loop — `cefsimple` calls the blocking `CefRunMessageLoop()`, and even the external-pump sample calls `[NSApp run]` itself (`main_message_loop_external_pump_mac.mm:110`). Norma is a SwiftUI app whose run loop already exists. Can CEF be driven from inside it, and what does that cost?

**Short answer: yes — a page renders, proven by pixels, with CEF driven entirely from SwiftUI's run loop and no `CefRunMessageLoop()` anywhere.** Three things qualify that:

1. **The mechanism the spike assumed would install the required `NSApplication` subclass — `Info.plist`'s `NSPrincipalClass` — does not work under SwiftUI at all.** It is silently ignored. The fix is small but it changes Norma's app entry point: `@main` has to go, replaced by a `main.swift`. This is the plan-altering finding.
2. **The pump is cheap** — 1–4% of one core across all six processes at idle, at CEF's own 33 ms ceiling — **and it does not stall under event tracking, provided the timer is not registered in the default run-loop mode alone.** Registered the naive Swift way, CEF's pump does *zero* work for the entire duration of a window resize: measured, 5 seconds, 0 `DoWork` calls.
3. **One intermittent first-load failure went un-root-caused.** Every structural cause was excluded by control and it then stopped reproducing (1 in 24 runs). It is the honest soft spot here, and §"What breaks" documents both it and the two ways I nearly misdiagnosed it.

This file is the only write inside the repo. All work happened in a scratch directory; the dev app and daemon were never launched or touched; `~/.norma` and `~/.norma-dev` were never read or written. The CEF distribution the spike downloaded (`cef_binary_151.3.16+gbe1e15d+chromium-151.0.7922.109_macosarm64`) was reused as-is — nothing was re-downloaded and no Chromium was built from source.

## The headline correction

**`NSPrincipalClass` is ignored by SwiftUI's `App` lifecycle.** The spike's §Q5 closed with an explicitly-unverified inference:

> rely on Norma's existing, already-explicit `NSPrincipalClass` override in `apple/Norma/project.yml:97` (currently pointed at plain `NSApplication`) to install a `CefAppProtocol`-conforming subclass in its place

That inference is **false**, and it was the first thing measured. A 60-line SwiftUI app — `@main struct App`, `@NSApplicationDelegateAdaptor`, `NSPrincipalClass` set to a logging `NSApplication` subclass in a hand-written `Info.plist`:

```
SMOKE[applicationWillFinishLaunching]: NSApp class = SwiftUI.AppKitApplication; is PumpApplication = false; principalClassInPlist = PumpApplication
SMOKE[applicationDidFinishLaunching]:  NSApp class = SwiftUI.AppKitApplication; is PumpApplication = false; principalClassInPlist = PumpApplication
SMOKE[after 2s of run loop]:           NSApp class = SwiftUI.AppKitApplication; is PumpApplication = false; principalClassInPlist = PumpApplication
```

`PumpApplication.init()` never ran and `sendEvent:` never fired. SwiftUI's `App.main()` does not route through `NSApplicationMain`'s principal-class lookup; it constructs its own private `SwiftUI.AppKitApplication` and ignores the key. Norma's `project.yml:97` `NSPrincipalClass: NSApplication` has, in other words, never done anything — which is why nothing has broken so far, and why nothing would warn Plan B that setting it to a CEF subclass silently does nothing.

Since CEF's `CefScopedSendingEvent` calls `[NSApp setHandlingSendEvent:]` on whatever `NSApp` is, a plain `SwiftUI.AppKitApplication` would fail that call. **This is a hard prerequisite, not a nicety.**

### The fix, measured working

`+[NSApplication sharedApplication]` returns the existing `NSApp` if one is already set, regardless of which subclass receives the message. So the CEF subclass simply has to get there first — which means Norma needs an explicit `main.swift` instead of `@main`:

```swift
// main.swift — top-level code; the `@main` attribute must be REMOVED from the App struct
import AppKit

let app = NormaCEFApplication.shared   // claims the singleton first
PumpApplicationScene.main()            // SwiftUI's App.main() now reuses it
```

Measured result, same app otherwise:

```
PUMP: main.swift: NSApp = NormaCEFApplication
PUMP: willFinishLaunching: NSApp = NormaCEFApplication
...
16 doWork=546 ctx=true windows=1 visible=true
```

SwiftUI's `WindowGroup` still creates and shows its window (`windows=1 visible=true`), the delegate adaptor still fires, and `sendEvent:` now runs through the CEF subclass. Two constraints come with this:

- `@main` and a `main.swift` are mutually exclusive — `swiftc` errors with *"'main' attribute cannot be used in a module that contains top-level code"*. Norma's `NormaApp.swift` must drop `@main` in the same change.
- A single-file `swiftc` invocation needs `-parse-as-library` for `@main` to work at all; the moment `main.swift` exists that flag must go. Xcode/xcodegen handle this by filename convention, but it is a real trap when reproducing this outside a build system.

## What the wiring actually looks like

The scratch app is `NormaCEFPump.app`: SwiftUI `@main`-equivalent entry, an `NSApplication` subclass, an Objective-C++ shim, five helper bundles, and the framework — the same shape `NormaCEF` will have. Compile and link flags were cribbed verbatim from the `cefsimple` build the spike already proved on this machine (`build/tests/cefsimple/CMakeFiles/cefsimple.dir/{flags.make,link.txt}`) rather than re-derived.

### The bridging seam is narrower than expected

The C++ API never has to reach Swift. The shim's entire Swift-facing header is plain Objective-C:

```objc
@interface NormaCEFApplication : NSApplication
@end

#ifdef __cplusplus
extern "C" {
#endif
BOOL NormaCEFLoadLibrary(void);
BOOL NormaCEFInitialize(int argc, char **argv, int remoteDebuggingPort,
                        const char *rootCachePath, const char *subprocessPath);
void NormaCEFCreateBrowser(NSView *parent, const char *url);
void NormaCEFResizeToParent(NSView *parent);
void NormaCEFShutdown(void);
#ifdef __cplusplus
}
#endif
```

Consumed from Swift with nothing but `-import-objc-header`. **The `extern "C"` block is load-bearing**: the implementation is `.mm`, so without it the definitions get C++ mangling and Swift's C-linkage references fail to link with a wall of undefined symbols. That cost one build cycle to find.

This also means the spike's flagged "fork in the road" — CEF's plain **C API** (`cefsimple_capi`) as an alternative to a C++-via-ObjC++ shim — **is not a fork Plan B needs to take**. The ObjC++ shim confines C++ entirely to one `.mm` file, and Swift never sees a CEF type. The C API remains untested here and no longer looks necessary.

### The `NSApplication` subclass

```objc
@interface NormaCEFApplication () <CefAppProtocol> {
 @private
  BOOL handlingSendEvent_;
}
@end

@implementation NormaCEFApplication
- (BOOL)isHandlingSendEvent { return handlingSendEvent_; }
- (void)setHandlingSendEvent:(BOOL)handlingSendEvent { handlingSendEvent_ = handlingSendEvent; }
- (void)sendEvent:(NSEvent *)event {
  CefScopedSendingEvent sendingEventScoper;
  [super sendEvent:event];
}
- (void)terminate:(id)sender {
  NormaCEFShutdown();
  [super terminate:sender];
}
@end
```

`CefAppProtocol` (`include/cef_application_mac.h`) is only `-isHandlingSendEvent` + `-setHandlingSendEvent:` inherited from Chromium's `CrAppControlProtocol`. Conformance is what CEF checks — not class identity — but the subclass is still required, because `sendEvent:` must be wrapped.

### The pump, and the one line that is easy to lose

`MainMessageLoopExternalPump` (the algorithm) and `MainMessageLoopExternalPumpMac` (the `NSTimer`) were ported essentially verbatim, with `[NSApp run]` removed. **Both source files live under `tests/shared/`, which the *minimal* distribution does not ship** (the spike's §Q1 established there is no `tests/` directory there at all). Plan B must vendor these ~100 lines into `NormaCEF`; it cannot depend on them.

The scheduling algorithm is fully specified by CEF and has no free parameters worth inventing:

```cpp
const int32_t kTimerDelayPlaceholder = INT_MAX;
const int64_t kMaxTimerDelay = 1000 / 30;  // 30fps

void OnScheduleWork(int64_t delay_ms) {
  if (delay_ms == kTimerDelayPlaceholder && IsTimerPending()) return;
  KillTimer();
  if (delay_ms <= 0) { DoWork(); }
  else { if (delay_ms > kMaxTimerDelay) delay_ms = kMaxTimerDelay; SetTimer(delay_ms); }
}
```

plus a re-entrancy guard around `CefDoMessageLoopWork()` — `CefDoMessageLoopWork` can re-enter the pump through paint and IPC callbacks, and the discarded call must be reposted rather than dropped.

The timer's run-loop modes are the detail that only shows up by reading the source:

```objc
NSRunLoop *owner_runloop = [NSRunLoop currentRunLoop];
[owner_runloop addTimer:timer_ forMode:NSRunLoopCommonModes];
[owner_runloop addTimer:timer_ forMode:NSEventTrackingRunLoopMode];
```

A naive `Timer.scheduledTimer(withTimeInterval:)` registers in the default mode only. **This was measured as an A/B rather than argued** — see §C below.

`OnScheduleMessagePumpWork` can arrive on any CEF thread and must hop to the main thread first:

```objc
[handler_ performSelector:@selector(scheduleWork:)
                 onThread:[NSThread mainThread]
               withObject:[NSNumber numberWithLongLong:delay_ms]
            waitUntilDone:NO];
```

### Ordering, in the only order that works

Inside `applicationWillFinishLaunching` (which worked first time; `didFinishLaunching` was never needed as a fallback):

1. `NormaCEFApplication.shared` — **before this**, in `main.swift`, before SwiftUI exists.
2. `cef_scoped_library_loader_create(0)` — `dlopen`s the framework from `Contents/Frameworks`. The framework is never linked; `cef_library_loader.h` documents this as a macOS sandbox requirement. Nothing else in the shim may be called first.
3. `CefInitialize(main_args, settings, app, nullptr)` with `external_message_pump = true`.

Real `argv` is passed through (`CommandLine.argc` / `CommandLine.unsafeArgv`), and the proof plumbing goes through `CefSettings` rather than command-line switches — `remote_debugging_port`, `root_cache_path`, `browser_subprocess_path` are all set in code.

**`OnContextInitialized` fired synchronously inside `CefInitialize`**, contrary to my expectation going in: `contextInitialized(immediately) = true` on every run. The scratch app still queues browser creation behind it, and Plan B should keep that queue — the ordering is timing-dependent, not contractual, and `NSViewRepresentable.makeNSView` can plausibly run before the context on a slower or busier launch. But the measured behaviour here is synchronous, and this report should not be cited as evidence that it is async.

### Embedding into an `NSView`

`CefWindowInfo::SetAsChild(parent, bounds)` with the `NSViewRepresentable`'s container view. Per `cef_types_mac.h:152`, **providing `parent_view` already forces Alloy style**, so the embed dodges the Chrome-style omnibox chrome the spike warned about automatically; `runtime_style = CEF_RUNTIME_STYLE_ALLOY` is set explicitly anyway so a future refactor cannot silently inherit it.

Creating the browser in `makeNSView` — when the container is **not yet in an `NSWindow`** — works. This was tested against the alternative (deferring to `viewDidMoveToWindow`) and both load and render identically (see the control table in finding 2). It is not a constraint, though deferring is the more defensive choice.

## Did a page render?

**Yes.** Proven the way the spike established was trustworthy in this environment — CDP `Page.captureScreenshot`, which asks the browser's own compositor for pixels and is unaffected by the missing Screen Recording TCC permission that makes `screencapture` return a false-negative black frame.

```
url        = data:text/html,<h1 id=hello>hello-from-swiftui-pump</h1>...
readyState = complete
h1         = "hello-from-swiftui-pump"
bodyLen    = 23
screenshot = shot-data.png 19570 bytes   (PNG image data, 1800 x 1200, 8-bit/color RGB)
```

The PNG contains the actual rendered heading. **Network URLs render too**, which is the result that matters for a browser panel: `https://example.com` in the child view produced a 1800×1200 PNG showing the fully laid-out page — heading, body copy, and styled "Learn more" link — and `http://localhost:8899/` did the same with the request visible in the server's own access log. Across every scratch-app run whose document was actually probed after the rebuild — **23 runs, 1 failure** — this held, with the document committing at t+1.0 s on 5 of 5 in a dedicated timing harness (the single exception is finding 2 below).

To be precise about what that proves: the pixels come from Chromium's compositor inside a browser whose every message-loop turn was driven by `CefDoMessageLoopWork()` calls scheduled from `OnScheduleMessagePumpWork` onto SwiftUI's run loop. `CefRunMessageLoop()` is never called, and `[NSApp run]` is called only by SwiftUI itself, exactly once, as it always was.

## What it costs

### Idle CPU, and what the scheduling ceiling buys

`kMaxTimerDelay` is the one parameter with no obviously correct value, so it was swept. A static `data:` page (deliberately *not* the rAF page used for the tracking test — a requestAnimationFrame loop is not idle), 30-second window, CPU measured as a **cumulative CPU-time delta** across the main process and all five helpers. macOS `ps %cpu` is a decaying since-start average, not an instantaneous reading, and reports meaningfully different numbers; the delta method is the one quoted here.

| `kMaxTimerDelay` | measured pump rate | CPU across all 6 processes |
| --- | --- | --- |
| 16 ms | 61.1 `DoWork`/s | 2.6% of one core |
| **33 ms (CEF's own `1000/30`)** | **30.3 `DoWork`/s** | **1.3% of one core** |
| 100 ms | 10.4 `DoWork`/s | 3.4% of one core |

**The pump rate tracks the ceiling exactly and linearly** — 61.1, 30.3, 10.4 against a predicted 62.5, 30.3, 10.0 — which is the clearest evidence that the ported scheduling algorithm behaves as CEF's does. The CPU column does **not** move monotonically, and the 100 ms row costing more than the 33 ms row is a strong hint that between-run noise dominates the differences at this magnitude. The honest reading is: **idle cost is 1–4% of one core across the whole process tree at every setting tested, and the pump interval is not the thing that decides it.**

**I settled on CEF's own 33 ms**, and the reasoning is not the CPU column — it's that 33 ms is the value CEF's reference implementation ships, it bounds worst-case input-to-paint latency at one 30fps frame, and nothing measured here argues for deviating from it. Choosing 100 ms to "save CPU" would be optimising against noise while tripling worst-case latency.

### Did the UI stay responsive

Within what could be tested without TCC permissions, yes. Across every run: `NSApp.windows.count = 1` with `visible = true`, a 1 Hz main-thread `Timer` never missed a beat over runs of 60+ seconds, and a 50 ms SwiftUI `Timer.publish` heartbeat view animated continuously alongside the browser. Nothing in the pump starved SwiftUI's own rendering.

The important caveat is in §"What I could not determine": no real drag, live resize, menu track, or scroll was ever synthesised. What *was* tested is the run-loop condition those produce — below.

### The run-loop-mode trap, measured

The spike identified the run-loop-mode registration as the detail "easy to drop in a Swift port". It is, and it is worth exactly what the spike said it was. Rather than argue it, the harness holds the main run loop in `NSEventTrackingRunLoopMode` for a real 5 seconds — the same run-loop condition AppKit creates for the entire duration of a window resize, a menu track, or a scroll-wheel drag — and counts `CefDoMessageLoopWork()` calls across the window.

Same binary, same page, one environment variable apart:

| timer registered in | `DoWork` during the 5 s window | `DoWork`/s, per second, across the window |
| --- | --- | --- |
| `NSRunLoopCommonModes` + `NSEventTrackingRunLoopMode` (CEF's recipe) | **151** (`580 → 731`, ~30/s) | `… 30 32 31 30 30 30 31 30 …` |
| `NSDefaultRunLoopMode` only (what `Timer.scheduledTimer` gives you) | **0** (`572 → 572`) | `… 33 8 0 0 0 0 23 30 …` |

**Five seconds, zero message-loop work.** CEF's pump — and with it the embedded browser, every animation, every network callback, every paint — stops dead for the entire duration and resumes only when tracking ends. This is a total freeze, not a slowdown, and it would present as "the panel hangs whenever you resize the window." It is invisible in any test that does not enter a tracking mode, and no CEF sample exercises it because samples own their run loop.

**Which of the two registrations is doing the work was not established.** The A/B compared *both modes* against *default only*; it never tested `NSRunLoopCommonModes` alone. It is often said that AppKit adds event tracking to the common-modes set, which would make CEF's second `addTimer:` redundant — but that was **not measured here**, and if it is wrong, registering only `.common` reintroduces exactly the 5-second freeze above. **Register both, as CEF does.** What is measured is the failure mode of the default mode alone, which is what the idiomatic Swift one-liner gives you.

## What breaks, and what surprised me

**1. `codesign -f -s -` breaks the renderer; leaving the linker's signature alone fixes it.** The first build ad-hoc-signed every bundle inside-out, the way the spike's §Q4 recipe does. The app launched, the pump ran, CDP's target list appeared — and every `Runtime.evaluate` hung forever, with the log showing the same error the spike saw in State C:

```
base/mac/process_requirement.cc:159 Unable to derive validation category for current process.
Signature validation of current process failed: NSOSStatusErrorDomain Code=-67030
```

The difference is a signature *class*, not an entitlement:

| | flags | https loads |
| --- | --- | --- |
| `codesign -f -s -` (explicit ad-hoc) | `0x2(adhoc)` | **no — renderer wedges** |
| as-built, untouched (linker ad-hoc) | `0x20002(adhoc,linker-signed)` | yes |

The `cefsimple` the spike proved working is `adhoc,linker-signed` on the app, every helper, and the framework — CEF's macOS build never explicitly codesigns; `ld`'s automatic arm64 ad-hoc signature is what it ships. **Removing the codesign step entirely made the error disappear.** For Plan B this is a *development*-build rule: do not re-ad-hoc-sign CEF bundles in Debug. It says nothing about the real Developer ID path, which remains untested (spike §Q4's open question is still open).

**2. An intermittent first-load failure I could not root-cause — and a warning about how easy it is to misdiagnose.** This consumed most of the task's time and is the honest soft spot in this report.

Early in the session, five consecutive runs showed the first navigation never producing content: the CDP target *listed* the right URL, but the live document was `about:blank` with `readyState: "complete"` and an empty body. `data:` URLs were unaffected; `http://localhost` and `https://` failed alike, so it was never TLS, DNS or the network. Nothing appeared in the app's log even under `--enable-logging=stderr --v=1`.

**Every structural explanation was eliminated by control:**

| Control | loads a network URL |
| --- | --- |
| stock `cefsimple` (Views, Chrome style, `CefRunMessageLoop`) | yes |
| `cefsimple --use-native --use-alloy-style` | yes — so **not** Alloy style |
| `cefclient --external-message-pump` (CEF's own external pump) | yes — so **not** the external pump as a concept |
| scratch app, child view, created in `makeNSView` | yes |
| scratch app, creation deferred to `viewDidMoveToWindow` | yes — so **not** "parent view not yet in a window" |
| scratch app, top-level browser, no `parent_view` | yes — so **not** child-view embedding |

**Then it stopped reproducing.** Across every scratch-app run after an intervening rebuild — 3 discriminator runs, 3 reproducibility runs, 12 `LATE_INIT` A/B runs, 5 commit-timing runs — it recurred exactly **once in 23**. (The cefclient control is excluded from that tally; it is not this app.) A dedicated timing harness that attaches CDP immediately and polls without ever issuing a navigation of its own found the document committed at **t+1.0 s on 5 of 5 runs**. When this works, it is instant; a ten-second wait is already anomalous.

Two ways I nearly misdiagnosed this, both worth recording:

- **`about:blank` + `readyState: "complete"` is also the *pre-commit* state of a fresh tab.** A single early sample cannot distinguish "aborted" from "hasn't committed yet". Several of my early "failures" were probes at 12 s that later passed at 18 s.
- **The `net::ERR_ABORTED  canceled: true` I treated as the smoking gun was very likely self-inflicted.** It came from a CDP `Page.navigate` issued *while the original load was still in flight* — which is exactly how Chromium reports a superseded navigation. The dedicated harness never issues `Page.navigate` for this reason.

The one correlate that survived: on the failing runs the pump did markedly less work in the first second (`doWork=40` in the first heartbeat, versus 82–122 on passing runs). That is consistent with a startup starvation window — `CefInitialize` runs inside `applicationWillFinishLaunching`, before the host run loop is spinning, so the `performSelector:onThread:` posts that `OnScheduleMessagePumpWork` depends on cannot be serviced during precisely the interval in which CEF is standing up its first browser. **This hazard structurally cannot arise in any CEF sample**, because a sample calls `[NSApp run]` itself immediately after initialising, and it is the one mechanism unique to the embed-in-an-existing-run-loop shape.

I tried to test that hypothesis directly (`NORMA_CEF_LATE_INIT`, deferring `CefInitialize` to a `DispatchQueue.main.async`) and **the experiment was inconclusive on both sides**: the baseline had stopped failing (6/6 pass), so there was nothing to improve, and the log shows the deferral did not actually push `CefInitialize` past the run loop starting — the order stayed `CefInitialize` → `makeNSView` → `didFinishLaunching`. Read the `LATE_INIT` result as "not tested", not as "the hypothesis is wrong."

**3. `RunLoop.run(mode:before:)` returns after one input source, not at the limit date.** My first event-tracking test used it directly and produced a confident non-result — the "tracking window" lasted one timer fire (`doWork` 552 → 553), so the correct and incorrect run-loop-mode registrations measured identically. It has to be looped:

```swift
let end = Date().addingTimeInterval(5)
while Date() < end { RunLoop.current.run(mode: .eventTracking, before: end) }
```

Recorded because anyone writing this same test will hit it, and the first version *looks* like it passes.

**4. `OnContextInitialized` fired synchronously inside `CefInitialize`** on every run, which is the opposite of what I expected going in and worth not over-generalising in either direction (see §"Ordering" above).

**5. `extern "C"` around the shim's C entry points** — an `.mm` file mangles them otherwise, and the failure is a wall of Swift link errors that look like a missing object file.

**6. ChatGPT.app on this machine runs Chromium `151.0.7922.71`**, against CEF 151.3.16's `151.0.7922.109` — noticed incidentally while checking for stray processes. The embedded-surfaces measurement and this CEF build are essentially the same Chromium generation.

## What Plan B must handle that is not obvious

- **Norma's app entry point has to change.** `apple/Norma/Sources/App/NormaApp.swift` must drop `@main`, and a new `main.swift` must instantiate the `CefAppProtocol`-conforming `NSApplication` subclass before calling `NormaApp.main()`. `project.yml:97`'s `NSPrincipalClass` is inert under SwiftUI and cannot do this — it never has. This is the single least obvious thing in the whole task, and the spike's §Q5 explicitly (and honestly) flagged it as inferred rather than tested; it does not survive testing. Norma is unusually well-placed for the change — its Scene is already just `Settings { EmptyView() }` with every real window AppKit-owned by `AppDelegate` — but it is still a change to the app's entry point, not an additive one.
- **Vendor the pump, don't reference it.** `main_message_loop_external_pump.cc` / `_mac.mm` live under `tests/shared/`, absent from the minimal distribution. ~100 lines, including the `INT_MAX` placeholder protocol, the 33 ms ceiling, and the re-entrancy repost — all three are load-bearing.
- **Register the pump timer in `NSRunLoopCommonModes` *and* `NSEventTrackingRunLoopMode`.**
- **Do not re-ad-hoc-sign CEF bundles in Debug builds** (finding 1). Norma's Debug builds sign ad-hoc today; if Plan B adds a nested-bundle signing loop, gate it to Release the way the existing `norma-core` resign step already is.
- **Do not trust the first navigation blindly** (finding 2). It committed in ~1 s on every clean measurement, but failed outright in a cluster early on and once more afterwards, and was never root-caused. Wire `CefLoadHandler::OnLoadError` / `OnLoadEnd` and give the panel a visible retry rather than assuming the first page just appears — and note that a probe which navigates to check on a load will itself abort that load.
- **The Swift-facing bridge can be pure C + ObjC.** The C-API-vs-C++ fork the spike flagged does not need resolving; the ObjC++ shim keeps every CEF type out of Swift.
- **`SetAsChild` already forces Alloy style**, so the Chrome-style omnibox chrome the spike warned about is avoided by construction in an embedded panel — but set `runtime_style` explicitly anyway.

## What I could not determine

- **The root cause of the intermittent first-load failure** (finding 2). Every structural explanation was excluded by control and the symptom then stopped reproducing (1 in 24 runs afterwards), which is the worst possible outcome for diagnosis: it is neither reproducible enough to bisect nor rare enough to dismiss. The starvation hypothesis is plausible and specific but **untested** — the `LATE_INIT` experiment did not actually defer past the run-loop start. If Plan B sees an empty panel on first open, start here.
- **Anything about real Developer ID signing.** Every run here is ad-hoc/linker-signed with no hardened runtime. The spike's §Q4 question — does one real identity, signed inside-out, launch and fetch cleanly — is still open, and finding 1 above narrows but does not answer it.
- **Real user-interaction responsiveness.** Entering `NSEventTrackingRunLoopMode` programmatically reproduces the run-loop condition of a drag, but no actual drag, resize, menu-track, or scroll was synthesised — that needs Accessibility/Screen-Recording TCC permissions this environment does not have. Whether a genuine live resize of a CEF-hosting SwiftUI window is smooth is **untested**.
- **Norma-specific deltas.** The scratch app is a regular-activation-policy app with one `WindowGroup` and one fixed browser view. Norma is `LSUIElement: true` with AppKit-owned windows and a menu-bar orb. Nothing measured here touches activation policy, and there is no reason to expect it to interact with run-loop mechanics — but it was not tested, and Norma's `syncDockPresence` machinery already shows this app has non-trivial activation-policy behaviour.
- **Shutdown latency is variable and unexplained.** The orderly path works — `NSApp.terminate(nil)` → the `-terminate:` override → `CloseBrowser` → `CefShutdown`. On the one run where the exit was captured it took **~2 s and returned exit code 0, with zero orphaned helper processes**. On an earlier run the process was still alive 11 s after `terminate:` and had exited by the time it was next checked; its exit code was never observed, only the absence of any crash report. So: it completes cleanly, but the latency varies by at least an order of magnitude and was not chased. Worth re-measuring with more than one browser open.
- **Multiple simultaneous browsers**, tab switching, and the `NSViewRepresentable` resize path under real layout changes — one browser, one view, fixed size throughout.

## The scratch app, for reproduction

Everything lives outside the repo, in this session's scratchpad (`.../scratchpad/cef-pump/`), and reuses the spike's already-downloaded, already-built distribution at `.../scratchpad/cef-spike/` — nothing was re-downloaded and `libcef_dll_wrapper.a` was reused as-is. `cefclient` was built once (for the D4 control) with `make -j14 cefclient`; no Chromium was built from source at any point.

| File | What it is |
| --- | --- |
| `Sources/main.swift` | Top-level entry: claims the `NSApplication` singleton, then calls SwiftUI's `App.main()` |
| `Sources/App.swift` | SwiftUI `App`, delegate, `NSViewRepresentable` browser host, heartbeat + harness switches |
| `Shim/NormaCEF.h` | The entire Swift-facing surface: plain ObjC + `extern "C"`, no CEF types |
